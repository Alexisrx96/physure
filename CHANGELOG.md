## [Unreleased]

### Added
- **The `interval` flag of the catalog** (spec `docs/superpowers/specs/2026-11-20-interval-flag-design.md`; commits `2e89ac0`, `996d7b3`, `c101917`, `63ab4bd`). A unit line may carry `interval`, as `noprefix` and `own_kind`: a temperature interval, how far apart two points are. The catalog's `delta_celsius` and `delta_fahrenheit` carry it, and a unit system's own definitions may (`dT = 1.0, O, interval, [dT]`): a user's interval unit is now caught as `delta_degC` is. `RationalUnit` has `interval: bool` (not part of equality or of the hash: `delta_degC` is a kelvin, the two convert with the factor 1 and compare equal in value); `UnitFacts`, Python's `facts()` and the Python `RationalUnit` say it. The flag on a unit with a zero point, on a level, on the base unit of a dimension or on a unit of a dimension with no point defined before it (`zm = 2.0, L, interval`) is refused with the reason. A user's line that restates an interval entry without the flag (`delta_celsius = 1.0, O, [...]` copied from the 0.4.0 catalog into a project's `physure.conf`) is refused, and the entry stays an interval: without this, `5 delta_degC < 20 degC` was `True` and `20 degC => delta_degC` `293.15 delta_degC` again under such a conf. The core's arithmetic carries it: an interval times or over a ratio (`2`, `50 %`), an interval plus or minus an interval, and a point minus a point (still printed in `K`) are intervals; a step through another dimension drops it. A plain `K` (or `degR`) is of unknown kind, an absolute temperature (`20 degC => K`) or a difference, and so is its sum with an interval, in either order: `(300 K + 5 delta_degC) => degC` is `31.85 degC` and compares with a point. A frozen file records it with its sources, `phs conf diff` and `show` see it, and a file frozen before the flag keeps the shipped `delta_celsius` and `delta_fahrenheit` intervals (the trusted reading flags them).
- **`physure-wasm` has a README and npm metadata** (commit `9176583`; the README of the npm package, `homepage`, `bugs` and nine `keywords` in `physure-wasm/package.json`), and the root README has an npm badge (commit `79a5e18`). npm 0.4.0 was published without them: a published npm version cannot change, so the package page shows them from the next version.

- **`sec`, `csc`, `cot` and `erf` exist at run time** (audit T4; commits `049c74f`, `d5b673d`). `sec`, `csc` and `cot` were produced by the symbolic engine (`integral("tan(x)", "x")` is `ln(abs(sec(x)))`; `erf` is not known to it: `deriv("erf(x)", "x")` and `integral("erf(x)", "x")` say 'Unknown symbolic function') and the interpreter did not know them, so `sec(1)` was "Undefined function" and `integral("sec(x)^2", "x", 0, 1)` was refused: the quadrature that confirms an antiderivative evaluates the integrand through the interpreter. They are core functions of PHS and of the Rust `Quantity` now. `sec`, `csc` and `cot` take an angle or a plain number read as radians, like `sin` (`sec(60 deg)` is 2, `sec(1 m)` is an error); `cot(0)` and `csc(0)` are an error ("cot of 0 is undefined"), not infinity. `erf` takes a dimensionless value, like `exp` (an angle is refused). The uncertainty is propagated in every mode (Gaussian, Monte Carlo, unscented, moments). `integral("sec(x)^2", "x", 0, 1)` is `tan(1)` = 1.5574077246549023 now, and `integral("sec(x)", "x", 0, 1)` is `ln(sec 1 + tan 1)`.

### Changed
- **Breaking: a temperature point does not convert to an interval unit, nor an interval to a point** (spec `docs/superpowers/specs/2026-11-20-interval-flag-design.md`; commits `1b1c378`, `63ab4bd`, `3dcd6af`). `20 degC => delta_degC` was `293.15 delta_degC` (the point's absolute value read as an interval) and `5 delta_degC => degC` was `-268.15 degC` (the interval read as kelvin above absolute zero); `Quantity::convert_to` and the plan `UnitRegistry::conversion` refuse both ("cannot convert a temperature point (`20.0 degC`) to a temperature interval (`delta_degC`): a point says where, an interval says how far; ..."), and Python's `.to()` raises `IncompatibleUnitsError` with the core's words. A difference of two points is an interval, so `(20 degC - 10 degC) => degC` is refused too, in PHS, the core, Python and WebAssembly; not in Java, whose `Quantity` carries its unit as text, so the difference is a plain `K` back in Java and still converts to `-263.15 degC` (an open line of the roadmap; a unit written as an interval is refused in Java as everywhere). **What to write instead:** a difference of two points (`(20 degC - 0 degC) => delta_degC` is `20 delta_degC`), or a point moved by an interval (`T1 + 5 delta_degC`). `10 K => delta_degC` and `5 delta_degC => K` convert as before (a plain `K` is of unknown kind, a point or an interval).
- **Python `round` of a quantity ties away from zero, as the core and PHS do** (spec `docs/superpowers/specs/2026-11-20-python-rounding-delegates-design.md`; commits `8bd6c80`, `6cbb8cc`, `a884865`, `5509bcb`). `round`, `math.floor`, `math.ceil` and `math.trunc` of a scalar `Quantity` were Python's own: they rounded the magnitude with Python's `round` and rebuilt the quantity. They are the core's `Quantity::round`, `floor`, `ceil` and `trunc` now (`trunc` is new in the core; the PyO3 `Quantity` has `round`, `floor`, `ceil`, `trunc`, `from_lineage` and `lineage`). **What changes:** a tie goes away from zero: `round(Q_(2.5, 'm'))` was `2 m` and is `3 m`, `round(Q_(-2.5, 'm'))` was `-2 m` and is `-3 m`, `round(Q_(0.125, 'm'), 2)` was `0.12 m` and is `0.13 m`; a scalar NumPy magnitude (`np.float32`) comes back as a Python float; and the result keeps the uncertainty's sources, so it is correlated with the unrounded value (`x - round(x, 1)` had a standard deviation of 0.14 for `x = 1.234 +/- 0.1 m`, it is 0, in the Gaussian, Monte Carlo and unscented modes and under `python_lineage()`) and keeps the degrees of freedom (`round(Q_.from_samples(..), 1).dof` was `inf`). **Known difference:** an array-backed magnitude (NumPy, PyTorch, JAX) is not the core's, which is scalar: it keeps its backend's own path, JAX's elementwise half-to-even `round` (`round` of `[0.5, 1.5, 2.5] m` is `[0, 2, 2] m`) and a `TypeError` for the others, as before (an open line of `docs/ROADMAP.md`).
- **A temperature point and a temperature interval do not compare** (spec `docs/superpowers/specs/2026-11-20-round-and-temperature-kinds-design.md`; commits `ee6cdd3`, `128e5be`, `3b28db3`, `9a91774`, and after the review `3e54635`, `c7655bb`, `fd685d7`). `5 delta_degC < 20 degC` was `True`, `5 delta_degC > 20 degC` `False`, `5 delta_degC == 5 degC` `False`, `max(5 delta_degC, 20 degC)` `20 degC`, and `vector(5 delta_degC, 20 degC)` was accepted: the interval was read as an absolute temperature of 5 K. The comparison of the core (`Quantity::comparable_magnitudes`, behind `<`, `>`, `<=`, `>=`, `==`, `!=`, `assert(a, b)` and `phs_compare` of every binding) refuses a point (`degC`, `degF`) against a unit written as an interval (`delta_degC`, `degC_delta`, `delta_degF`, `delta_fahrenheit`), in either order: ``cannot compare a temperature point (`20.0 degC`) with a temperature interval (`5.0 delta_degC`)``. `max`, `min`, a vector, `linspace` and a range refuse the pair too (`max of a temperature point and a temperature interval: ...`, `a vector holds one dimension and one kind of temperature: ...`), also when a `K` stands between them (`max(1 K, 25 delta_degC, 20 degC)`, `[300 K, 5 delta_degC, 20 degC]`): every element is set against the first point and the first interval of the list. Python's `Quantity` `<`, `>`, `<=`, `>=` raise `IncompatibleUnitsError` for the pair, with the core's words (`point_against_interval_message`), and `==` is `False`, as the core says (`UnitRegistry.point_against_interval`, asked only for a temperature); `IncompatibleUnitsError` takes an optional `reason`. Point with point (`20 degC > 10 K`, `20 degC == 68 degF`) and interval with interval (`5 delta_degC < 6 delta_degC`) are unchanged, and `K` and `degR`, which stand for a point or an interval alike, compare with both (`(30 degC - 20 degC) > 5 delta_degC`). **Breaking; what to write instead:** compare the difference of two points with the interval (`T2 - T1 > 5 delta_degC`). `x => K` does not make an interval a point: it reads its number as kelvin above absolute zero (`5 delta_degC => K` is 5 K, -268.15 degC), which is what the old comparison silently did; write it only if that is the meaning. `phs check` does not flag the pair (the interpreter does).
- **`max`, `min`, a vector, `linspace` and `round` refuse values of different dimensions** (spec `docs/superpowers/specs/2026-11-17-unit-holes-design.md`; commits `5e5187d`, `b8e0fda`, `a5e9461`, `35ab0d8`, `c806eee`, and after the review `5469ca6`, `46f053e`, `6fa8d76`, `c6828cd`). Each answered with a confident unit where there is no answer: `max(1 m, 1 s)` and `min(1 m, 2)` were `1.0 m` (base-unit magnitudes compared across dimensions), `max(20 dB, 2)` was `20 dB` and `max(3 dB, 2)` was `2.0`, `vector(1 m, 2 s)` and `[1 m, 2 s]` were accepted (and `norm`, `dot`, `trapz`, `det`, `matmul` refused their elements later, one by one), and so was a mixed vector built by a `for`, `parallel_map`, `transpose`, a plugin or a Python host function; `linspace(0 m, 1 s, 3)` took the unit of the first endpoint and the number of the second, `linspace(0 m, "x", 3)` read the text as 1, a count of `2.7` was truncated, and `round(1.5 m, 1 s)` read its decimals from a quantity whose unit it ignored. **This is a breaking change** (decision of the owner of 2026-11-17: the elements of a vector share one dimension). **What to change:** compare values of one dimension (`max(1 m, 30 cm)`; a plain number compares only with a dimensionless value that is not a level, a level only as `<` compares it (`max(20 dB, 30 dB)`), and an angle is its own dimension: `max(1 rad, 1)` is an error); put each dimension in its own vector (a state vector of a position and a time is two vectors, `x = [1 m, 2 m]` and `t = [0 s, 1 s]`; a matrix may keep rows of different dimensions, `[[1 m, 2 m], [1 s, 2 s]]`, but its transpose is refused); give `linspace` numeric endpoints of one dimension and a whole, non-negative count; give `round` a whole, plain number of decimals (negative ones still round to tens). The messages name both values and their dimensions, and what made the vector when it is not `vector(...)`: `` max of different dimensions: `1 m` is a length and `1 s` a time; compare values of one dimension ``, `` a vector holds one dimension: the `for` gives one where `1 m` is a length and `1 s` a time; put each dimension in its own vector ``. Details. Two values have one dimension when `<` would set them side by side: the test `1 m + 1 s` is refused by (`RationalUnit::same_dimensions`), and, when a level is in it, `Quantity::comparable_magnitudes`; one helper of `physure-script` (`builtins/dimensions.rs`) asks it. Every vector the interpreter builds goes through `PhsValue::vector_checked` (a new public function of `physure-script`): `vector(...)` and `[...]`, an elementwise operation (which names the operation: `2 m ^ vector(1, 2)` gives `` the elementwise `^` gives one where ... ``), a `for`, `parallel_map`, `gradient`, `cross`, each row of `transpose` and `matmul`, a plugin's vector, and a list a Python host function returns or passes to `invoke` (a Python `ValueError`). The ones left build one unit by construction (`linspace`, a conversion) or hold text. Not covered: a Rust embedder that writes `PhsValue::Vector(...)` itself. A vector of one dimension in several units (`vector(1 m, 2 km)`) and text are unchanged; the rows of a matrix are not compared with each other. `max(v)` and `min(v)` of one vector argument are the extremum of its elements (an empty vector is an error); one number or quantity is itself, and anything else is "expects numbers or quantities" (it was returned unchecked). `linspace` reads both endpoints in the unit of the points, which fixes a wrong answer found writing the tests: `linspace(0 m, 1 km, 3)` was `[0.0 m, 0.5 m, 1.0 m]` (the `1` of `1 km` read as metres) and is `[0.0 m, 500.0 m, 1000.0 m]`; `linspace(0 m, 10 m, 5 s)`, an endpoint that is not a number or a quantity, and a count of `2.7`, `50 percent` or `-3` are errors; `linspace(0, 1)` keeps its 50 points. `round(x, 2.7)` and `round(x, 1 percent)` are errors ("round needs a whole number of decimals"). `phs check`'s `mixed-extremum`, its one warning while the interpreter accepted the program, is an error, and the report says it once (`check::explains` knows the runtime words); no finding is a warning today. The checker still does not see vectors, so a mixed vector is found when the line runs. Tests that pinned the old answers were changed: `min(3, 1 m)` (now `min(3 m, 1 m)`, and the mixed form asserted refused), `from_samples([1.0 V, 2.0 m])`, which the vector now refuses before `from_samples` sees it, and the `phs check` and language-server tests that used `max(1 m, 1 s)` as their example of a warning.
- **A name with no value is an error, not its own text** (audit T5; commits `f113796`, `1338828`, `5b3e4b0`, `9e48139`, `bd374a2`, `18d329f`, `664ee0f`, `8c9c62f`, `9187767`, `0f48b71`). A bare name with no binding, no `pi` or constant and no unit symbol was the string of itself: `foo` was the text `foo`, so a typo or a missing definition became a value that travelled until some later operation refused it, far from the cause, and the interpreter disagreed with the JavaScript the same program transpiles to (a `ReferenceError`). It is the error `` `foo` has no value `` now, in every position (a statement, an operand, a call argument, a condition, the value of a `=>`, a range, the iterable of a `for`); the message adds the likely fix when there is one, in this order: a function of PHS written as a value (`` `sqrt` has no value: `sqrt` is a function of PHS, not a value; pass a user function (`fn f(x) = sqrt(x)`) or write the call ``), a name the program binds at most two edits away (`speeed` gives `` `speeed` has no value: did you mean `speed`? ``), a unit one edit away for a name of four characters or more, or a slip of case (`5 metre` gives `` `metre` has no value — did you mean the unit 'metro'? ``, `5 Km` names `km`); a one-letter or short name gets no unit hint (the catalog has a symbol next to almost every short word: `x` was told `'A'`, `count` `'pound'`), and a condition that is a lower-case `true` or `false` still says that the Bool literals are `True` and `False`. **This is a breaking change.** **What to change:** a program that used a free word as a text now fails; quote it (`"foo"`) or define the name. The forms that read this way and worked are: the variable of a function of `calc` or `plot` written bare (`deriv("x^2", x)`, `deriv(x, x)`, `integral("x^2", x)`, `integral("x^2", x, 0, 1)`, `integral(x, x)`, `limit("sin(x)/x", x, 0)` and `lim`, `substitute("x + 1", x, 2)`, `series("sin(x)", x, 0, 5)` and `taylor`, `dsolve("y' = y", y, x)`, `grad("x^2+y^2", [x, y])`, `solve(e1, x)`, `plot("sin(x)", x, 0, 1)`): write the variable as text, `"x"`; the error says so (`` `x` has no value: the variable of `deriv` is text, write "x" ``). A function of PHS passed by name (`parallel_map(sqrt, v)`, `plot(sin, 0, 1)`): pass a user function (`fn f(x) = sqrt(x)`) or the expression as text. `m = 5` followed by `[1, 2] m` (or `(2 + 3) m`) was `[5.0, 10.0]`, the variable; the unit after an expression is a unit now, so the line is refused as ambiguous, as `5 m` is in that program: write `* m` for the variable or `* "m"` for the unit. `format(x, spec)` evaluates its second argument (`s1 = ".2f"; format(3.14159, s1)` is `3.14`), and an unknown spec, which was read as `.6f` without a word, is an error naming the valid forms (`base`, `frac`, `ifrac`, `.N` with `f`, `e` or `g`). A program that ran and never used a free word as a text is unchanged. Details. The format words (`x: base`, `x: frac`, `x: ifrac`, `x: .2f`, `.2e`, ...) are text in the syntax tree (`format(x, "base")`) and no longer looked up as names, so a variable named `base` or `frac` no longer changes the format; `format(x, spec)` written as a call evaluates `spec` as before T5 (a first version of this change read a bare identifier there as its own text, which made `format(3.14159, s1)` print `3.141590`). The Rust and Java generators wrote the word as a bare `.2f`, which compiles in neither; they write the text now, and the Python generator no longer turns `format(x, s1)` into `format(x, "s1")`. Two things worked only because a name was its own text and keep working: a unit written after an expression, `(2 + 3) m/s` and `[1, 2] m`, is built by the parser as the unit's literal (`1 m/s`; before, it was a name made of the unit's text, and the code generators emitted that text as a bare identifier, which does not run in any target; they write a quantity of 1 in the unit now, but only of the first unit of a compound: `(x) kg m/s^2` is written `x * Q_(1.0, "kg") * m / s ** 2.0`, with `m` and `s` bare identifiers in every target, a gap older than T5 recorded in the roadmap); and `f'(x)` with a free `x` is read as the derivative's variable. The two patches that detected a name that evaluated to its own text (`=>` and a condition) are gone, the general error replaces them, and `check::explains` knows the new wording so the report does not say one problem twice. Measured before the change over the suites of `physure-script`, `physure-cli` and `physure-lsp` (362 fallbacks) and over every program of the documentation and the guide (a test, `docs_programs_need_no_unbound_names`, keeps it so): the only working program that relied on the fallback was the format spec; the others were half-typed documents, lower-case `true`/`false`, deliberate error cases and programs the checker already flagged. The checker and the interpreter agree (a program the checker flags as an unknown name, the interpreter refuses naming it; a name the interpreter gives a value is never flagged); the language server shows a half-typed word as an error diagnostic; Python, WebAssembly and Java get the error with no code change, and one test of each of the last two, which read the text `x` of a variable of another registry, now expects the error. Every code generator writes an unbound name as the bare identifier, which does not run (JavaScript and TypeScript: a `ReferenceError`; Rust and Java: it does not compile; Python: a `NameError`), and refuses it at transpile time when the program's own statements evaluate it.

- **A program can no longer bind a statement word, a literal or a core function, nor a function of a module it imports** (spec `docs/superpowers/specs/2026-11-16-reserved-names-design.md`, phase 1; commits `63922bb`, `a6408c6`, `7487bf4`). `use`, `from`, `import`, `export`, `as`, `fn` and `in`; `true`, `false`, `None`, `none`, `inf`, `infinity` and `oo`; the 31 functions of the core (`abs`, `max`, `min`, `round`, `floor`, `ceil`, `sqrt`, `sin`, `cos`, `tan`, `exp`, `ln`, `log`, `format`, `assert`, `vector`, `uncertainty`, `sigma`, `dof`, ...); and, from the `use` on, the functions of `calc`, `array` or `plot` that the program imports (`use * from calc` reserves all of `calc`, `use solve from calc` reserves `solve`, `use solve as sv from calc` reserves `sv` and leaves `solve` free) are refused as a variable, a parameter, a function name, a `for` variable, a `where` binding or an import alias, with an error that names the class: "`max` is a function of PHS and cannot be bound as a variable; choose another name". An import of a function of `calc`, `array` or `plot` that would replace a variable or a function the program already holds, or remap a function the program already imported under that name, is refused too. Before, a call always reached the builtin, so `fn max(a, b) = 100` was accepted and never called, and `inf = 3` was accepted while `inf` stayed infinity. **What to change:** rename a variable, parameter or function that has one of these names. Not reserved: unit names (`m`, `s`, `kg`), `e`, the words of a format (`base`, `frac`). The variables of an equation call (`eq(sigma=5, A=2)`) are local to the call and are refused only when they are a keyword, a literal, `pi` or a catalog constant. `in` is also the inch symbol: a variable cannot be named `in`, and a quantity written with the unit (`2 in`) is unaffected. Phases 2 and 3 are in the entries below.
- **`sec`, `csc`, `cot` and `erf` are reserved names** (audit T4; commit `d5b673d`). They are functions of the core now, so they join the reserved names of the entry above. **What to change:** a variable, parameter or function with one of these names is an error; that includes `fn sec(x) = 1/cos(x)`, the old workaround, which can simply be deleted now. `sec` as a unit (`3 sec`, `2 sec => ms`, `=> sec`) is unaffected: a call needs `sec(`, which the unit grammar does not take.
- **`phs check` reports a reserved name before the program runs** (phase 2 of the reserved names; commits `5dad248`, `29d8d88`). The checker reads the top-level statements in order and reports, with the code `reserved-name`, a statement word, a literal or a core function bound in any form, a function of an imported module bound after its `use`, an import over a name the program holds, and an import that would remap one; it says what the interpreter says. The decision about an import is one function (`reserved::plan_import`, commit `fd4ece1`) that the interpreter calls too. The checker may miss what the interpreter refuses (an import nested in a function or a loop body, a name a `.phs` import binds) and never reports what the interpreter accepts.
- **A value a host gives and an equation-call argument are local, and a host or a plugin cannot install a function under a reserved name** (phase 3 of the reserved names; commits `d0beea2`, `15c2c9a`). `run_program_with` and `eq(sigma=5, A=2)` bind a name for one run, and a local never hides a call, so a name like `sigma`, `max` or `dof` is accepted there (it was refused for a host value in the entries above, which broke the Java `PhyEquation.callWith` for an equation with a variable named `sigma`); a keyword, a literal, `pi` and the catalog's constants are still refused. `PhsInterpreter::register_fn` returns a `Result` and refuses a reserved name, as does the import of a native plugin that exports one, because a call would reach the builtin first and the function would never run; the Python `register_function` raises `ValueError`. An import of a module function over a function a host registered or a plugin installed is refused too (the order hosts use: register at start-up, `use` later). The Python `ext/` loader names the file and the function when one of them is refused. **What to change:** an embedder that calls `register_fn` adds `?` or `.unwrap()`; a function registered as `max` or `sin`, and a public function named like a core function in an `ext/*.py` file of a Python project, needs another name.
- **The language guide lists the reserved names** (commit `14d6f66`). `PHYSURE_LANGUAGE_GUIDE.md` has a section 1.7 generated from the table (`phs doc`), and a test of `physure-cli` fails when the committed guide is not what `phs doc` prints.

### Fixed
- **A temperature interval is known by the catalog's flag, not by the name of its unit** (spec `docs/superpowers/specs/2026-11-20-interval-flag-design.md`; commits `2e89ac0`, `996d7b3`, `1b1c378`, `63ab4bd`). `RationalUnit::is_written_interval` tested the name for `delta_` / `_delta`, so: `(1 K + 5 delta_degC) < 20 degC` was accepted while `(5 delta_degC + 1 K) < 20 degC` was refused (the name followed the left operand), now both are accepted, in PHS, the core and Python, since the `K` may be an absolute temperature (`300 K + 5 delta_degC` is 31.85 degC): the second one, refused by name before, is accepted now; in Python the sum of a `K` and an interval is written in `K` (`5 delta_degC + 1 K` was `6 delta_degC`), while PHS and the core still print `6.0 delta_degC` (the name is a label there, the kind is the flag); `(5 delta_degC * 50 %) < 20 degC` lost the name and was `True`, now refused; an interval unit of a user's conf (`dT`) was not caught, now it is; `(20 degC - 10 degC) < 20 degC` was `True` (a point minus a point is `K`, which counted as either), now refused; `20 degC => delta_degC` was `293.15 delta_degC`, now refused (Changed above). Values are unchanged; printed units too, except the Python sum above. **Still open**, as the spec decides (a step through another dimension drops the flag): `(5 delta_degC * 1 s / 1 s) < 20 degC` and `sqrt((5 delta_degC)^2) < 20 degC` are still `True`; see `docs/ROADMAP.md` section 3.

- **The numeric `limit` decides the same whatever unit the point is written in, confirms an infinity before answering it, and scales its first step to a small point** (audit T11; commits `642af8a`, `c4b3bef`). It sampled from a first step of 1/8 *of the unit the point was written in*, so the same limit gave a different answer in `m`, `mm`, `km` and `um`: of 1200 pairs of units measured, 394 differed (accepted in one, refused in the other), and `limit("(x/(1 m))/((x/(1 m))*(1+1e6*(x/(1 m))^2))", "x", 0 km)`, a hole whose limit is 1, answered `inf`. What holds now:
  - **The same decision in every unit.** The variable is sampled in the coherent unit of the point's dimension (a dimensionless point such as `3 percent` is the plain number 0.03), so the value or the refusal is the same whether the point is written in `m`, `km` or `um`. A plain-number variable is still the user's own scale: `limit("sin(x*1e3)/(x*1e3)", "x", 0)` is refused as before.
  - **Narrow features are refused, not answered.** At 0 the smallest step is about 6e-5 of the coherent unit, so a feature narrower than about 1e-3 of it is refused in every unit: the hole above is refused at `0 m`, `0 km` and `0 um` alike (it was answered 1 in `mm` and `um`, `inf` in `km` and `Mm`).
  - **An infinity is confirmed by finer sampling.** A bounded function seen from farther off than its feature grows like an infinity: `limit("x/(x*(1+(x/(1 nm))^2))", "x", 0 nm)` and the plain `limit("x/(x*(1+1e9*x^2))", "x", 0)` answered `inf` (the plain one before T11 too). An infinity at a finite point is now sampled again down to 1e-12 of the coherent unit next to 0 (1e-8 of `|p|` elsewhere) and refused when the growth stops; `1/x`, `1/x^2`, `ln(x)` and a pole away from 0 still answer `inf` or `-inf`. A bounded function whose feature is narrower than that (`x/(x*(1+1e30*x^2))` at 0) still reads as `inf`: this is not a guarantee.
  - **The first step is scaled to a small point.** At `|p| < 1` (coherent) the first step is `|p|/8`, not 1/8, so the samples no longer cross 0, where `ln` ends: `limit("ln(x/(2 mL))/(x/(2 mL)-1)", "x", 2 mL)` answers 1 (with the coherent step alone it said the limit does not exist), and so do the same at `5 mg`, `3 um^2` and `1 g`.
  - **The unit of the answer may be the coherent one.** The value at the point itself, where the expression is continuous, is still taken at the point as written (`limit("x", "x", 2 km)` is `2.0 km`), but an extrapolated answer whose unit comes from the variable is given in the coherent unit (`limit("x/sin(x/(1 m))", "x", 0 mm)` is given in `m`, it was `1000 mm`), and a refusal message shows the coherent unit (except the refusal of an uncertain point, which shows the point as written).
- **`phs eval` reports a second problem on a line the checker flagged** (audit T1; commits `5538761` and `5434e1d`). The report dropped every interpreter error on a line the checker had already flagged, so `undefined_fn(1) + (1 m + 1 s)` showed only the dimension mismatch and the undefined function appeared after the first was fixed. The interpreter's error is shown now when it is not the problem the checker said. The two word one problem differently, so `check::explains` matches the wording of the problem's kind and what it names (the same unit, function, parameter, binding or temperature operation): `undefined_fn(1) + 5 fooz` and `("a" + 1) + 5 fooz` report both problems. A problem said by both is still said once, and so is a dimension error (`Unit mismatch`) or a bad exponent on a line where the checker flagged one of that kind, because the interpreter's words do not say which operands failed. `ok` and the findings of programs with one problem per line do not change.

## [0.4.0] - 2026-11-15

**Tags:** `v0.4.0`, `core-v0.4.0`, `java-v0.4.0`, `wasm-v0.4.0`

**Upgrading from 0.3.x.** This release makes PHS say what it means: where 0.3.x quietly answered a question that had no answer, 0.4.0 raises an error that names the fix, and a few answers that depended on the unit or on chance no longer do. What to change in code written against 0.3.x (each is described below):

PHS programs (everywhere PHS runs: `phs`, `phs eval` and MCP, the language server, Python's `PhsInterpreter`, Java and WebAssembly `evaluate`):

- Arithmetic binds tighter than `=>` and comparisons, so `a + b > c` and `x => km < 5 km` now work. `x => km - 5 m` and `x => m + y` are parse errors: write `(x => km) - 5 m`. A chain of comparisons is a parse error: write `a < b and b < c`.
- Two statements on one line need a `;` between them (`1 m => km 2` used to be two statements).
- A zero needs a unit: `x > 0` becomes `x > 0 m` (`t > 0 degC` for a temperature). A level or an angle is not a plain number: `20 dB == 100` becomes `20 dB > 10 dB` or `(x => unity) == 100`, and `30 deg > 0` becomes `30 deg > 0 deg`.
- A condition is a Bool: `while true` becomes `while True`, `if x` becomes `if x != 0 m`, `if s` becomes `if s == "on"`. Text, numbers, vectors and NaN are errors in `if`, `while`, `? :`, `and`, `or`, `not`, `@requires` and `@ensures`.
- `==` and `!=` are relative (1e-12) in any unit, so `1 pm == 2 pm` is now `False`, and nothing but an exact zero equals zero (`cos(90 deg) == 0` is `False`: write `abs(x) < 1e-9 m`); vectors cannot be compared with `==` and strings cannot be ordered with `<` (`s == "on"` still works); `≈` is relative, with `[Settings] approx_rel_tol` (default `1e-3`); `x == t +/- k sigma` needs a measured left operand; `assert(a, b)` is the same test as `==`.
- `pi`, `π` and the 411 constants of the catalog (`molar_gas_constant`, ...) are global names and cannot be bound (`pi = 3`, `f(pi) = ...`, `for pi in ...`): rename the variable. A program that used one of these names as text, or as a unit of value 1, now gets the constant.
- `1 m +/- 0.1 m` is an error: write `1 +/- 0.1 m`. An uncertainty after a parenthesis that is not a literal is an error instead of being dropped, and `=> unit` of a Bool, text, function or `None` is an error.
- `limit`: a two-sided limit needs the expression defined on both sides (`limit("x*ln(x)","x",0)` is an error: pass the side, `limit("x*ln(x)","x",0,"+")`); the fourth argument or `side=` picks a side (it was an error, or silently dropped); calc builtins refuse a keyword they do not take. `integral`, `limit` and `dsolve` refuse what they cannot confirm instead of answering a number.
- Symbolic strings read `-x^2` as `-(x^2)` and refuse `x^2^3`.
- A `.phs` module runs once, in its own scope: it no longer sees the importer's names, a cyclic import is refused, and a module that binds a reserved name makes every import from it an error.
- Monte Carlo draws are deterministic by default (`[Settings] monte_carlo_seed = 0`): write `monte_carlo_seed = random` for the old behaviour. Each unit of evaluation (a program run, a REPL session, a `phs serve` start, a language-server document, a Java or WebAssembly handle, a Python `PhsInterpreter`) draws its own stream, and a loop in `monte_carlo` mode runs on the thread of its unit. A Monte Carlo uncertainty is the sample standard deviation (larger by `sqrt(M/(M-1))`), and fewer than two samples are refused.
- A conversion reads the radian and the steradian as 1 by default (`½·I·ω² => J` works); `[Settings] angle_mode = dimension`, `physure.angle_mode("dimension")` or `units::angle_mode::scoped(AngleMode::Dimension)` bring the old rule back. Sums and comparisons still refuse an angle against a plain number, and `rad/s => Hz` is still refused.
- Printed text changes: a fractional power is `m^(1/2)` (it was `m⁰⋅⁵`), a level keeps its unit under a sign (`-5.0 dB`), and `µm`, `µs` and `µF` now parse (the micro sign is the prefix `u`). `phs transpile` writes comparisons through the core's `phs_compare` and fixes `pi` and the catalog constants at generation; a program the interpreter refuses is not transpiled.

Python:

- `create_system("absent.conf")` raises `FileNotFoundError` (a bare name is a packaged file and never the working directory's), and a dict-validated `Quantity` gets the system "SI", not "Default". `enable_currency()` reads the packaged `currency.conf`.
- `parse_unit_string` moved to `physure.domain.measurement.unit_text`; `CompoundUnit.to_string(use_alias=True)` gives the unit's name; `default_system.settings` no longer holds the six ignored keys; `samples=0` or `1` raises `ValueError`.
- `tensor + seconds` raises `IncompatibleUnitsError` and a plain array leaves a quantity's unit alone; a conversion keeps the sources of the quantity it converts.
- While a frozen configuration is in force (`PHYSURE_CONF`, or a `physure.frozen.conf` found from the working directory upwards), `import physure` raises a `RuntimeError`: Python does not honour a frozen file yet.

Rust (crate `physure`): `Quantity: PartialEq` is exact, so use `Quantity::phs_eq` for the PHS meaning; `MonteCarloBackend::from_stats` returns a `PhysureResult` and `Quantity::new_scalar` panics on fewer than two samples (`try_new_scalar` returns the error); `declare_dof` refuses to change a declared infinite number of degrees of freedom; the crate has a build script that runs `rustc -V` and reads `PHYSURE_BUILD_COMMIT`.

Java: `getUnitExponents` throws `PhysureException` for a fractional exponent (use `getUnitPowers`); results that reuse a measurement differ and are now correct (`x.subtract(x)` is exactly `0`); `evaluate` returns the last statement exactly and refuses a value that is not a quantity; a registry built from custom text throws `Invalid unit definitions: ...` naming the line and really uses its own catalog; `null` is a `NullPointerException` and a NaN or infinite uncertainty an `IllegalArgumentException`; a frozen configuration in force makes the registry calls fail.

WebAssembly: `UnitRegistry.fromContent` throws on a definition it cannot read, and the `Quantity` getters read the displayed triple (`2 m * 3 km` is `6000 m^2`, not `6 m^2`).

Frozen files and `phs eval`, `phs unit`, `phs mcp`, `phs check` are new in this release: nobody on 0.3.x has a frozen file or an earlier `phs eval` to migrate, and only a file made with a development build between the releases reports a changed catalog and new witnesses (run `phs conf update`).

- **One-sided limits: `limit(expr, var, point, side)`** (audit T10; commits `924767f`, `10d8e72`, docs `7593041`). `side` is `"+"` (from the right) or `"-"` (from the left), as the fourth argument or the keyword `side=` (both at once is an error); any other value, and a side at `"inf"`/`"-inf"`, is an error. Before, the fourth argument was an error ("limit expects (expression_string, variable_string, target_point)") and `side="+"` was dropped silently, running a two-sided limit. Now `limit("1/x","x",0,"+")` is `inf`, `"-"` `-inf`; `limit("abs(x)/x","x",0,"+")` `1.0`; `limit("x*ln(x)","x",0,"+")` `0.0`; `limit("sqrt(x)","x",0,"-")` "there is no limit from the left". The guide, `phs doc` and the language server's hover and completion describe it. Affects PHS programs and the bindings' calculus calls that go through PHS.

- **Witnesses: a frozen configuration also pins behaviour** (Phase 3 of the configuration freeze; plan `docs/superpowers/plans/2026-11-13-conf-freeze-phase-3-witnesses.md`, user guide `docs/conf_freeze.md` section 9). `phs conf freeze` records in the sealed `[Witness]` block a built-in battery of versioned reference calculations (`physure_core::frozen::battery`; 47 when Phase 3 landed, 63 at this release, see Changed: 12 unit conversions including affine and logarithmic units, 6 catalog constants, 11 uncertainty cases in every propagation mode with the GUM H.1 and G.4.1 examples, 8 Student-t factors, 10 chemistry cases; each checked in `physure-core/tests/battery_reference.rs` against NIST SP 811, the SI Brochure, CODATA 2022, the NIST/SEMATECH Student-t table, JCGM 100:2008 or CIAAW 2024) as IEEE-754 bit patterns and unit text (`<mean>:<u>:<unit>`, `text=`, `failed=`; `physure_core::frozen::witness`), and with `--witness FILE.phs` (repeatable) the user's own scripts, embedded and recorded as the SHA-256 of their canonical result (`physure_script::report::canonical_witness`, format `phs-witness-1`). Everything is evaluated under the file about to be written (a sealed probe of it), never under the unfrozen catalog. `phs conf verify --run [--timeout-ms N]` evaluates them again under the file and compares bit for bit (both bit patterns, decimals and the distance in ulps on a difference; exit 1 on a difference, a missing case or an error, and for a file that records no built-in witness; exit 3 and nothing evaluated under another engine); the embedded scripts run sandboxed with fixed loop and pipeline ceilings the file's `[Settings]` cannot raise, a 60 s default deadline and panic capture (no memory cap). `update` and `seal` show the witnesses as recorded against evaluated under the file they would write and refuse (exit 1, nothing written) a change of a recorded witness unless `--accept-witness-changes all|KEY[,KEY...]` names it; the history line then counts and names the changes and the hash of the old block. `update` records the battery of a file made before witnesses (no flag needed), and its hint is what `verify --run` suggests. `ops` is now a draft, a probe and a single reseal (`prepare_freeze/prepare_update/prepare_seal`, `Draft::finish`), and the compare-and-swap of `update`/`seal` also compares the SHA-256 of the bytes it read. `status` shows the recorded witness counts. Hardened after an adversarial review: **the PHS parser bounds how deep a script nests** (a flat chain of 200,000 `+` ended `verify --run` and `freeze --witness` in a stack overflow): an expression tree is at most `MAX_EXPRESSION_DEPTH` = 128 levels (every operator of a chain is a level; a longer chain is a syntax error, `expression too deeply nested: at most 128 levels`), and `MAX_NESTING_DEPTH` (64) also counts `if` chained without brackets and function bodies nested by indentation; `phs conf` deletes `phs-witness-probe-*` files more than a day old before it makes a probe; `verify --run --expect SEAL` evaluates nothing when the seal does not match; a user witness must evaluate cleanly and produce at least one result (`freeze` refuses an empty or comment-only script, exit 2; `verify --run` reports such a witness as an error even when its hash matches, and `update`/`seal` never re-record it, whatever `--accept-witness-changes` says); `--accept-witness-changes` with nothing to accept warns (stderr and JSON `warnings`, exit 0); under the policy `binary` or `build` with the engine matching, a built-in case the file lacks is an error (exit 1), while under `release` and `record` it stays informational; `verify --run` evaluates only while the file has the bytes it verified (`Inspection::read_sha256`, checked just before and just after evaluating, exit 1 otherwise).

- **`phs conf`: the commands of the configuration freeze** (Phase 2; `physure-cli/src/conf.rs`, user guide `docs/conf_freeze.md`). `status` (which configuration is in force and why, seal, verification, engine, history length, atomic-weight edition, warnings for an ignored `physure.conf`, a missing required file and environment differences), `show [SELECTOR] [--origin]` (the catalog in force as `section.key = value`, with the source of each value), `freeze --reason TEXT [--engine-policy binary|build|release|record] [--out PATH]` (default policy `build` when the build names its commit and `binary` when it does not; `build` is refused on a build without `PHYSURE_BUILD_COMMIT`, and the message names `binary`, `release` and `record`), `verify [FILE] [--expect SEAL]` (`--expect` compares with a seal recorded outside the directory: a match needs a file that verifies and an equal seal), `diff [A] [B]` (data by kind, then engine and environment; by default the file in force against what this build gives unfrozen here, so it shows both a library upgrade and drift of `physure.conf`; the environment is listed but informational, so files that differ only there are identical, and JSON adds `environment_identical`), `update --reason TEXT [--engine-policy P] [--yes]` (adopt this build's catalog and engine, keeping the overrides), `seal --reason TEXT [--yes]` (accept a hand edit of the overrides, showing their canonical text and what they contribute to the catalog; a file pinned to another engine is refused with exit 3 and the message says to run `update` first, the only way onto another engine) and `history [FILE]` (problems first, rows after a broken link marked unverified, engine-block and pin changes shown). Exit codes: 0 ok or identical, 1 a discrepancy, 2 misuse, a missing required file or a refused or declined operation, 3 only the engine differs. `--json` prints one document with `"schema": 1`, `"command"` and `"exit_code"`; fields are only ever added. `update` and `seal` ask on a terminal (refusing without one unless `--yes`; with `--json` they never ask and refuse without `--yes`, the preview inside the document) and are a compare-and-swap: a file whose length or modification time moved since it was read is not overwritten (exit 1, nothing written; residual risk 1c-14). `phs conf` is dispatched before any other argument handling (before, `phs conf freeze --reason help` printed the help and exited 0, since the flag commands matched words anywhere in the arguments) and is exempt from the pre-command check of the configuration in force, except `show`. - **Every catalog as a list of entries, and the semantic difference of two** (`physure_core::frozen::{entries, embedded_entries, diff, summary}`; Phase 1d of the configuration freeze; the `phs conf diff` and `show` commands are in the `phs conf` entry above). `entries(registry, constants, settings)` lists, sorted by kind and name, everything the catalog determines: base and derived units, aliases, what the registry answers for every name (the unit, its dimension, kind, linearity, alias and simplified form), prefixes with their exact values and names, the names of each unit, the base unit of each dimension, recipes, units that take no prefix, unit and constant metadata, categories, constants, your atomic weights, every edition's table and the selection, and the process-wide settings with the value each ends up with (a setting the file does not mention shows its compiled default, so a file that leaves it out differs from one that sets it to another value). `diff(old, new)` says what was added, removed or changed, with the old and new value; `summary` is one line for the history (`unit +2 -0 ~1; constant +0 -0 ~3`). **Completeness is tested, not assumed:** `entries` destructures `UnitRegistry` without `..`, so a field added to the registry does not compile until it is listed, and a test mutates each of the 18 fields and checks that the entries notice; a sealed copy of the shipped catalog lists exactly what `embedded_entries()` does, and the fixture's overrides differ by exactly the entries they touch. `ProcessSettings::effective` gives the value of every setting a file gives (activation uses it).
- **A frozen configuration in force replaces the catalog for every consumer, and cannot be bypassed** (`physure_core::frozen::{active, load, ops}`; Phase 1c of the configuration freeze, plan in `docs/superpowers/plans/2026-11-08-conf-freeze-phase-1c-loading.md`). **Resolution:** an explicit path set by the host (`set_explicit_conf`, the CLI's `--conf`), then `PHYSURE_CONF`, then the nearest `physure.frozen.conf` from the current directory upwards, then none; an explicit path or variable that names no file is an error and never falls back, and `PHYSURE_REQUIRE_FROZEN` must be unset, `0` or `1` (`1` without a file is an error; any other value too, so a typo cannot switch the audit off). **Sealed loading** (`load_file`): read at most 64 MiB, parse, verify, check the engine under the file's policy (the host names the file `binary` hashes with `set_engine_file`; `phs` names its own executable), then replay every source strictly into an empty registry, source 1 with the trusted reader; the library's own catalog and the working directory's `physure.conf` are not read, so an upgrade of the library cannot change a value. The replay refuses what the lenient reader drops in silence (unknown settings and sections, bad values and compatibility rows, a line outside a section, a byte-order mark, a constant that is not a quantity, a selected edition no source defines). **Fail closed:** `build_registry_from_conf`, `with_conf_registry` and `build_registry_with("")` consult `frozen::active()` first; the new `try_with_conf_registry` and `try_build_registry_from_conf` return the error, which `Parser::parse_expression`, `Quantity::new` and the chemistry functions pass on as an ordinary error, and the two infallible functions panic only as a backstop; `build_registry_with` refuses a non-empty `extra` while a frozen file is in force. `frozen::ensure_valid()` turns a problem into an error at start-up with `exit_code()` 1 (integrity), 2 (resolution) or 3 (engine): `phs` runs it before every command, `--version` included (`phs conf` is dispatched before this check and reports what is wrong with the file itself, see the `phs conf` entry), and the language server reports it with `window/showMessage` from `initialized` (tower-lsp drops a message sent from `initialize`) and as a diagnostic on every document. **One process, one configuration:** loading changes no process-wide setting; activating a frozen file puts the settings back to their compiled defaults and applies the file's `[Settings]` and `[Compatibility]` in one step, and after that a resolution that gives another file or none is `ActiveError::ResolutionChanged` until `reset_cache()` (paths are compared as text, so one file through two spellings is a refusal too); `reset_cache()` restores the compiled defaults and the embedded catalog's settings; a request for the catalog while a frozen file is loading on the same thread is `ActiveError::Reentrant` instead of a deadlock. The outcome is cached per process under the inputs of resolution, and each use checks only the stamp of the file in force: a frozen file created in a directory after the process resolved it to unfrozen is not seen until the inputs change or `reset_cache()`. **Bindings that read the embedded catalog themselves refuse** while a frozen file is in force, with an ordinary error that says what to do (`frozen::refuse_unwired`), until Phase 5 wires them: Python's `default_conf()` (a `RuntimeError`, so `import physure` raises it too; checked by `physure-python/tests/test_frozen_refused.py`, which passes) and Java's catalog; WebAssembly (`wasm32-unknown-unknown`) has no file system and is always unfrozen. PHS reads the catalog in force on every use instead of a copy kept for the whole process.
- **`freeze`, `update` and `seal` as library operations** (`physure_core::frozen::ops`; the commands are in the `phs conf` entry above). `freeze` makes a file from what is in force unfrozen (the embedded catalog and the working directory's `physure.conf`, or a comment block) and refuses when a frozen file is already in force for that directory, when the output exists, when the policy cannot be recorded by this build (the message names `--engine-policy release or record`) and when `physure.conf` would not replay strictly. `plan_update` adopts the library's catalog and the running engine into a verified file, keeping the overrides and the policy, and returns nothing when nothing differs; it refuses a modified file. `plan_seal` accepts a hand edit of the overrides block and nothing else, proved by `FrozenFile::only_the_overrides_changed` (an edit of source 1 with its marker recomputed, an appended source, the engine block, the witnesses or the history are refused). Every result is verified and replayed as loading would before it is returned, and none of them writes: `write_atomic` does (a temporary file in the same directory, flushed and renamed; without `replace` an existing file is never overwritten). `actor_from_env` and `now_unix` read the actor and the time for the CLI.

- **The identity of the engine and how a frozen configuration pins it** (`physure_core::frozen::engine`; Phase 1b of the configuration freeze, plan in `docs/superpowers/plans/2026-11-08-conf-freeze-phase-1b-engine-identity.md`). A new `physure-core/build.rs` always emits the build facts under internal names that the library reads with `env!`, so a value the build script rejected never reaches the binary. `EngineIdentity::current()` gives the version, the commit, the profile, the target, the features (the named features of `physure-core` that are enabled, sorted, without `default`, computed in the code and kept in step with `Cargo.toml` by a test), the compiler (`rustc -V`) and the build flags (opt-level, debug assertions, panic strategy, and SHA-256s of the rustflags and target features). **The commit** is the builder's claim, and git is not consulted: exactly 40 or 64 lowercase hexadecimal characters from `PHYSURE_BUILD_COMMIT` (the release workflows set it to `github.sha`), or `unknown`, decided by a pure, unit-tested rule (`build_support/commit.rs`); a value that is not a full lowercase hash gives `unknown` and a cargo warning, and an unset variable gives `unknown`. A build cannot prove that the files it compiles are those of a commit, so what pins behaviour is the `binary` policy and, later, the witnesses. A build fact that cannot be determined stops the build instead of becoming `unknown`. **Scope:** the commit names the revision the builder says it built, not the whole evaluating engine (`physure-script`, `physure-cli` and the bindings evaluate too); only `binary` pins the artefact. Every field is validated (`EngineIdentity::validate`; `rustc` and `flags` refuse every control character and U+2028/U+2029). **The four policies** (`EnginePolicy`): `binary` (the SHA-256 of the file that contains the engine), `build` (version, commit, profile, target, features, compiler and flags), `release` (the version), `record` (nothing enforced). `check` reports every field that differs, and every doubt is a difference: `unknown` equals nothing, not even another `unknown`; `binary` without a recorded hash or with an unreadable file is a mismatch, and the file is hashed only under `binary`. `freezable` refuses to record `build` for an unknown commit (it compares the commit and `unknown` equals nothing); `binary`, `release` and `record` need none. `EngineMismatch` is an `Error`, and `EngineBlock::check` checks the running engine against a block. **The `[Engine]` block** is built by `engine_pairs` (which refuses an invalid identity, a policy that cannot be recorded and `binary` without a hash) and read strictly by `read_engine`: eight required keys, an optional `binary_sha256`, and any other key is an error. `environment_pairs` records `os`, `arch`, `family`, `endian`, `pointer_width` and `cpus` for `[Environment]` (informational, outside the seal), and `sha256_of_file` hashes a file in blocks; the core has no "hash my own executable" helper, because in a binding that would pin the interpreter. **The history records the engine block:** each entry now has `engine_sha256` (the SHA-256 of the canonical `[Engine]` pairs at that entry), `policy` (the block's policy) and `pinned` (the short form of the identity the block records), all derived by the library from the block and inside the entry hash, so a change of the block, weakening the policy included, shows in the log as a different `policy`, `pinned` or `engine_sha256` between consecutive entries whatever the `reason` and `diff` say; the entry's `engine` stays the caller's text for the acting engine. `verify` reports a block that cannot be read or could not have been recorded (`build` with an unknown commit, `binary` without a hash) and a last entry whose `engine_sha256`, `policy` or `pinned` does not match the current block, and a file can be neither made nor resealed with such a block. The format of Phase 1a was not released, so the entry simply gained the fields. **Not pinned, and documented in the design:** `overflow-checks`, `lto`, `codegen-units`, the dependency versions of a consumer's lockfile, dynamically linked libraries, compiler arguments after `--` in `cargo rustc`, `RUSTC_WRAPPER`, dependency overrides, custom profiles; `release` accepts development builds that share a version number; whoever controls the build environment controls the identity (`build` protects against accidents, `binary` is the only policy whose evidence is the artefact). Loading a frozen file and the commands (`phs conf ...`) are the entries above.
- **The data layer of a frozen configuration** (`physure_core::frozen`; Phase 1a of the configuration freeze, design in `docs/superpowers/specs/2026-11-07-conf-freeze-design.md`, plan in `docs/superpowers/plans/2026-11-07-conf-freeze-phase-1a-file-model.md`). `sha256` is SHA-256 (FIPS 180-4) without a dependency, checked against the NIST vectors (including the one-million-`a` message) and against splitting the input at every point. `canonical` defines the canonical form of a source: lines trimmed, blank lines and `#`/`;` comment lines dropped, so comments, blank lines, surrounding whitespace and line endings do not change the hash while one digit does (an inline comment is content, because the conf grammar has none), and the hashes built on it: the hash of one source, the content hash over the origins and source hashes in order, and the canonical text of `key = value` lists; witness scripts are hashed byte-exact instead (`exact_sha256`: only CRLF and trailing newlines are normalised), because in PHS `;` ends a statement, indentation is significant and a string may span lines. The canonical form of a source is the one the core's conf reader defines, so a frozen source must be replayed through the core reader. `model` is the frozen file as data (header, engine, environment, witnesses, history, sources and witness scripts; fields read through getters, `[Engine]`, `[Environment]` and `[Witness]` as validated `Pairs`) with a strict renderer and parser: a malformed file is an error that names the line, values are one line without surrounding whitespace, a section opened twice, a repeated key, a number not written canonically (`+1`, `01`) and a line starting with `@@ ` (the framing marker) inside a block are refused, a bare carriage return is refused, and source text is normalised (CRLF to LF, trailing newlines removed) so that rendering and parsing round-trip exactly; the renderer re-checks everything the parser would refuse. `seal` builds a file from named `FrozenParts` with its first history entry, appends a hash-chained entry when a hand-edited or updated file is accepted again (`reseal`), and `verify` lists every problem it finds instead of stopping at the first: a modified source, a content hash that does not match the sources, a modified witness script, a history entry that was edited, deleted, reordered or renumbered, a history that does not start with a `freeze` or does not continue from one entry's content to the next, a reason that is not 1 to 500 characters, a history tip that does not record the current content, a broken structure (source 1 must be `embedded`, source 2 `overrides`, origins and witness names unique, a `user.<name>` key in `[Witness]` for every witness script and none without one, `created` equal to the time of the first entry), and a seal that does not match. The seal is the SHA-256 of labelled lines holding the format, the creation time, the content hash and the hashes of `[Engine]`, `[Witness]`, the witness scripts (names and byte-exact texts, in order) and the last history entry, so no pair or script can move between parts unnoticed; a new file and a reseal are refused if the result would not verify. Two things are outside the seal: the `[Environment]` block, and formatting that carries no data (comment and blank lines, whitespace, line endings and key order in the header, and in a source what its canonical form drops). `time` writes and validates UTC times as RFC 3339 text (real calendar dates from 1970 on, no leap second; nothing is written past 9999-12-31T23:59:59Z), so the model reads no clock. The module reads no clock, environment or file, and does not touch the unit registry yet; `physure-core/tests/frozen_file.rs` exercises it through the public API only. The commands (`phs conf ...`) and the loading of a frozen file are the entries above.
- **Chemistry in the Rust core** (`physure_core::chemistry`; plan 1 of the chemistry port, `docs/superpowers/plans/2026-11-07-chemistry-core.md`). `parse_formula` reads `Ca(NO3)2`, `H₂O` and hydrates (`CuSO4·5H2O`); `Species` carries a formula and its molar mass (the atoms of one element add linearly, `ν_E·u(Ar(E))`, and the elements combine in quadrature); `mass_to_moles` and `moles_to_mass` put the uncertainty of the molar mass into the result; `Reaction::from_string` balances an equation with exact, checked rational arithmetic, reads the separators `->`, `=`, `→`, `<=>` and `⇌`, and refuses a reaction that does not have exactly one solution; `arrhenius`, `clausius_clapeyron` and `gibbs_free_energy` work on `Quantity`, with the gas constant read from the catalog. The atomic weights are not a table in Rust: they are tables in `physure.conf` (in g/mol), each a section `[AtomicWeights:<edition>]` named by its **edition**, and two are shipped. `standard-2024` is the full CIAAW Standard Atomic Weights 2024, that is the table of the 2021 report with the 2024 revisions of Gd, Lu and Zr, as CIAAW prints them, with the intervals kept as intervals, and it is the default. `abridged-2024` is the CIAAW abridged table, available as an option, and not the default because its "±" is, in the words of the report, "A conservative +/- value ... is given as a simplified measure of the reliability of the abridged values" and, for the weights quoted to more than five significant digits, only the place value of the last rounded digit, and its single value for the interval elements "does not correspond necessarily to the midpoints of the intervals (in case of Li, Mg, S, Ar and Pb)" (Prohaska et al., Pure Appl. Chem. 94, 573-600 (2022), section 7), so using it as a half-width would put a rounding convention where the Commission's evaluation should be. A line is `symbol = weight, U` (CIAAW's `x(n)`: U is the uncertainty in the last digits shown), `symbol = [a, b]` (an interval, for the 14 elements for which CIAAW prints one: H, Li, B, C, N, O, Mg, Si, S, Cl, Ar, Br, Tl, Pb) or `symbol = weight, u, standard`. The sections are generated by `scripts/gen_atomic_weights_conf.py` from `tests/golden/ciaaw_standard_atomic_weights_2024.tsv` and `tests/golden/ciaaw_abridged_atomic_weights_2024.tsv` (the tables as printed), `physure-core/tests/atomic_weights_ciaaw.rs` holds each to its file, and `docs/atomic_weights.md` documents the data, the model, the checks and the limits. **Which table is read** is chosen in the `[Chemistry]` section of any conf or unit system with `atomic_weights = <edition or alias>`; the aliases are `standard` (the newest standard edition this release ships: `standard-2024`, what the shipped file selects) and `abridged` (`abridged-2024`). **An alias moves when a release ships a newer edition of its kind, and the CHANGELOG of that release says so; a pinned edition name never changes meaning.** **Your definitions** are the section `[AtomicWeights]` (empty in the shipped file): they override or add elements on top of whichever table is selected, in any order, and over nothing else (the lookup is your definitions, then the selected table, with no fallback to any other table), so a conf of your own or a unit system can override an element or add an isotope (`D = 2.01410177812, 0.00000000012, standard` makes `D2O` parse under any edition). **A complete table of your own** is a section `[AtomicWeights:acme-2026-03]` selected with `atomic_weights = acme-2026-03`: nothing is taken from the shipped tables for it, an element it lacks is an error that names the element and the edition, and a selected edition that no text defines makes every use fail with an error naming it. Edition names are lower-case ASCII letters, digits and `-`, `_`, `.`, starting with a letter, at most 64 characters (a table cannot be called `standard` or `abridged`, which are aliases). **How a text is read:** as the definitions of a unit system (`extend_registry`, `UnitRegistry.extend_conf`) every one of these sections is read strictly like the rest of the conf (a bad row, a bad edition name or an unknown `[Chemistry]` key refuses the whole text), whereas the `physure.conf` of the working directory is read leniently, as it always was, so a bad line there is skipped and the rest applies, but every problem found in it is now reported on stderr as `physure.conf: <problem>; the line is ignored` (once per process for each distinct message), so a bad `[AtomicWeights]` or `[Chemistry]` line no longer silently falls back to the defaults. A text of a user cannot edit a shipped edition (`[AtomicWeights:standard-2024]` and `[AtomicWeights:abridged-2024]` are a problem, only the embedded catalog defines them) and the names that start with `standard-` or `abridged-` are reserved for the editions of this library, so that a table of a user called `standard-2026` is never silently merged with a shipped one on the day a release adds it. A header that is a near miss of a section (`[chemistry]`, `[Chemistry ]`, `[Atomicweights]`) is a problem naming the right spelling instead of an unknown section ignored without a word; a section name that is not close to any known one is still ignored. A later definition of a symbol replaces the earlier one. An interval whose standard uncertainty would underflow to 0 is refused, and its midpoint is computed as `a/2 + b/2`, so that `[1e308, 1.7e308]` is not turned into an infinite weight. **Reproducibility in audited use:** a released edition is frozen (a fingerprint test, FNV-1a 64 over the exact bits of every weight and uncertainty, fails if either shipped table changes by one bit; a new CIAAW release becomes a new edition, never an edit), so a validated calculation that pins `atomic_weights = standard-2024` gets the same atomic weights from every later release of the library, and `chemistry::atomic_weight_edition()` / `UnitRegistry::atomic_weight_edition()` return the table that produced a result (`standard-2024`, `abridged-2024 + 1 definitions (fnv1a:e03dd5b5b2476b01)`, where the hash identifies the definitions, `nope-1 (undefined)` for a selected edition that no section defines, `acme-2026-03`) for a report to quote; what is guaranteed is that the numbers of a shipped edition are the same in every release (a fingerprint test) and that no text of a user can edit one or use a name reserved for one; this covers the atomic weights only, the other data of `physure.conf` are versioned with the library release, and a modified build of the library is not detected at run time. The chemistry module reads the weights from the catalog in scope, and `parse_formula`, `Species::new` and `Reaction::from_string` refuse a symbol that catalog lacks, naming the element and the edition. Elements with no standard atomic weight (Tc, Pm, Po-Ac, Np-Og) carry the mass number of a long-lived isotope and an uncertainty of 0, a convention of the file and not a CIAAW value. The uncertainty CIAAW prints is the half-width of the interval in which the atomic weight of normal materials is expected to lie, a decisional uncertainty that "differs essentially" from the GUM expanded uncertainty, and no coverage probability is attached to it (Possolo et al., Pure Appl. Chem. 90, 395-424 (2018)). It is read as a uniform distribution, as IUPAC recommends (Prohaska et al. 2022; van der Veen et al., "Interpretation and use of standard atomic weights", doi:10.1515/pac-2017-1002, whose quotations were checked against the peer-review manuscript PAC-REC-16-04-01): `symbol = weight, U` is stored as the standard uncertainty `U/√3`, an interval `[a, b]` as its midpoint `(a+b)/2` with standard uncertainty `(b-a)/√12`, and a third field `, standard` marks a number that already is a standard uncertainty and is stored as given. The uncertainty of a molar mass combines per element, `u² = Σ ν_E² u²(Ar(E))`: the atoms of one element add linearly (`ν_E·u(Ar(E))`), so repeated atoms of one element are one quantity, and the elements combine in quadrature. Molar masses and their uncertainties therefore differ from the Python package, and from the CIAAW abridged table, as these examples show (g/mol, standard uncertainties): H 1.007975 ± 0.0000779 (Python 1.008 ± 0.0002; abridged table 1.008 ± 0.000115), Na 22.98976928 ± 0.0000000115 (Python 22.98976928 ± 0.00000002; abridged 22.990 ± 0.000577), Ar 39.8775 ± 0.0494 (Python 39.948 ± 0.001; abridged 39.95 ± 0.0924), Pb 207.04 ± 0.520 (Python 207.2 ± 0.1; abridged 207.2 ± 0.635); H2O is 18.01535 ± 0.000264 and CO2 44.0094 ± 0.000718, worked out in `docs/atomic_weights.md`; `Species::molar_mass_parts` returns a `Result` because an element can be missing from the catalog in scope. `tests/golden/chemistry_molar_mass.tsv` is computed by `scripts/gen_chemistry_golden.py` from the conf's weights (the selected table and the definitions, read with its own parser of the three forms, not the core's) and the Python formula parser, and `chemistry_reactions.tsv` is still what the Python implementation answered; the core is held to both. Python and PHS do not use the core module yet. **Where the core deliberately differs from the Python package (the core is right):** (1) a hydrate dot is accepted, Python refused it; (2) a count of zero (`H0`), empty parentheses (`H()`) and non-ASCII decimal digits are refused, Python accepted the first two; (3) `arrhenius` and `clausius_clapeyron` keep the uncertainty of every input, Python dropped all but the prefactor's / the pressure's; (4) an overflow in the balancing is an error; (5) the molar mass of an element is one stable uncertainty source (for the same weight and uncertainty: another edition or a definition of yours is an independent source), so the same molar mass cancels on a round trip (`moles_to_mass(mass_to_moles(m))` keeps the uncertainty of `m`) and species that share an element are correlated through it, where Python rebuilt an independent quantity each time; a molar mass is always Gaussian, whatever the global propagation mode is; (6) a mass of exactly 0 with an uncertainty keeps its uncertainty through `mass_to_moles`, Python gave 0 ± 0; (7) the Python package used the half-width CIAAW prints as if it were a standard uncertainty, which is √3 too large; the core divides it by √3; (8) for the 14 elements CIAAW gives as an interval the Python package used one conventional value (Ar 39.948, Pb 207.2), the core keeps the interval, with its midpoint and `(b-a)/√12`.
- **Java quantities keep the sources of their uncertainty, and have degrees of freedom** (the Java piece of the work in `docs/superpowers/specs/2026-11-02-java-provenance-design.md`). A Java `Quantity` was a bare `(value, uncertainty, unit)` triple that every native call turned into a new core quantity, so a result kept no record of the measurements it came from. It now carries them as `(source id, contribution)` pairs: a result of the core arrives with the sources the core reports (folded with the scale of an anonymous compound unit like the numbers shown, and kept through a conversion), and a quantity constructed in Java mints its one id from the core's counter the first time it is used, remembered on the object so that racing threads agree and nothing is minted at construction. `equals` and `hashCode` stay value-based. New API, the same as the other bindings: `withDof(nu)`, `Quantity.fromSamples(double[], unit)` (Type A), `effectiveDof()`, `coverageFactor(p)` and `expanded(p)`, which returns an `ExpandedUncertainty` whose text is `(10.0 ± 1.1) V (k=2.12, p=95 %)`. `UncertaintyDofGoldenTest` holds Java to `tests/golden/uncertainty_dof.tsv` (the file the core and WebAssembly are held to), and the Java generator writes the clause as `.withDof(9.0)` instead of refusing it. `sin`, `cos`, `tan` and `abs` are the core's now (they were computed in Java, `|cos x| u` by hand, which dropped the sources). `PhyFunction.call(Quantity...)` and `PhyEquation.call(...)` bind quantity arguments by value, with their sources, for the call only; a `String` argument is still PHS source, and a non-finite value is still refused. `QuantityVector.dot` lost its `a == b` special case: sources make `x * x` the square of `x` whatever objects hold it.
- **The sources of a quantity as plain data, and a program run with values bound by name.** `Quantity::sources()` and `display_sources()` read the lineage as `(source id, contribution)` pairs (the second in the unit `display_parts` reports), `Quantity::from_sources(mean, sources, unit)` rebuilds a Gaussian quantity from them, reserving the ids, and `uncertainty::new_source_id()` mints an id from the one counter; only the Gaussian model has sources. `PhsInterpreter::run_program_with(program, bindings)` evaluates in a copy of the environment with the bindings added, so a binding can call a function with the quantities it holds without making new measurements of them, and nothing stays in the interpreter. WebAssembly's `PhyFunction.call`, which still writes its arguments into the source, can use it later.
- **Effective degrees of freedom, coverage factor and expanded uncertainty in the core** (Welch–Satterthwaite, JCGM 100:2008 G.4; stage D1 of the work in `docs/superpowers/specs/2026-11-01-welch-satterthwaite-design.md`). `Quantity::with_dof(nu)` declares the degrees of freedom of a measurement, `Quantity::from_samples(values, unit)` is a Type A evaluation (mean, `s/sqrt(n)`, `n - 1` degrees of freedom), `effective_dof()` combines the degrees of freedom of the independent sources a value came from by `nu_eff = u_c^4 / sum((c_i u_i)^4 / nu_i)` (the lineage terms are exactly those contributions, so a shared source is counted once), `coverage_factor(p)` is the Student-t factor at `nu_eff` truncated to an integer as the Guide recommends (the normal factor when it is infinite) and `expanded(p)` returns an `Expanded` with `U`, `k`, `p` and `nu_eff`: a result of its own, not a `±`. The degrees of freedom of a source are kept once, in a table by source id; a source that declares none has infinitely many. Only the Gaussian model has them: Moments, Monte Carlo and unscented quantities raise. `math::stats::student_t_two_sided` is new (no dependency). Checked against the Guide's own example H.1 (`u_c` 31.664 nm, `nu_eff` 16.752 where the Guide prints 16.7, `k` 2.12 and 2.92, `U` 0.07 and 0.09 µm) and against 160 `scipy.stats` values to 1e-9. PHS, Python, WebAssembly and Java have it too (see their entries).

The binding wraps the core's `Quantity`, so the sources of a result survive every operation and a conversion, and the degrees of freedom with them. `tests/golden/uncertainty_dof.tsv` (11 budgets, among them the Guide's end gauge at 95 % and 99 %, computed independently with scipy by `scripts/gen_uncertainty_dof_golden.py`) freezes what a sum of measurements must report; the core and the WASM binding (under Node, with `wasm-pack test`) are held to it. - **Degrees of freedom in Python** (stage D3). `Q_(10.003, "V", uncertainty=0.002, dof=9)` declares them (or `q.with_dof(9)` on a measurement), `q.dof` reads the effective ones, `q.coverage_factor(p=0.95)` is the Student-t factor at their integer part and `q.expanded(p=0.95)` returns an `ExpandedUncertainty` (value, unit, `u_c`, `U`, `k`, `p`, `dof`) whose text is `(50000840 ± 70) nm (k=2.12, p=95 %)`, rounded as the Guide presents a result. `Q_.from_samples(values, unit)` is a Type A evaluation: the mean, `s/sqrt(n)` and `n - 1` degrees of freedom, from numbers or from exact quantities of one dimension. All of it is the Rust core's (new `Lineage.effective_dof`, `declare_dof`, `physure._core.coverage_factor`, `type_a_evaluation` and `gum_round`): no runtime dependency and no second implementation. Arrays, `python_lineage()` and the sampling modes use other uncertainty models, and raise `NotImplementedError` instead of answering. - **Degrees of freedom in PHS** (stage D2). A literal declares the degrees of freedom of its uncertainty with a keyword after the value: `10.003 +/- 0.002 dof 9 V` (`ν 9` is the same, `dof inf` is infinite), before or after the unit. It is a keyword and not a parenthesis because a parenthesis after `+/-` already means the asymmetric pair; an asymmetric pair, a `sigma` bound or a non-positive number cannot carry it, and `dof -2` is refused as what it is and not read as the unit `dof` minus 2. New builtins: `dof(x)` (effective degrees of freedom, `inf` for none), `coverage_factor(x, p)`, `expanded(x, p)` (`U` as a quantity in the unit of `x`) and `from_samples([..] unit)` (Type A). The Guide's end-gauge calibration (Annex H.1) is a program (`docs/tutorials/dof_example.phs`, run by a test): `nu_eff` 16.752, `k` 2.12, `U` 67.1 nm at 95 %. The static checker types `dof` and `coverage_factor` as plain numbers and `expanded` in the unit of its argument, the language server completes and explains them, and the code generators carry the clause (Python `Q_(…, dof=9.0)`, Rust `.with_dof(9.0)`, JavaScript and TypeScript `.withDof(9)`, Java `.withDof(9.0)`): a quantity with nine degrees of freedom never comes out of a generator as one with infinitely many.
- **A training-step benchmark for `Quantity` under `torch.compile`** (`benchmarks/bench_compile_training_step.py`). - **`phs mcp`: a Model Context Protocol server for agents** (N5c). JSON-RPC 2.0 over stdio, written on `serde_json` with no SDK dependency, speaking protocol versions 2024-11-05, 2025-03-26 and 2025-06-18. Four read-only tools: `evaluate` and `check` run the program in a child `phs` process (`phs eval -` / `phs check -`) that is killed if it does not finish, so a crash or a hang cannot take the server down; `convert` and `describe_unit` call the core in-process (`physure_script::report::convert` is new, and refuses a unit expression longer than 200 bytes). The resource `phs://language` is the `phs doc` reference. 14 unit tests, and 3 session tests that drive the real binary. Design: `2026-10-30-agent-validation-surface-design.md`.
- **`phs eval`, `phs unit` and `phs check -`: structured answers for agents** (N5b). `phs eval <file|->` runs a program in the N5a sandbox and prints one JSON document: for every statement with a value its `kind`, `text`, and for a quantity `value`, `uncertainty`, `unit` and `dimension`; and `diagnostics` that merge the static checker, syntax errors, runtime errors, `limit` and `forbidden` refusals. Exit code 0 / 1 / 2; `--seed` (default: the `monte_carlo_seed` in force, 0 unless the configuration says otherwise, see the seed entry) and `--timeout-ms` (default 5000); a watchdog ends the process with a `limit` report if the deadline is not honoured. `phs unit <symbol>` prints what the core knows of a unit. `physure_script::report::{evaluate, describe_unit}` carry the same for embedders. Design: `2026-10-30-agent-validation-surface-design.md`.
- **A sandboxed PHS interpreter for text from outside** (N5a of the agent validation surface). `PhsInterpreter::sandboxed(Limits)` reads no file (`import` finds nothing), loads no native plugin, refuses the mesh export that writes a file (`forbidden:`), evaluates `for` expressions and `parallel_map` on one thread, stops at a deadline (`time limit reached`), and stops when the native stack in use passes a budget (`stack limit`), checked at every expression so deep nesting inside recursion is covered. `Limits` carries the numbers; `run_sandboxed(limits, f)` runs `f` on a thread sized for the budget. `physure_core::uncertainty::with_seed(seed, f)` makes the Monte Carlo draws on the thread reproducible. Design: `2026-10-30-agent-validation-surface-design.md`; `phs eval` and `phs mcp` build on it in the next stages.
- **Static dimensional checking of PHS.** `physure_script::check` reads a program and reports, without running it, where a sum, a difference, a comparison or a conversion mixes incompatible dimensions (`1 m + 1 s`, `5 m => s`, `sin(1 m)`), where a unit is not in the catalog (an error), where a word that is neither a variable nor a unit meets a quantity, where an absolute temperature is added to another or scaled by a plain number, and where an exponent is not a dimensionless constant. It follows quantities through assignments, products, powers and the builtins with the interpreter's own rules, takes units from the core's `UnitRegistry::facts` so the checker and the interpreter cannot disagree about what a unit is, checks a parameter with a unit (`fn f(m: kg)`) at every call, and for a parameter without one checks the body for the dimensions of each call, reporting a mismatch inside it at its own line with the call that caused it. It reports an error only when the interpreter is certain to refuse the operation; a value it cannot type silences what depends on it. `max` or `min` of different dimensions, which the interpreter accepts and compares by base-unit magnitude, is a warning. A diagnostic points at the line of its statement (the AST has no columns). `phs check <file>... [--json]` prints the findings (exit code 1 for an error, 2 for a file that cannot be read or parsed), and the language server publishes them with the syntax diagnostics. Tests, and a corpus test that runs the checker on every program in the crate's own tests: no error on any program the interpreter runs. Design: `2026-10-30-static-dimension-checking-design.md`.
- **The micro sign is the prefix `u`.** `µm`, `µs`, `µF` and `µg` parse, with the micro sign a keyboard types (U+00B5) and with the Greek letter (U+03BC); only `um` did, and the core's own printer wrote `µ`. The text a quantity was written with is the text it keeps (`µm` prints as `µm`). The sign is a prefix only: `µ` alone is not a unit.
- **The Java binding is tested on every platform its jar ships a library for.** `bindings.yml` builds the native library for Linux x64, Linux arm64, macOS arm64, macOS x64 (built for Intel on the Apple Silicon runner and loaded by an x64 JDK under Rosetta) and Windows x64, runs the suite on Java 21 on each (on every LTS, 8 to 25, on Linux x64), and then packages the jar the way the release does, with the library staged where `java-release.yml` puts it, and runs it with no library path: the jar has to find and load its own library. `NativeLibraryLocatorTest` checks the path the loader reads for what each JVM reports, including the layout `java-release.yml` stages (a platform added to the workflow and not to the loader fails it), and `JarLoaderSmokeTest` loads the library through the jar's own fallback in a child JVM on whichever platform the tests run, with a control that fails when the library is not there.
- **The Java and WASM bindings are held to what the core says about a unit.** `tests/golden/unit_dimension_scale.tsv` freezes the base-unit exponents and the scale that the core gives for 44 unit expressions (the catalog's representative ones plus fractional powers, spelled-out prefixes and compound units). `physure-core/tests/binding_contract_golden.rs` checks the core against it (`PHYSURE_BLESS_GOLDEN=1` rewrites it for a change made on purpose), `physure-java/src/test` (JUnit 5) and `physure-wasm/tests/binding_contract.rs` check what each binding returns after its own marshalling, scales to the last bit. Before this, `physure-java` had no test at all and no workflow ran the WASM tests. The new `bindings.yml` workflow runs both when `physure-core`, `physure-script`, a binding or the golden file changes, and `java-release.yml` and `wasm-release.yml` run it before they publish. The Java suite runs on every LTS release, Java 8, 11, 17, 21 and 25, against one native library built once. `physure-java` has a `junit-jupiter` test dependency and a surefire plugin, which touch no consumer of the jar; `mvn test` needs the native library (`cargo build -p physure-java`) first, and a `native-access` profile passes `--enable-native-access=ALL-UNNAMED` on Java 24 and later, where loading a JNI library without it is a warning today and will be blocked.
- **`UnitRegistry.getUnitPowers(expr)` in the Java binding** returns the base-unit exponents as `Double`s (numerator over denominator), as the WASM binding already did: `s^0.5` is `{s=0.5}`.

### Changed
- **Monte Carlo results are reproducible by default, which changes reproducibility expectations in both directions** (commits `d1a5a7a`, `67af7de`, `320f1a7`, `785defc`). Runs that were random are now deterministic: under `propagation_mode = monte_carlo`, three runs of `phs mc.phs` with `x = 10 +/- 1 m` printed x = 10.0335345834355, 10.0427004576721 and 10.0354394418721; now every run gives the stream of seed 0 (the bits of `phs eval --seed 0`), the same in the REPL, the TUI, the web view, `phs serve`, the language server, WebAssembly, Java and Python. **Write `monte_carlo_seed = random` for the old behaviour.** `phs eval` used seed 0 whatever the configuration said; it now uses the seed in force (5 under a frozen seed-5 file), and a user witness evaluated under a non-zero file seed records another hash than before (files with seed 0, every file made before this release, are unchanged). A `for` loop or `parallel_map` in `monte_carlo` mode now runs on the thread of its unit: its values depended on the worker count (RAYON_NUM_THREADS=1 gave t = 10.0008141166994 ± 0.00602741380771973 m, 8 threads 9.99990039281738 and 10.000397593332 m on two runs) and are now the same at any thread count (9.99988684814229 ± 0.00760951786082866 m); loops in every other mode stay parallel with every bit kept (timings within noise; the Monte Carlo loop program, min/median of 15 runs, 596/608 → 526/540 ms). `phs serve` loads its modules in name order inside one unit and every request starts at the position after loading: two modules no longer hold the same samples, and repeated requests of the same program give the same samples (they are not independent replicates).
- **A frozen file made by a development build reports a changed library catalog and new built-in witnesses** (commits `429cf6a` to `1d0ca1f`). Frozen files are new in this release, so nobody on 0.3.x has one; this concerns only a file made with a build between the releases. The shipped `physure.conf` gains nine `[Settings]` keys (`monte_carlo_samples`, `max_while_iterations`, `asymmetric_shape`, `default_dof`, `monte_carlo_seed`, the four display keys), the thermochemistry edition and its selector, and loses the six ignored settings, so `phs conf diff` shows those entries and `phs conf update` adopts them. The built-in battery grows from 47 to 63 cases (`unc.asymmetric_sum`, twelve `display.*`, three `chem.*`); `phs conf verify --run` lists them as NEW rows until `phs conf update` records them (at `969d3ec`, `verify --run` evaluated and matched the 60 cases of then under a file with `display_significant_digits = 6`). A key the file does not set takes its compiled default, which reproduces the previous behaviour except for the seed (0, where the draws used to be unseeded).
- **The accepted-but-ignored settings leave the shipped catalog and warn where a user sets one** (owner question Q8; commit `df63945`). `default_output`, `auto_simplify`, `default_system`, `readable_representation`, `verbose` and `mkml_recursion_limit` are read by nothing (verified by search in every crate and in Python). They are no longer set in the shipped `physure.conf`; every reader still accepts them (`setting_ignored` entries). `phs conf status` and `verify` (text, and JSON `ignored_settings`) warn once per key set by a source of the frozen file other than its embedded catalog, and, unfrozen, for the working directory's `physure.conf`: `overrides: [Settings] verbose = true is accepted and ignored: no part of physure reads it, so it changes nothing`. Python's `default_system.settings` no longer holds the six keys.
- **Currency units are shipped catalog text, read fail-closed** (audit A2, M4; commit `44de88a`). `enable_currency()` reads `physure/infrastructure/config/systems/currency.conf` (`[Dimensions] money = $, noprefix` and the USD, EUR and MXN units) from the installed package and extends the system through the core. The rates and every result are bit-identical (`100 MXN => USD` is still `5.8999999999999995`); the rates are placeholders as of 2026-11-15, and the file says so. A missing packaged file raises `FileNotFoundError`; a `currency.conf` in the working directory is never read; a second call no longer logs "Dimension '$' is being redefined". Not frozen until Phase 5.
- **What may break on upgrading** (summarised under "Upgrading from 0.3.x" above, each detailed in its own bullet): the PHS rules (precedence of `=>` and comparisons, a zero needs a unit, a condition is a Bool, relative `==` and `≈`, reserved names, `;` between statements on one line, limits, `=> unit` and uncertainty errors; see "Migrating a PHS program to these rules"); Monte Carlo draws are seeded by default (above); a `.phs` module now runs whole, in its own scope, when imported (Fixed), so a module that binds a reserved name (`pi = 3`, a catalog constant) makes every import from it an error, whichever name is imported (`use fine from "pi_mod"` gave `fine = 1.0` and is now "`pi` is the constant π and cannot be bound as a variable"), and a cyclic import is refused; Python's `create_system("absent.conf")` raises `FileNotFoundError` instead of quietly building a base-catalog system (Fixed); the Java binding refuses or answers differently in the cases listed under Fixed; and a frozen file made by a development build reports a changed catalog (above).
- **Operator precedence: arithmetic binds tighter than conversion and comparison** (audit B26; commits `6eb3d23`, `5f0cda7`, docs `923bfc4`). Tightest first: `^` and unary minus; `*`, `/` and implicit multiplication; `+`, `-`; `=>` (conversion, left-associative, its target a unit); comparison (one per expression); `..` (one per expression); format spec; `not`; `and`; `or`; ternary; `where`. Before, comparison bound tighter than `+`/`-`, and `+ -` and `=>` shared one level. Measured before → after (`phs eval -`): `0.1 + 0.2 == 0.3`, `0.1 m + 0.2 m == 0.3 m`, `a + b > c`, `a - b == c - d`, `1 + 1 == 2 and 2 < 3` were "Invalid operand types for binary operation" and are `True`; `2 m + 3 m => km == 0.005 km`, `x => km < 5 km`, `1 m => km == 0.001 km` were parse errors and are `True`. **Breaking, with an error instead of a new meaning:** a `+` or `-` after `=> unit` (`x => km - 5 m` was `-0.004 km`, `x => km + 5 m` `0.006 km`, also in an assignment, a one-line function, after a vector) is the parse error "after `=> km`, a `-` needs parentheses: write `(x => km) - 5 m` (the target of `=>` is a unit, and arithmetic binds tighter than the conversion)"; a chain of comparisons (`1 < 2 < 3` was "cannot compare Bool and Quantity", `True == False == False` and `3 > 2 == True` were `True`) is the parse error "a comparison chain has no meaning here: write `a < b and b < c`". `+/-` after a unit is still an uncertainty. Unchanged: `-2 ^ 2` is `-4.0`, `2 ^ 3 ^ 2` is a parse error, `1 m + 2 m => cm` is `300.0 cm`, `0 m .. 10 m => km`, `not 1 < 2`, `True or False and False`. The symbolic strings of `deriv`, `integral`, `limit`, `solve` and the other symbolic builtins follow the same order (see Fixed for the sign bug this removed); a sign on an exponent (`e^-x`, `2^-x`) and `**` stay accepted there. The extra grammar tier costs one level of bracket nesting on a 1 MiB debug stack (parentheses 25 → 24, brackets 28 → 26, `abs(` 27 → 26); `MAX_NESTING_DEPTH` (64) and `MAX_EXPRESSION_DEPTH` (128) are unchanged. Repository corpus (33,385 unique snippets): no PHS snippet changed meaning; the only repository text that wrote `=> unit` followed by `-` was a parser test, now `(1 m => km) -2`. Affects PHS programs everywhere PHS runs.
- **Two statements on one line need a `;`** (commit `becbd1c`). A statement used to begin wherever the one before it could not go on, so a line silently became two statements: `1 m => km 2` was `2.0` (after `0.001 km`), `x = 2 m => km 3; x` left a stray `3`, `5 m => km "t"` was `t`, `a not b` was `a` then `not b`. Each is now the parse error "expected a newline or `;` before `2`: the statement before it ends there, and two statements on one line need a `;` between them", at the second statement. `;`-separated statements, newlines, trailing comments, `where`, the ternary, `if`, decorators and indented blocks are unchanged. Repository corpus: the 21 snippets that stopped parsing are English prose, not PHS. Affects PHS programs.
- **A zero needs a unit, and a level or an angle is not a plain number** (audit T1; commit `9bed746`). This replaces the dimensionless-zero exception of the B22 bullet below. `Quantity::comparable_magnitudes` (PHS `==`, `!=`, `<`, `<=`, `>`, `>=`, `≈`, `approx`, `assert(a, b)`, the WASM and Java `phs_assert`) refuses: a plain number against a quantity with a dimension, zero included ("cannot compare 1.0 m with the plain number 0: a zero needs a unit, write `x > 0 m` (for a temperature point or a level, each scale's zero is a different value: 0 degC is 273.15 K, 0 dB is a ratio of 1)"; a non-zero number: "... a number compared with a quantity needs a unit, write `x > 5 m`"); an angle against a plain number in both angle modes (the mode only lets a conversion read rad and sr as 1); a level (dB, pH) against a dimensionless value that is not a level ("cannot compare 20.0 dB with the plain number 100: write the level with its unit (`x > 20 dB`) or compare the ratio explicitly (`(x => unity) > 100`)"). Before → after: `1 m > 0`, `0 < 1 m`, `1 m >= 0`, `0 m == 0` `True`, `1 m == 0` `False` → errors; `20 dB == 100`, `5 dB > 0`, `-5 dB > 0` `True`, `0 dB == 0`, `-5 dB < 0` `False` → errors; `1 rad > 0`, `30 deg > 0`, `1 sr > 0` `True` → errors; `assert(20 dB, 100)` passed and `approx(20 dB, 100)` was `True` → errors; `1 m > 5` and `20 degC > 0` were "Unit mismatch: expected 'm', got ''" → the messages above. The static checker already refused the first group, so `phs check` and the interpreter now agree (75 snippets × both angle modes in `tests/zero_and_conditions.rs`). Unchanged and `True`: `1 m >= 0 m`, `20 degC > 0 degC`, `20 dB == 20 dB`, `20 dB > 10 dB`, `(20 dB => unity) == 100`, `30 deg > 0 deg`, `50 % == 0.5`, `x = 1 %; x > 0`, `1 unity > 0`: a dimensionless ratio in any unit compares with plain numbers. Affects PHS programs everywhere PHS runs and the bindings' `phs_assert`.
- **A condition is a Bool; text and numbers are not conditions** (audit T6; commits `ee9f7f1`, `867c753`, docs `a9d310c`). This replaces the truthiness of the B22 bullet below. `if ... then ... else`, `? :` and `ternary(...)`, `while`, `if ... then return`, `@requires`, `@ensures`, a conditional breakpoint, `and`, `or`, `not` and one-argument `assert` take only `True` or `False`, with one table of messages, "<context> needs a Bool (True or False), got ...": a Number ("a number is not a condition; compare it, e.g. `x != 0`"), a Quantity ("... e.g. `x != 0 m`", in its own unit), the String `"true"`/`"false"` ("the Bool literals are True and False"), other text ("compare it, e.g. `s == "on"`"), None, and a Vector, Range, Function, Matrix, Plot, Sigma, sigma bound or Equation by name; a condition that is a name with no value says "`true` has no value; the Bool literals are True and False". Before (`00cc92a`): `if "true"`, `if "1"` chose `then` and `if "false"`, `if ""` chose `else`; `if true`/`if false` read the text; `if 1`, `if -5`, `if 1e-16`, `if 1 m` chose `then`, `if 0`, `if 0 m` `else`; a vector, a range, a function or a sigma bound was silently false; `1 ? 2 : 3` was `2.0`; `x = 1; while x { x = x - 1 }` stopped at `0`; `while true { ... }` and `while "1" { ... }` ran to the loop guard ("did not converge after 10000 iterations"). Every one of these is now the error of the table; `True`, `False`, comparisons and `and`/`or`/`not` of Bools are unchanged. `phs check` reports the same error where it knows the type (see Added). Affects PHS programs everywhere PHS runs, including the Java and WASM runaway-loop tests, which now write `while True`.
- **Transpiled comparisons call the core's comparison** (commit `cb975c4`). Every `phs transpile` target compares through `Quantity::phs_compare` (two operands the generator can see are Bools keep the target's own operator). Before → after, for `x = 2 m; ok = x > 0 m`: Rust compared `canonical_magnitude()` with no dimension check (`1 m > 1 s` compiled and answered) → `phs_compare(..).unwrap_or_else(|e| panic!("{e}"))`, so a refused pair stops the program; Python used Python's `Quantity` comparison (`==` answered `False` for different dimensions) → `phs_compare(x, ">", Q_(0.0, "m"))`; Java used `greaterThan` and `.equals` (exact: `1 km == 1000 m` was false) → `x.phsCompare(..., ">")`; JavaScript and TypeScript compared `getValue()`, which the WASM `Quantity` does not have → `x.phsCompare(...)`. A program the interpreter refuses (`x > 0`, `20 dB == 100`) is not transpiled at all, in any target. Checked by `transpile_parity_tests.rs` (`comparison_across_units`) run through cargo, uv, javac + java and `node --check`. Affects generated code. Still open: the JavaScript target emits `Quantity.of` and, for a non-literal exponent, `getValue()`, neither of which the WASM `Quantity` has.
- **Binding `pi`, `π` or a constant of the catalog is an error** (commit `f53243c`). An assignment, a function name or parameter, a `for` variable, a `where` binding, an import of a named symbol or a module that defines one, a value given by the host (`run_program_with`), an argument name of an equation call, the variable of `integral`/`limit` or a `where` binding inside their text: "`pi` is the constant π and cannot be bound as a variable; choose another name", "`molar_gas_constant` is a constant of the catalog in force (8.31446261815324 J*mol^-1*K^-1) and cannot be bound as a variable; choose another name". Checked once per statement before it runs, from the catalog in force, so a conf that adds a `[Constants]` entry makes binding that name an error under that conf only. Before: `pi = 3` was `3.0`, `f(pi) = pi * 2; f(3)` `6.0`, `for pi in 0..3 { pi }` `[0.0, 1.0, 2.0]`, `x = pi where pi = 3` `3.0`, `molar_gas_constant = 3` `3.0`. Affects PHS programs that used one of these names as a variable.
- **A two-sided `limit` needs both sides, and calc builtins refuse keyword arguments they do not take** (commits `924767f`, `10d8e72`). The previous rule that "a side undefined at every sample counts as absent" is withdrawn, and the value-at-the-point shortcut now requires the first sample of each approached side to be defined. Before → after: `limit("x*ln(x)","x",0)` `0.0` → "the expression is undefined for x < 0.0 next to the point ...; use side "+" for the limit from the right"; `limit("sqrt(x)","x",0)`, `limit("x^0.5","x",0)`, `limit("sqrt(1-x^2)","x",1)` `0.0` → errors (with `"+"`, `"+"`, `"-"`: `0.0`); `limit("sin(sqrt(x))/sqrt(x)","x",0)` `1.0` → error (with `"+"`: `1.0`). The calc builtins never received keyword arguments, so `limit("1/x","x",0,side="+")` ran two-sided and `integral("x","x",0,1,foo=2)` answered `0.5`; every calc builtin now refuses a keyword it does not take ("integral: unknown keyword argument `foo`; it takes no keyword arguments: pass its arguments by position") or one given twice. Affects PHS programs and the bindings' calculus calls.
- **A unit written after an uncertainty that already follows a unit is an error, and an uncertainty is never dropped** (commit `8decf7b`). `1 m +/- 0.1 m` and `1 m ± 0.1 m` were `1.00 ± 0.10 m^2` (the second `m` multiplied) and are "`1 m +/- 0.1 m`: the uncertainty takes no unit of its own: write `1 +/- 0.1 m`, with the unit once, after the uncertainty" (every form: `±`, `%`, the `(a, b)` pair, `sigma`, `dof`). An uncertainty after a parenthesised expression that is not a literal value is an error instead of being dropped: `(2 + 3) +/- 0.1 m` was `5.0 m`, `x = 2 m; (x) +/- 0.1` `2.0 m`, `(1 +/- 0.1) +/- 0.2` `1.00 ± 0.10`, `(1 +/- 0.1) m +/- 0.2` `1.0 ± 0.2 m`. A sigma bound after an expression is an error ("a `sigma` bound is written after a literal target value, `x == 9.80 m/s^2 +/- 2 sigma`"): `(x == t +/- 2 sigma)` with `t` a variable compared exactly (`False`) and `assert(x == t +/- 2 sigma)` was "Invalid operand types". Unchanged and accepted: `1 +/- 0.1 m`, `1 m +/- 0.1`, `10.0 +/- 0.5 m`, `1 m +/- 10 %`, `1 +/- 10 % m`, `(1 +/- 0.1) m`, `1 +/- 0.1 m^2`. Affects PHS programs.
- **`=> unit` refuses a value that has no unit to convert** (commit `a14c883`). `convert_value_to_unit` returned anything that was not a quantity, vector or range unchanged: `a = 1 m; b = 2 m; (a<b) => km` was `True`, `True => km` `True`, `"x" => km` `x`, `[True, 1 m] => cm` `[True, 100.0 cm]`, `f => km` `fn f`. A Bool, String, Function, Equation, Plot, Sigma or None (also inside a vector or range) is now "cannot convert a Bool (True) to `km`: only a quantity or a number, or a vector, matrix or range of them, has a unit to convert", and a name with no value says "`unbound_name` has no value: there is nothing to convert to `km`" (it was its own text). A plain number converts as the dimensionless value it is (`5 => km` is still an error, `0.5 => %` still `50.0 %`). Affects PHS programs; in the repository only lines taken out of longer programs, where the converted name is unbound, changed.
- **Migrating a PHS program to these rules.** `x > 0` → `x > 0 m` (the unit of `x`; `t > 0` with `t` in degC → `t > 0 degC`); `20 dB == 100` → compare with a level, `20 dB > 10 dB`, or the ratio, `(x => unity) == 100`; `30 deg > 0` → `30 deg > 0 deg`; `while true` → `while True`; `if x` → `if x != 0 m`; `while i` (a number) → `while i != 0`; `if s` (text) → `if s == "on"`; `x => m + y` → `(x => m) + y`; `a < b < c` → `a < b and b < c`; `pi = 3` and any other binding of `pi`, `π` or a constant of the catalog → another name; `1 m +/- 0.1 m` → `1 +/- 0.1 m`; a two-sided `limit` whose expression is defined on one side only → pass the side, `limit("x*ln(x)","x",0,"+")`; two statements on one line → separate them with `;`. The language guide (and the identical `phs doc` text) has the precedence table, the resolution order of names, the comparison table and the condition table with these errors.
- **The unfrozen catalog with a `physure.conf` in the working directory is built once per version of the file** instead of on every use (a PHS script of 2000 quantity literals took about seven times longer with a one-line `physure.conf`). The merge is cached by the file's absolute path, length and modification time; a use costs one `stat`, and while the modification time is within two seconds of the reading the text is compared again, so a quick edit of the same length is still seen. The file's `[Settings]` and `[Compatibility]` are now applied when the merge is built or rebuilt, not on every use: a setting the program changes afterwards is no longer put back by the next unit parse. A file edited with its length and an old modification time restored by hand is not seen until `frozen::reset_cache()` or a change of directory.
- **A conversion reads the radian and the steradian as 1, as the SI does.** `½·I·ω² => J` (the energy of a rotating disk), `(10 rad/s) * (0.5 m) => m/s`, `(377 rad/s) * (0.1 H) => ohm` and `(100 cd) / (2 m)^2 => lx` were unit mismatches, because the catalog made the angle a base dimension. SI Brochure Table 4 gives `rad` and `sr` the expression 1, so `=>`, `to`, the binding of an annotated parameter and the registry's conversion plan now identify them with 1 when the rest of the unit agrees. Nothing else does: a sum or a comparison still refuses an angle against a plain number (`2 rad + 1`, `5 deg + 50 %`, `2 m*rad + 1 m`), `rad` still does not convert to `sr` or to a level, and `10 rad/s => Hz` is still refused, because the SI reserves the hertz for periodic phenomena and a frequency and an angular frequency differ by 2π (`(10 rad/s) / (2π rad) => Hz` is the way to write it). `[Settings] angle_mode = dimension` in `physure.conf`, `with physure.angle_mode("dimension"):` in Python, or `physure_core::units::angle_mode::scoped(AngleMode::Dimension)` in Rust brings back the old behaviour exactly, and `[Compatibility]` in `physure.conf` lists the markers a conversion may read as 1. In Python `physure.get_angle_mode()` reads the mode, `Quantity.to` asks the core when the dimensions differ so that an angle a conversion may read as 1 converts, and a system conf can name the periodic units (the hertz). `phs check` stays silent on a conversion that differs only in the angle, because the interpreter decides it under the angle mode. Design: `docs/superpowers/specs/2026-11-05-angle-mode-design.md`.

- **Java results that reuse a measurement are different, and now correct.** `x.subtract(x)` is exactly `0` (it was `sqrt(2) u`), `x.multiply(x)` and `x.pow(2)` have uncertainty `2 |x| u` (the first was `sqrt(2) |x| u`), `x.add(y).subtract(y)` is `x` with its own uncertainty, `x.to("cm")` is the same measurement as `x`, and a function called with `f(x, x)` sees one measurement. Checked against the GUM formulas for 8 shape pairs and 4 operations on numpy, torch and JAX, under `python_lineage()`, and through the differentiable torch store, where the gradient of the uncertainty with respect to the input uncertainties equals the gradient of the GUM formula written in torch. JAX needed three more fixes on the way: its Jacobians are converted to numpy at the Rust boundary like torch's, the broadcast operator is dense as that backend's identity and diagonal operators are (a BCOO is not an `is_array` there and was read as a scalar), and the sign of a subtraction is applied to the coefficients instead of multiplying a sparse operator.
- **A scalar quantity on the left of an array no longer loses the array's uncertainty.** `Q_(2.0, "m", 0.1) + array_quantity` answered with the scalar's uncertainty alone (silently wrong); `scalar * array` and `scalar / array` raised an error or, with a 0-d numpy array, gave a wrong value for every element but the first. The array operand now drives the operation (`s + A = A + s`, `s - A = -(A - s)`, `s / A = A**-1 * s` for the propagation); the magnitude of each is bit-for-bit what plain arithmetic gives, including the quotient (`1/a * s` differs from `s / a` in the last digit for a quarter of the elements).
- **A quantity keeps its unit when a plain array multiplies or divides it.** `Q_(array, "s") * np.array(...)`, `/ np.array(...)` and `np.array(...) * Q_(...)` came out dimensionless (`unit * ndarray` is numpy's reflected product, an array of units), and with torch `tensor / quantity` kept the unit instead of inverting it while `tensor + quantity` was treated as if the tensor were in the quantity's unit. A plain number or array is dimensionless and leaves the unit alone; `tensor + seconds` and `tensor - seconds` raise `IncompatibleUnitsError` like `5 m + 2` does; a dimensionless quantity can absorb a plain array additively.
- **Uncertain arrays on torch propagate again.** Adding, subtracting, multiplying or dividing two torch `Quantity` arrays that carry an uncertainty (`Q_(torch_a, "m", torch_u) * Q_(torch_b, "s", torch_v)`), or multiplying one by a number, raised `TypeError: argument 'jacobians': 'Tensor' object cannot be converted to 'PyArray'`; only `**` worked. The covariance store kept the Jacobians as torch tensors, which the Rust core cannot take (it holds numpy arrays; `register_diagonal` already converted its variance, `propagate` did not). The values are now handed to the core as numpy arrays, so torch gives what numpy gives. A Jacobian keeps its autograd graph only under `physure.python_lineage()`, as before; the magnitude keeps its gradient either way. 49 tests check the standard uncertainty of 11 operations on 1-D and 2-D arrays against the formulas of the GUM (JCGM 100:2008, 5.1) written out in the test, for numpy (the Rust store) and torch, in float64 and float32. Operations between uncertain arrays of different shapes (broadcasting) are fixed in the entry above.
- **Runaway recursion no longer aborts the process.** `fn f(x) = f(x)` followed by `f(1)` overflowed the native stack and killed the whole `phs` process. Every user-function call now counts its depth and stops at `call depth limit` (1,000 for an unrestricted interpreter, 200 in the sandbox). Measured: a PHS call costs 15 to 20 KB of native stack in a release build (about 100 KB in debug), so a 1 MiB main thread, the Windows default, still overflows near 60 levels before the limit is reached; only an interpreter given a stack budget (the sandbox) is protected on a small stack.
- **The Java jar finds its native library on an Intel Mac.** The loader read the JVM's `os.arch` straight into the path of the library inside the jar, and OpenJDK reports an Intel Mac as `x86_64` where Linux and Windows say `amd64`; the release stages the Intel Mac library under `macos/amd64`, so on those machines the jar looked for `/natives/macos/x86_64/...`, found nothing and failed (unless a library path was set by hand). `NativeLibraryLocator` names the platform (`windows`, `macos`, `linux`; `amd64`, `aarch64`) from what the JVM reports, `x86_64`, `x64`, `arm64` and the like included. Found by reading the loader against the release workflow, not by a failing user report; no macOS machine was involved, and the first release that ships it is its test on a Mac.
- **Parsing nested brackets no longer takes exponential time or ends the process.** `physure-script` parsed the contents of every parenthesis twice (`method_call | primary_base`), so each level of nesting doubled the time: 24 nested parentheses took 53 seconds in a native build, 18 took 19 seconds in WebAssembly, and 30 would have taken hours, in the CLI, the language server and every binding. A primary is now one rule (a base and zero or more `.name(...)`), and 24 levels parse in 3 ms. Beyond that, 100 levels overflowed the stack and ended the process (a JVM, the CLI and the language server with it, which no caller can catch): source that nests brackets deeper than 64 levels (`physure_script::parser::MAX_NESTING_DEPTH`, brackets in strings and comments not counted) is now a parse error.
- **A quantity's number and unit reach the Java and WASM callers together.** `2 m * 3 km` is a quantity of 6 in a unit with scale 1000, which the core shows as `6000.0 m^2`; the bindings read the stored 6 and the scale-less symbol `m^2` separately, so a caller got 6 `m^2`, a thousand times too small and no error (`2 m * 3 km`, `3 km / 2 m`, a dot product of vectors in different scales). `Quantity::display_parts()` is the triple `Display` already used, and the JNI results and the WASM `value`, `uncertainty` and `unit` getters now read it.
- **A unit the core writes, the core reads back.** A fractional power was written `m^1/2`, which the unit parser reads as `m^1` divided by 2 and refuses, so the unit of `sqrt(4 m)` could not be used in a second operation in any binding. It is written `m^(1/2)` now.
- **An uncertainty that is `NaN` or infinite is an error, not an exact value.** `Quantity::with_uncertainty(1.0, f64::NAN, "m")` came out with no uncertainty at all. A negative one is its magnitude, as before.
- **`u` is no longer listed as a mass unit.** The `mass` category named `u`, which is only the prefix micro and not a unit, so `getUnitScale("u")` failed for a name taken from the catalog's own list; a test now parses every unit of every category.
- **The Java `Quantity` no longer drops what the core computed or answers what the core refuses.** The native operations never received the uncertainty (`(10 ± 0.5 m) + (5 ± 0.3 m)` had none), and the wrapper around them repeated the core in Java: it caught every native error and added the raw numbers (`1 m + 5` was `6 m`, `5 + 1 m` was `6`), converted before adding (`20 degC + 5 K` was refused and `20 degC - 5 K` was 288.15 K), scaled a temperature point by a plain number (`20 degC * 2`), answered `1 m / 0` with `Infinity ± NaN`, took `sin(90 deg)` as 0.894 and `sin(1 m)` as a number, overflowed `round(1e300, 20)` to 0.09 and read `1.5 ± 0.1 m` as 1.5 of the unit `± 0.1 m`. Addition, subtraction, scalars and conversion are the core's now (uncertainty in and out), trigonometry reads the angle in its unit and propagates its uncertainty, and `Quantity.parse` reads both `+/-` and `±` and refuses `1,5 m`. A `null` argument is a `NullPointerException`, and a `Quantity` with a `NaN` or infinite uncertainty is an `IllegalArgumentException`.
- **A Java `UnitRegistry` shared by threads no longer corrupts the native heap.** Eight threads calling `evaluate` on one registry ended the JVM with `0xC0000374` (heap corruption), because the PHS interpreter behind it is one mutable native object. Every call, `close()` included, now holds the registry's lock; separate registries do not wait for each other.
- **The Java calculus calls work.** `UnitRegistry.solve`, `deriv` and `integral`, and everything built on them (`PhyFunction.deriv`, `integral`, `solve`, `PhyEquation.solve`), failed with "Undefined function 'solve'" because the interpreter never unlocked the calculus builtins, which the WASM binding does. A double quote in an argument is an `IllegalArgumentException`: it ended the PHS string the argument is put in, and what followed ran as a statement.
- **`UnitRegistry.evaluate` returns the value of the last statement, exactly.** It parsed the whole text output: the README's `a = 15 m; b = 5 m; a * b` came back as 15 of the unit `m\n5.0 m\n75.0 m^2`, and an uncertainty was rounded for display (`0.2236` read `0.2`). A native `evaluateQuantity` returns the quantity itself, and an expression that is not a quantity (a string, nothing) is a `PhysureException`.
- **Java functions and equations.** `PhyFunction.add`, `subtract`, `multiply`, `divide` and `compose` returned the left operand unchanged for functions defined in PHS and now build the combined function; combining a Java function with a PHS one is an `UnsupportedOperationException`. A call keeps the precision and the uncertainty of its quantity arguments. `PhyEquation` splits on its own `=` and not on the one in `<=`, `==`, `>=` or `!=`, `substitute` takes `$` and `\` in the value as text, and `call` solves for the one variable not given (it failed for every equation). `QuantityMatrix.det` handles any square size, and `QuantityVector.norm` and a vector dotted with itself take each component as one measurement (`x * x` is `x^2`): the norm of `(3 ± 0.1, 4 ± 0.1) m` had an uncertainty of 0.071 and is 0.1, as the first-order propagation says.
- **PHS evaluation reads units against the registry it runs for.** The PHS parser (which decides that a word after a number is a unit) and the quantities built from unit text while a program runs used the embedded catalog whatever registry the caller had, so on a registry built from `km = 7.0, L, [km]`, `getUnitScale("km")` said 7 and `evaluate("1 km")` used 1000, and a unit it added (`5 fur`) was unknown to `evaluate`. `physure_core::units::with_catalog(&registry, || ...)` makes a registry the catalog that unit text is read against, on that thread, for the duration of the call (scopes nest, the inner one wins, a panic restores the outer one, another thread does not see it; no scope reads the embedded catalog as before), and the Java and WASM bindings run `evaluate`, `evaluateRaw`, `solve`, `deriv`, `integral` and `PhyFunction` calls inside the scope of their registry. `1 km => m` is 7 m on that registry, `5 fur => m` is 1005.84 m on one that defines the furlong, and two registries (and two threads) each answer with their own. `UnitRegistry::redefinitions_of(base)` names the units a registry gives another meaning than `base`. Design: `2026-10-30-phs-per-registry-catalog-design.md`.
- **Custom unit definitions are read strictly in Java and WASM.** A line that could not be read was dropped without a word (a unit "defined" by it was then unknown), and a conf's `[Settings]`, which are process-wide, changed the whole process. `UnitRegistry.fromContent`, `new UnitRegistry(path)` and the WASM `UnitRegistry.fromContent` now throw `Invalid unit definitions: ...` naming the line, and the WASM `fromContent` returns a `Result` (it throws in JavaScript). The embedded catalog is parsed once, not once per registry, in WASM too.
- **A Java `UnitRegistry` uses the catalog it was built from, and no longer rebuilds it on every call.** The native side ignored the registry handle: every call (`getUnitExponents`, `getUnitPowers`, `getUnitScale`, `getCategories`, and the quantity operations) parsed the embedded catalog again, about 0.8 ms each, and a registry made with `UnitRegistry.fromContent(...)` or `new UnitRegistry(path)` threw the custom conf away, so a unit defined there was "unknown" (`getUnitScale("fur")` failed after `furlong = 201.168, L, [fur]`). The handle now owns its catalog, the embedded one parsed once per process plus the custom conf, so those calls take about 3 microseconds (`getUnitScale`) and 11 (`getUnitPowers`) and a custom unit is known to the registry that has it and to no other. `evaluate` costs about 0.4 ms per call, which is the PHS interpreter and not the registry; it now reads the registry's own catalog too (see the entry on PHS evaluation). Present in the Java artifact up to 0.3.0.
- **Java `UnitRegistry.getUnitExponents` no longer answers a fractional power with its numerator.** It returned the exponent's numerator only, so `s^0.5` was `{s=1}`, `m^1.5` was `{m=3}` and `Hz^0.5` was `{s=-1}`: a wrong dimension with no error (found by the contract test above; the WASM binding was fixed for this in August, the Java one was not). `getUnitExponents` keeps returning `Map<String, Integer>` and now throws `PhysureException` for a unit that has a fractional exponent, naming `getUnitPowers`; whole exponents are unchanged. Present in the Java artifact up to 0.3.0.

## [0.3.0] - 2026-10-29

**Tags:** `v0.3.0`, `core-v0.3.0`, `java-v0.3.0`

**Upgrading from 0.2.x.** This release moves the unit algebra into the Rust core and deletes the Python code that duplicated it, so several things that were Python objects are now data or answers of the core. What to change in code written against 0.2.x (each is described below):

- `UnitSystem.register_unit(...)` takes `scale`, `offset` and `level` instead of a converter object, and `physure.domain.measurement.converters` is gone.
- The tables of `UnitSystem` (`UNIT_DIMENSIONS`, `UNIT_REGISTRY`, `ALIASES`, ..., `get_definition`, `get_base_unit_for_dimension`) are gone: ask `system.core_registry`.
- `physure.units.core`, `physure.units._index` and `UnitRegistry.register_static` are gone; the units of `physure.units` are the catalog's names, so `units.km` works and `units.attodB` does not.
- A plain number no longer scales an absolute temperature (`Q_(20, 'degC') * 2` is a `ValueError`), a level and a plain quantity do not add, and angle and solid angle are different dimensions.
- The powers of units and dimensions are exact (an `int` or a `Fraction`) and read-only, and a dimension keeps fractional powers (`Q_(4, 's') ** 0.5` has the dimension `T^(1/2)`).

### Changed
- **Python and the core now share one unit catalog.** Python used to carry its own hand-maintained copy of `physure.conf` that had drifted from `physure-core`'s: it did not know `percent` / `%`, `ppm` or Spanish aliases such as `julio`, and it never saw `parallel_threshold`, `max_loop_iterations` or `max_pipeline_steps` in `[Settings]`. The copy could not simply be refreshed, because `configparser`'s default interpolation raises on the literal `%` in `percent`'s alias list. Python's `UnitSystem` is now built from the catalog embedded in the native extension (`physure._core.default_conf()`), read with interpolation off, so a unit added to `physure-core/src/units/physure.conf` is available to both. A `physure.conf` in the working directory still overrides the defaults, and is now also read without `%` interpolation, so a `%%` in it is no longer collapsed to `%`.
- **`jit` moved out of the private `physure._jit` package** to `physure.application.jit`, so the tracing primitives no longer import `Quantity`. `physure.jit` and `from physure import jit` are unchanged.
- **`trace_formulas` moved from `physure.application.tracing.context` to `physure.domain.symbolic.tracer`**, next to `FormulaTracer`, so the tracer state that the arithmetic reads no longer imports the symbolic package. It was never exported from `physure`; code that imported it from the old path must follow.
- **Units with several definitions have one name per definition.** `cal` is the thermochemical calorie (`cal_th`; `cal_it` is the International Table one), `BTU` the International Table BTU (`btu_it`; `btu_th`, `btu_iso`), `acre` the international acre (`acre_international`; `acre_us_survey`), `gal` and `fl_oz` the US ones (`gal_us`, `fl_oz_us`; `gallon_imperial`, `fluid_ounce_imperial`), `hp` the mechanical horsepower (`hp_mechanical`; `hp_metric`, `hp_electric`) and `yr` the Julian year (`year_julian`; `year_gregorian`). The short symbols keep their meaning, except `btu`/`BTU`, whose old value `1055.06` was a rounding that matched no definition. A test reads the catalog and fails if two units claim the same name.
- **The Rust core converts between units with exact rational scales.** A unit's scale is kept as the rational that `physure.conf` writes (`ExactScale`, in `physure-core/src/units/exact.rs`) and a conversion divides two of them and rounds once, as Python's `Fraction` arithmetic does. `1 ppm => percent` was `9.999999999999999e-05`, `1 ft => inch` was `12.000000000000002` and `1 g/cm^3 => kg/m^3` was `999.9999999999999`; they are `1e-4`, `12.0` and `1000.0`, and Python and Rust now agree to the last bit over the whole catalog. Converting out of Celsius or Fahrenheit divides by the scale instead of multiplying by its reciprocal, as Python does. The `scale` field of `RationalUnit` stays an `f64`, now the single rounding of the exact one.
- **The embedded unit catalog is parsed once per process.** `Parser::parse_expression` (and with it every quantity written from a unit string in Rust) rebuilt the whole registry from `physure.conf` on every call, and applied the catalog's `[Settings]` again each time, undoing any setting changed since. Each call now gets a copy of the registry parsed the first time; a decimal that fits in two `u128` is read without allocating.
- **The Rust core reads spelled-out prefixes.** `kilometer`, `attoampere` and the rest of the `[Prefixes]` names of the catalog are units in PHS and the Rust API, as they already were in Python. When several prefixes fit a name the longest one that leaves a unit wins; the answer used to depend on the order a hash map happened to iterate in.
- **The Rust core knows the logarithmic units.** `dB`, `decibel` and `pH` (the `Log` lines of the catalog, which the Rust parser used to skip) are levels in PHS and the Rust API: a level is dimensionless and a scale over plain ratios, so `20 dB => unity` is `100`, `50 percent => dB` is `-3.01`, `7 pH => unity` is `1e-07` and `10 dB + 20 dB` is `20.41 dB`, with the same operations as Python's `LogarithmicConverter` (the two agree to the last bit) and the uncertainty carried through the logarithm. Angles and solid angles still never convert into a ratio. A level takes no prefix and no compound unit (`dB/km`, `dB*m`, `dB^2`) and is refused in `ln`, `sqrt`, `sin`, ... instead of being read as a plain number; `10 dB + 1 unity` is refused as well (Python adds the numbers after converting). `pH` is the level and no longer the picohenry (`picohenry` still is).
- **The Rust core adds temperatures as points and intervals.** An absolute temperature (`degC`, `degF`) is a point on an interval scale: `20 degC + 5 K` is `25 degC`, `20 degC - 5 K` is `15 degC`, `20 degC - 5 degC` is `15 K`, and the sum of two points (`20 degC + 5 degC`, which used to answer `571.3 K`) or an interval minus a point (`5 K - 20 degC`) is an error. A plain number no longer scales a point (`2 * 20 degC` is 40 degC on one scale and 586 K on another); a pure sign does keep the scale, and a quantity with dimensions of its own takes the temperature as the absolute one it is (`R * 25 degC`, `T^4`). Python still scales the number in place and multiplies degC as if it had no zero point; the parity suite records both until Python adopts the core's types.
- **The Rust core says what a unit is.** `UnitRegistry::facts("J/s")` gives the physical dimension by dimension symbol (`L²·M·T⁻³`), the kind (`Point` for degC and degF, `Delta` for everything else), whether the unit is linear (not for an offset or a logarithmic unit), the name it is shown by (`W`) and the unit written out in base symbols (`kg·m²/s³`), with the same answers as Python's `CompoundUnit` for every unit of the catalog; `RationalUnit::symbolic_repr` prints a unit the way a `CompoundUnit` does (`kg·m/s²`, `kg/(m·s²)`, `1/s`). `physure._core.unit_facts(expression)` exposes it. Python keeps showing `degC` as written, because its catalog restates celsius with another symbol; that is the one difference, and goes away with the second catalog.
- **`physure.UnitDefinition`, `physure.convert_units_inplace` and the Rust `UnitConverter` and `UnitDefinition` are removed.** They were a second unit model, with `f64` scales, that `UnitSystem` filled in at registration and never read: the `_core.UnitDefinition` it built for each unit was dropped on the spot, and nothing called `convert_units_inplace`. Conversions go through `RationalUnit` and the registry, which keep exact scales; `UnitKind` (`Point` for degC and degF, `Delta` for the rest) stays, in `physure_core::units`.
- **`5 * unit` builds a quantity for the units of the core too.** `physure._core.RationalUnit` has a `__rmul__` that calls a factory Python registers at import (`register_quantity_factory`), so the sugar no longer depends on the unit being a `CompoundUnit`; the result of unit algebra keeps it.
- **The registry of the extension answers what a unit is.** `physure._core.UnitRegistry` has `parse_atomic`, `simplify`, `expand`, `dimension_of`, `kind_of`, `is_linear_of`, `alias_of`, `factor_between` and `facts`, and `UnitRegistry.from_conf_text(extra)` builds one from the catalog plus extra conf text. They are what `CompoundUnit` answers with a `UnitSystem`; nothing in Python calls them yet.
- **The core takes a system's definitions strictly.** `UnitRegistry.extend_conf(text)` (and `from_conf_text`) adds units, prefixes and levels all or nothing and raises with every line the core cannot read; the embedded catalog has none. A text parsed after another starts from the base units of the first, so money (`$`) can be a dimension of its own (`EUR = 1.08, $` is scaled from `USD`) and a second unit at scale 1 on a dimension that has a base unit is a name for it, not a new base unit. `[Settings]` is not applied by it. A level can be the level of a quantity: `dBW = Log, 10, 1.0, M*L^2*T^-3` converts to watts through the logarithm and levels of a power add as the powers.
- **A unit system owns a registry of the core, built from what it registers.** `UnitSystem.core_registry` is built by `create_system` from the merged `[Prefixes]` and `[Units]` text, and `register_unit` and `register_prefix` write what they register as conf text and give it to the registry first, so a unit the core cannot take leaves the system as it was. **Breaking:** a converter that is not exactly a `LinearConverter`, an `OffsetConverter` or a `LogarithmicConverter` (a custom `UnitConverter`, or a subclass of those) is refused with `TypeError`; a name a conf cannot hold, a number that is not finite, or a `kind` or `recipe` that contradicts the converter, with `ValueError`. `create_system` raises `ValueError` naming every line of `[Units]` or `[Prefixes]` that the core cannot read (the shipped system files have none). A prefix factor in a conf can be a fraction (`third = th, 1/3`), as a unit factor can. The best-effort mirror that kept a core registry in step is gone, with its three `contextlib.suppress` sites, the prefixed units it registered without their prefix factor, and the two lookup paths of `get_unit` and `in` that returned a unit without its scale (no test reached them).
- **Units and their conversion are the core's answer, and Python keeps no algorithm of its own for them.** `CompoundUnit.dimension`, `is_linear`, `kind`, `simplify`, `conversion_factor_to` and the alias that `to_string(use_alias=True)` shows ask the core registry of the system (`UnitSystem.core_registry`), and `Quantity.to` applies the plan that `UnitRegistry.conversion(source, target)` gives (a factor, two temperature scales with their zero points rounded once, or a level through the ratio it stands for) with the operations of its backend. About 140 lines of Python that did the same beside the core are deleted; conversions run twice as fast (`q.to('km')` 52 µs to 19 µs). Where Python and the core differed, the core's behaviour is the one now, each a change of its own: an angle and a solid angle no longer convert into each other (`Q_(1, 'arcmin').to('sr')` is an `IncompatibleUnitsError`); the catalog's `noprefix` is honoured by the core, so `kh`, `kin`, `kmi` and a prefix on a level (`kilodB`) are unknown units; a temperature scale with a prefix (`centicelsius`), which Python could not resolve, resolves and converts through its zero point; `UnitSystem.register_alias` writes the alias as a unit of the core, so the units of its exponents have to be registered first (`UnknownUnitError` otherwise); `CompoundUnit.to_string` loses `alias_preference`, which nothing used. The extension raises `physure._core.UnknownUnitError` (`symbol`, `suggestion`) and `UnitMismatchError` (`expected`, `actual`), both `ValueError`s, and `UnitRegistry.conversion` is new.
- **Points, intervals and levels combine as the core says, and the converters of the unit definitions are no longer read for arithmetic.** A point (degC, degF) moved by an interval stays a point in its own scale and two points make an interval in kelvin, now by the plan of the core, so the uncertainty adds up (`20±1 degC + 5±0.5 K` is `25 ± 1.12 degC`; the old code dropped it) and every temperature scale the core knows works, with arrays and tensors. Levels add as the quantities they stand for (`10 dB + 10 dB` is 13.01 dB, with the uncertainty through the ratio). **Breaking:** a level and a plain quantity do not add (`10 dB + 1` added the numbers after converting one of them); a plain number does not scale an absolute temperature (`Q_(20, 'degC') * 2` and `2 / Q_(20, 'degC')` are a `ValueError`; a pure sign still mirrors the number, `-Q_(25, 'degC')`), and a product with a dimensioned quantity, a quotient or a power takes the temperature as the absolute one it is (`R * Q_(25, 'degC')` is `R * 298.15 K`; it multiplied the 25 and kept degC in the unit); in `physure.core.functional`, `sub_quantities` of an interval minus a point is an error. `CompoundUnit.base_unit(system)` is new. About 300 lines of Python that read converters beside the core are deleted.
- **A dimension is a unit over the dimension symbols, with exact powers, and the core does its algebra.** `Dimension` held an integer vector of nine slots and rebuilt a Rust `DimVector` on every product; it now holds the powers as exact fractions (`T^(1/2)`) and multiplying, dividing and raising it to a power are the operations of the core. Any symbol is a dimension after the SI ones (an unknown symbol was a `DimensionError`), and the unit parser no longer refuses a fractional power (`s^(1/2)` went to the SymPy fallback, an optional extra). `Dimension._vector`, `ZERO_VECTOR`, `DIM_COUNT` and the constructor that took a tuple are gone. `UnitRegistry.unit_of_dimension` says the unit of a dimension in the base units the registry declares (the table of base units that `Quantity` kept in Python is deleted), and `CompoundUnit.of_dimension` is the one place that asks.
- **Unit strings are read by the core's parser alone.** `m**2`, `kg*m/s**2` and `s**0.5` used to reach a SymPy-based parser: the core read `**` as a multiplication and knew no decimal exponent, so the first such string imported SymPy (an optional extra) and cost its import time. The core now reads `**` as the power and a decimal exponent as the exact fraction it stands for (`0.5` is 1/2, `2.25` is 9/4), and `physure.core.parsing`, the SymPy unit parser, is deleted. A string that is not a unit is still a `ValueError`.
- **A unit system resolves its units through its registry, and the parallel tables of Python are gone.** `UnitSystem.get_unit` (and with it `in`) reads the expression with the core's parser, asks the system's core registry whether it knows every unit in it, simplifies it there and keeps the result per system; a unit the registry does not know raises `UnknownUnitError`, as before. `create_system` gives the registry the merged `[Prefixes]` and `[Units]` text in two calls instead of registering every unit one by one in Python (`startup.py` is 200 lines shorter), and `register_unit`, `register_prefix` and `register_alias` write what they register as conf text. **Breaking:** `UnitSystem.UNIT_SYMBOL_REGISTRY`, `UNIT_DIMENSIONS`, `UNIT_REGISTRY`, `ALIASES`, `ALIAS_TO_EXPONENTS`, `PREFIX_REGISTRY`, `prefix_definitions`, `unit_definitions`, `dimension_definitions` and `get_definition` are removed: ask `system.core_registry` (`names()`, `facts(name)`, `factor_between`). `physure.domain.measurement.conversions.UnitDefinition`, the `IUnitRepository` port, the legacy `Unit` dataclass and `block_prefixes_for_dimension_symbol` / `prefixes_allowed_for_dimension_symbol` are removed with them. Converting to a derived unit (`.to('km/h')`) is about 30 % faster, and no other operation of the benchmark is slower by more than the noise.
- **The registry of the extension lists its names.** `physure._core.UnitRegistry.names()` (and `UnitRegistry::names` in the Rust core) gives every name the registry holds for a unit, sorted: base units, derived units and aliases. A prefixed name such as `km` is read from its prefix and unit, so it is not in the list.
- **The units of `physure.units` are the catalog's, looked up in the core.** `physure.units.m` was `CompoundUnit({"m": 1})` out of two generated modules, `physure/units/core.py` and `_index.py` (13,700 lines written by `scripts/compile_units.py`), that listed every name of the catalog and every spelled-out prefix of it. A name is a unit now when the registry of the embedded `physure.conf` knows it, and `dir(units)` is what the core lists (13,235 names). `units.km`, `units.kPa` and `units.GHz` work (the index only held `units.kilometer`); `units.attodB` (a prefix on a level) and `units.k1` (a prefix on the number one), which the index listed by accident, do not. A name of the catalog no longer scans the entry points, and a unit of the catalog wins over a plugin of the same name. **Breaking:** `physure.units.core`, `physure.units._index` (`UNIT_INDEX`), `physure.units.electromagnetism`, `scripts/compile_units.py`, the 18 built-in `physure.units` entry points of `pyproject.toml` and `UnitRegistry.register_static` are removed (`UnitRegistry.register_catalog(catalog, make_unit)` takes the place of the last); the entry point group stays open to plugins. `physure sync-types` writes the stubs from `dir(units)` and types the units as `CompoundUnit` (they said `Unit`, a class removed with step 6b), so `Q_(...).to('km')` is a valid `UnitName` too.
- **The core says which names are units.** `UnitRegistry::knows(name)` (`UnitRegistry.knows` in the extension) answers whether a name is a unit, prefixed ones such as `km` and `kilometer` included, and `resolvable_names()` lists all of them, sorted (13,483 for the catalog). A level takes no prefix and neither does a unit marked `noprefix`, so `attodB` is not a name.
- **The unit `1` takes no prefix in the core.** `unity = 1.0, 1, [1]` is marked `noprefix`: `k1`, `E1` and `kilounity` were read as a prefix scaling the number one, and `E1` could not even be written as a unit (the lexer reads it as `E` followed by `1`).
- **`UnitSystem.register_unit` takes a scale, a zero point or a level, not a converter.** `register_unit(symbol, dimension, scale, name, *aliases, offset=, level=, recipe=, allow_prefixes=)` writes what it is given as the conf line the core reads, as it did with the converters, but the arguments are the numbers of that line: `register_unit("ft", length, Fraction(381, 1250), "foot")`, `register_unit("degC", heat, 1, "celsius", offset="273.15")`, `register_unit("dBW", power, name="decibel-watt", level=(10.0, 1.0))`. `scale` is 1 when omitted; a nonzero `offset` is what makes a unit an absolute scale; a `level` is `(factor, reference)` and excludes a scale, a zero point and a recipe. A number is exact when it is a `Fraction` or a `str` (`"5/9"`, `"0.3048"`) and a `float` is the decimal it prints as. **Breaking:** the third argument is no longer a converter object, `kind=` is gone (the zero point decides it) and `TypeError` for an unsupported converter is gone with them; `unit_definition_text` and `enable_currency` follow.
- **The converters module is removed.** `physure.domain.measurement.converters` (`UnitConverter`, `LinearConverter`, `OffsetConverter`, `AffineConverter`, `LogarithmicConverter`, `affine_coefficients`) is deleted: nothing registered a unit with one any more, the core computes the coefficients of a conversion, and the level stage of a conversion plan, the only user left, had four formulas to borrow, which now live in `conversion_plan.py` with the same arithmetic.
- **The powers of a unit are an `int` or a `Fraction`.** `CompoundUnit` held them as a dictionary of floats next to the rationals of the core; now `unit.exponents` is derived from one canonical key and is exact, whatever number a power was given as: a float is the closest simple fraction (`0.5` is `Fraction(1, 2)`), a pair or a list is that fraction. `CompoundUnit({"m": 0.5})`, `CompoundUnit({"m": (1, 2)})` and `CompoundUnit({"m": Fraction(1, 2)})` are the same unit, and a fractional power goes through the algebra of the core with its exact pair. **Breaking:** the powers read back as `Fraction(1, 2)` where they read `0.5` (`repr` shows it; `==` with a float still holds, and a fractional power is still shown as `m⁰⋅⁵`), and `normalize_exponents` is removed. Building the unit of a product no longer normalises and sorts every time (the flyweight finds an instance by the items it was given first, as `Dimension` does): `unit * unit` and `unit ** 2` are 37 % faster, and the operations on quantities, which spend little of their time there, move by less than the noise of the machine.
- **`propagate_affine` moved from `physure.domain.measurement.vectorized_uncertainty` to `physure.backends.affine`**, next to the backend code that calls it, so the backends no longer import the model. Code that imported it from the old path must follow.
- **The Rust uncertainty models propagate `log10` and `pow10`.** The Gaussian, moments, Monte Carlo and unscented models apply them, which the levels of the catalog (`dB`, `pH`) need to carry an uncertainty through a conversion.
- **`UnitSystem.get_base_unit_for_dimension` and `CompoundUnit._compound_factor` are removed.** Nothing called either (not the library, not the tests). The first read the `base_units` entry of `[System]` that `imperial.conf` (`L:ft, M:lb, T:s`) and `international.conf` set, and that nothing else reads: the setting is still stored in `system.settings` but no code applies it, and `CompoundUnit.of_dimension(dimension, system)` returns the base units of the registry, which are the SI ones for every system. The second was the factor to the base units that `conversion_factor_to` and the registry answer. **Breaking** for code that called the first.

### Fixed
- **Writing to `unit.exponents` or `dimension.exponents` no longer changes the unit for everyone.** A `CompoundUnit` or a `Dimension` is shared by everything that builds the same powers, and its `exponents` was a plain dictionary, so `unit.exponents["m"] = 2` changed the unit in the whole process. It is a read-only mapping now (`copy()` is still a dictionary, `==` with a dict holds), and a `Dimension` pickles its powers as a dict.
- **A unit raised to a power through floats keeps no error.** `(m ** 0.1) ** 3` was `m^0.30000000000000004` and reached the core as 1125899906842624/3752999689475413 instead of 3/10, and a power that came back from the core as a pair (`1/3`) was divided into a float on the way. It is `m^(3/10)` now, and `m ** 0.1 * m ** 0.2` is `m ** 0.3`.
- **A fractional power is no longer truncated to zero on its way to the core.** `_ensure_rational`, which turns an object with powers into a core unit for the JIT tracer and the compiler, took every power that was not a float or a pair for an integer: `int(Fraction(1, 2))` is 0, so a dimension of `T^(1/2)` came back dimensionless.
- **The units reference lists `unity`, `ppm` and `percent` under the dimension `1`.** `scripts/generate_units_readme.py` read the dimension `1` of those lines as an offset, so `docs/UNITS.md` listed them as `Scale ... (Offset 1)` under dimensions called `[1]`, `[ppm]` and `[%`, and `percent` had lost its `%` alias.
- **`SymbolicQuantity`, `SymbolicExpression` and `Function` use the unit system that is active when they are created.** Their default was bound once, when physure was first imported, so a `physure.use_system(...)` block was silently ignored and the object came out in the original system.
- **The torch backend no longer prints `DEBUG:` lines.** `TorchBackend.sparse_matmul` and `AutogradCovarianceStore.propagate` wrote a line to standard output on every call.
- **The constants table keeps every digit.** `[Constants]` was written with `f"{value:e}"`, which keeps 7 significant digits, so 189 of its 411 values (`eps0`, `mu0`, `sigma`, `m_p`, `m_n`, `u`, `a0`, `mu_B`, `Ryd`, ...) were wrong in the seventh digit and `eps0 * mu0 * c^2` was off by 3e-8. The table is now regenerated with `repr` from CODATA 2022 (scipy 1.15 or later), and the atomic and Planck units of `[Units]`, which were CODATA 2018, follow: `electron_mass` is `9.1093837139e-31` kg and `bohr` `5.29177210544e-11` m.
- **Unit factors that were typed with a few digits are now the exact value of their definition.** `1 deg` was `60.000043 arcmin`, `1 atm` was `760.0021 Torr`, `1 gal` was `230.99989 in^3` and `1 pc` was `3.26160 ly`, because `degree`, `arcminute`, `arcsecond`, `light_year`, `parsec`, `slug`, `acre`, `gallon_us`, `fluid_ounce`, `pound_force`, `btu`, `horsepower`, `psi`, `torr`, `mmHg`, `franklin` and `debye` carried 5 to 9 digits (up to 7e-6 off). `torr` is now exactly `101325/760` Pa and `mmHg` the conventional `133.322387415` Pa, `btu` is the International Table BTU.
- **The `physure` core benchmarks compile again.** `benches/core_benchmarks.rs` still imported the crate by its old name and a symbolic engine that moved to `physure-script`; the symbolic benchmark is gone and benchmarks for prefixed units, conversions and unit parsing are added.
- **Temperatures convert exactly at the fixed points.** `100 degC => degF` was `211.99999999999997` and `212 degF => degC` was `100.00000000000006`: the catalog wrote 5/9 and the Fahrenheit zero point as rounded decimals. They are now the fractions `5/9` and `45967/180` (the catalog reads fractions), and a conversion between temperature scales is `old * scale + shift` with both numbers rounded once from the exact values, in the Rust core and in Python alike. 0, 32, 100, 212 and -40 convert to each other exactly. The test that checks the generated type stubs no longer rewrites the tracked ones.
- **`delta_celsius` converts to kelvin in the Rust core.** It was declared at scale 1 on the dimension of kelvin and became a base unit of its own, so `5 delta_celsius => K` failed as a unit mismatch in PHS (`delta_degC` and `degC_delta` too). Only the first declaration at scale 1 for a dimension symbol is a base unit now; the catalog marks the one later entry that is a kind of its own, `steradian`, with `own_kind`, so an angle still never converts into a solid angle.
- **The sign of a temperature literal keeps its scale in PHS.** `-40 degC` was `-313.15 K`, a temperature below absolute zero, because the minus sign multiplied the temperature in kelvin; it is minus forty degrees Celsius now (233.15 K, and `-40 degF` is `-40 degC`).
- **Temperatures compare by what they stand for in PHS.** `20 degC == 293.15 K` was `false` and `20 degC > 280 K` too, because the comparison ignored the zero point; `min`, `max`, ranges and `assert` use the same value.
- **Java: a conversion returns the value and the spread in the target unit.** `Quantity.to` divided the spread by the target scale after the value had already been converted, so the spread was wrong whenever the target was not an SI unit.
- **The temperature scales are declared once.** `physure-python`'s `international.conf` restated `celsius`, `fahrenheit` and their deltas on top of the core catalog (the later definition wins), so the fractions of the catalog never reached Python until the numbers there were corrected by hand. The system file keeps only its `[System]` section; the core catalog lists `°C` and `°F` as the symbols of the two scales, the names Python has always shown them by.
- **A unit line the core could not read no longer registers its names.** A line whose dimension and recipe did not parse was dropped, but its aliases were registered pointing at nothing.
- **A dimension no longer drops a fractional power.** `(Q_(4, 's') ** 0.5).dimension`, `Q_(1, 'Hz**0.5').dimension` and the dimension of a noise density in `V/Hz**0.5` were `Dimensionless` (the power was cut to an integer), so `Q_(1, 's**0.5') + Q_(1, '1')` was accepted and `V/sqrt(Hz)` could be added to a number. They keep their time (`T^(1/2)`, `T^(-1/2)`, `L²·M·T^(-5/2)·I⁻¹`) and the addition raises `IncompatibleUnitsError`.

## [0.2.4] - 2026-08-28

**Tags:** `v0.2.4`, `core-v0.2.4`, `java-v0.2.4`

### Added
- **Asymmetric uncertainties as moments** (`physure_core::uncertainty::moments`). A measurement quoted as `12.3 +0.5 -0.4 pb` is not two standard deviations, it is the shape of a distribution, and averaging the two halves — the only thing a symmetric model can do — throws away the part that is often interesting. `moments_from_sigmas` maps the pair onto the first three moments of a dimidiated Gaussian in closed form, and `sigmas_from_moments` inverts it by bisection on the skewness, which is monotonic in σ⁺/σ⁻. A skew beyond what a pair of half-widths can describe (just under 1, reached when one side is zero) is reported rather than silently rounded down to the most skewed shape available. `MomentsBackend` and the `UncertaintyValue::Moments` variant give the pair somewhere to live — mean, spread with its lineage, third moment — and stop there. Propagating a third moment is left open on purpose: every arithmetic path on a moments value raises rather than falling through to a symmetric rule, which would report a plausible number with the skew averaged away. This is the groundwork a propagation model can be built on, not the model.
- **PHS parses asymmetric uncertainties**: `12.3 +/- (0.5, 0.4) pb` and `12.3 ± (0.5, 0.4) pb`, upper half first, in the order the operator reads. The parentheses are what keep the notation out of the binary operators' way — a bare `+` never reaches the uncertainty rule, so `12.3 + (0.5)` is still an addition, and the lexer already matched `+/-` and `±` ahead of `+` and `-`. Each half takes its own percentage, so `+/- (1%, 0.5)` means +2.0 and −0.5 on a magnitude of 200. Evaluating one raises: nothing propagates a third moment yet, and every consumer downstream takes a single standard deviation, so the measurement would come back symmetric with no sign that half of what was written had been dropped. The three transpilers refuse for the same reason rather than emitting a symmetric quantity in Rust, Python or Java.
- **`physure.uncertainty_model(...)`**, a per-scope choice of which uncertainty model a quantity is built with — `"gaussian"` today, `"moments"` once asymmetric propagation lands. It is a separate knob from `propagation_mode`, which decides how correlations are handled, not what shape the distribution has. Keeping them apart is what makes an asymmetric measurement the exception rather than the default: three moments cost more to carry through a large dataset than one standard deviation, so they are asked for per scope instead of paid for everywhere. A model that does not exist is rejected on the spot instead of quietly leaving the previous one in place, and selecting `"moments"` raises rather than handing back a gaussian, which would report symmetric answers inside a block entered to say the measurement is not symmetric.
- **`propagation_mode` is read from `physure.conf`.** The `[Settings]` key had been in the shipped conf since the beginning and nothing had ever read it, so a project that set `propagation_mode = uncorrelated` got correlated results anyway, with nothing on screen to say the file had been ignored. `get_propagation_mode()` now falls back to the active unit system's setting, so the default can be set once in a file instead of wrapping every call site; a `physure.propagation_mode(...)` block still outranks it, including when it asks for the value the file already had. An unknown mode is rejected when the conf is loaded rather than on use — a misspelt `uncorelated` would otherwise fall back to correlated, which is the one wrong answer that looks right.
- **The core honours `propagation_mode` too, so PHS and Python cannot disagree about it** (`physure_core::uncertainty::mode`). The core had no uncorrelated arm to switch to — lineage was always tracked, which is what "correlated" means — so a conf that asked for anything else was read by Python and ignored by everything else, and the same script gave two different answers depending on which language ran it. `uncorrelated` is now read in `Lineage::combine`, the single place where shared ancestry is what makes a difference, so both the Gaussian and the unscented arms get it from one branch: the result is a fresh measurement rather than a derivation, since keeping the operand ids would let a later operation cancel against the source the first one was told to ignore. The Monte Carlo arm carries correlation in its sample array instead of its lineage and gets its own answer, so a hand-picked backend cannot keep cancelling inside the scope that exists to stop it. `monte_carlo` and `unscented` in the conf pick what a new measurement is built with, and an exact value stays Gaussian whatever the setting says — a plain number has no distribution to sample, and drawing a thousand identical samples for every literal in a script is a cost with nothing behind it. `mode::scoped` gives Rust callers the per-thread override Python has as a context manager; the file's setting is process-wide, since a thread-local would land on whichever thread happened to read the conf first.
- **PhyEquation & PhyFunction architecture** with equation arithmetic, callable equations, and multi-language transpilation parity tests across PHS, Rust, Python, and Java 8+.
- **Infinity support** (`inf`, `-inf`, `∞`, `-∞`, `infinity`, `oo`) in PHS grammar, limits, and improper integrals.
- **Advanced vector calculus operators**: high-order derivatives `diff(f, var, order)`, gradient `grad`, divergence `div`, curl `curl`, laplacian `laplacian`.
- **`QuantityVector` & `QuantityMatrix`** (Order 1 & Order 2 tensors) with dot product, cross product, norm, transpose, matrix multiplication, and determinant — all with physical unit propagation.
- **N-dimensional native plotting**, written in the crate with no Rust dependency added:
  - `plot3d(expr, title)`: an interactive 3D surface, rendered in the browser with WebGL — rotate, zoom and pan, rather than the fixed isometric projection it started as. three.js and its `OrbitControls` are vendored into the crate instead of pulled from a CDN, so a plot opens with no network and the version cannot change under a file that was saved months ago.
  - `plot_field(u_expr, v_expr, title)`: 2D vector field arrow plots with magnitude colour scaling.
  - `plot_nd(matrix, title)`: N-D parallel coordinates visualization.
- **Strict tensor type separation**: `Quantity` (scalar), `QuantityVector` (vector), `QuantityMatrix` (matrix) as first-class citizens in Rust, PHS, Python, and Java 8+.
- **`PhsValue::Matrix`** variant in `physure-script` with full exporter support (JSON, CSV, Python).
- **Java 8+ classes** `com.physure.QuantityVector` and `com.physure.QuantityMatrix` with idiomatic Java collections API.
- **Python classes** `physure.QuantityVector` and `physure.QuantityMatrix` exposed via PyO3.
- **`abs` accepts a quantity**, returning the same unit and the same uncertainty — folding a magnitude to its absolute value moves where a measurement sits, not how well it is known. It delegates to the core's `UncertaintyValue::propagate_function`, so a Monte Carlo or unscented backend is not silently downgraded to Gaussian.
- **`exp`, `ln` and `log` accept a dimensionless quantity**, propagating its uncertainty, and reject a dimensioned one with a clear error. They used to refuse every quantity ("exp expects a number"), so `exp(0.5 +/- 0.01)` could not be evaluated at all, while `ln(5 m)` — a physics error, since a power series can only be summed over terms that share a unit — was the sort of thing the tool is supposed to catch.
- **`export3d(expr, "surface.stl")`** writes a plotted surface as a mesh file — STL, OBJ, glTF or PLY, chosen from the extension — so a result can go to a slicer, a CAD tool or a renderer instead of only to a screen. Reachable from PHS, the `phs` CLI, the LSP and Python (`Quantity.plot_3d`, `Quantity.export_3d`).
- **Range syntax, `a .. b`.** Sampling a surface needs an interval, and `plot3d(P, x = -2 m .. 2 m)` was a syntax error: `BinaryOp::Range` and `PhsValue::Range` had been in the tree from the start with no grammar rule that could produce one.
- **String interpolation**: `"the beam carries {load}"`, in the interpreter and all three transpile targets. Python and Rust had been emitting the raw literal as an f-string and a `format!`, which only holds for a bare name — `{2 m + 3 m}` is PHS, not Python — and Java, having no interpolated literal at all, raised. All three now share `split_interpolated`, which cuts the literal exactly as the interpreter does and transpiles each expression on its own; Java builds the result with `+`, and a string-valued assignment is declared `String` instead of `Quantity`, which did not compile.
- **`%` and `ppm` are dimensionless units.** `5.0 %` parses, and `200 kPa * 5 %` is `10 kPa` — a percentage is a ratio, so multiplying by one is a unit-preserving operation the system can check rather than arithmetic the reader has to do in their head.
- **Spanish unit aliases**: julio, vatio, pascalio, voltio, ohmio and porcentaje, alongside the SI symbols.
- **The `base` format spec**, quoting a measurement in the units it is built from: `2 kΩ: base` is `2000 A^-2 * kg * m^2 * s^-3`. The scale moves into the magnitude and the uncertainty is rescaled with it, so the physical value is the one `Display` prints — only the terms change. `physure-cli/README.md` had advertised it since its first page while the grammar only accepted the numeric `.3e` form, so it was a parse error. The `frac` spec advertised beside it is dropped from the README instead of guessed at.
- **The `frac` and `ifrac` format specs**, writing a magnitude as a common or a mixed fraction: `1.5 m: frac` is `3/2 m` and `1.5 m: ifrac` is `1 1/2 m`. Only when a fraction applies — a value with no small one behind it keeps its decimal rather than being rounded into a tidier lie, so `3.14159265358979: frac` stays as it is while `0.1 + 0.2: frac` is `3/10`. The f64 debris is cut at the 15 decimal digits an f64 actually carries before the ratio is taken, the same cut `format_float` makes, or `25 m/s => km/h` would ask for the fraction of 89.99999999999999 rather than of 90. Both halves of a measurement are quoted, not just the mean: `9.81 +/- 0.05 m/s^2: frac` is `981/100 ± 1/20 m/s^2`.
- **A range is checked to be an interval when it is built.** `PhsValue::Range` was assembled from whatever stood on either side of `..`, so `0 m .. 100 s` was a range between a length and a time, `100 m .. 0 m` ran backwards, and `"a" .. 100 m` held a string — none of which a plot's sampling or an integration limit has an answer for, and all of which produce a figure that looks fine and is not. Building one now refuses mismatched dimensions (`Incompatible dimensions in range: 'm' vs 's'`), a pair that does not run upwards, including the empty `5 m .. 5 m`, an endpoint that is not a magnitude, and a bound that cannot be ordered at all. An endpoint carrying no dimension of its own takes the other's unit, so `0 .. 100 m` reads as `0 m .. 100 m` — on paper the lower bound of an interval does not repeat the unit either — while a range of plain numbers stays dimensionless. A missing endpoint is caught by the grammar, which requires both.
- **The core's asymmetric moments are reachable from Python** (`physure._core.AsymmetricMoments`, `physure._core.MomentsBackend`, `max_skewness()`). Only `Lineage` had been exported, so the Python side could not reach `moments_from_sigmas` or its bisection inverse, and a second implementation of them would have drifted from this one until the two disagreed about the skew of the same measurement. Propagation is deliberately not exposed, because the core does not have it: a value built here can be measured and reported, and every arithmetic path still refuses rather than answering symmetrically.

- **Affine temperature units: `degC`, `degF` and `degR`.** The core's `RationalUnit` was purely multiplicative — a unit was a set of dimensions and a scale factor — so a scale with a zero point could not be expressed at all, and Celsius and Fahrenheit were simply missing from `physure.conf`. `20.0 degC` failed with "Unknown unit 'degC' — did you mean 'deg'?", which made calorimetry (`m * cap * (T2 - T1)`) unwritable in PHS. `RationalUnit` now carries an `offset`, applied as `base = value * scale + offset`, and the conf parser reads the zero point from the `factor, offset, dimension` form the Python config had been using all along. Only Celsius and Fahrenheit are affine; Rankine shares Kelvin's zero point and the `delta_*` units are the interval scales. The offset takes part in unit equality, since `degC` and `K` are otherwise identical and a conversion between them would look like a no-op.
- **PHS gains loops: `for x in iterable { ... }` and `while cond { ... }`.** Before this, the only way to repeat something over a range was to unroll it by hand. `for` is a vectorized functional expression — it evaluates to the vector of its body's value over each element of `iterable`, pre-allocating with `Vec::with_capacity` rather than growing one push at a time. `while` is the imperative counterpart for convergence loops (Newton's method, fixed-point iteration) that don't know their length in advance; it is capped at 10,000 iterations so a condition that never turns false fails loudly instead of hanging. Both compile to their natural equivalent in all four transpiled targets — Python, JavaScript/TypeScript, Rust and Java — as well as the interpreter.
- **`physure-lsp` re-evaluates a document incrementally instead of re-running every statement on every keystroke.** Editing one statement now only re-runs it and whatever transitively depends on it, tracked via a per-statement read/write dependency graph built from the AST (no execution needed to build it). A persisted interpreter carries `env` forward across edits instead of being rebuilt from scratch each time. Handles dynamic scoping correctly — a function call depends on every global its body reads, not just names in the call site's own text — and invalidates stale values left behind by a statement that used to succeed and now fails, including when an edit renames which variable a statement writes.
- **The Direct Foreign Execution Bridge**, so a `.phs` file is an autodeployable source of truth for external runtimes instead of something that only runs through the CLI or whatever language a transpile happens to target. `PhsModule` introspects a file's exported function signatures and their units, then `invoke`s one with unit-coerced arguments, dimensional checks, and full uncertainty propagation ahead of evaluation. `compose_with` chains two modules' functions together, and `PhsPipeline` runs a DAG of steps end to end. Python gets the ergonomic entry points, `physure.load_phs()` and `load_dir()`, returning a `PhsModuleWrapper` that calls exported functions as ordinary attributes with real `inspect.Signature`s. `phs pack` bundles a directory into a versioned `.phspkg`, described by a `phs.toml` manifest; `phs serve` exposes the same modules as a standalone REST model server with a function catalog and a pipeline-execution endpoint — three consumption tiers (in-process, packaged, served) over one execution engine, so a formula update never forces a re-transpile of every consumer.

- `Quantity.java` now uses `List<Quantity>` instead of raw `double[]` for `QuantityVector` interactions; added `mul()`, `div()`, `sub()` shorthand aliases.
- **BREAKING (PHS)**: local bindings moved from `let name = value in body` to a postfix `where` clause — `body where name = value[, name2 = value2]`. A later binding can use an earlier one. `let` stays a reserved word with no rule behind it, so the old form fails to parse instead of quietly meaning "let times inches".

### Fixed
- **`while`'s condition and a reassigned loop variable didn't survive transpilation.** The parser desugars `i < 5` into `FunctionCall { name: "op_<", .. }`, and no codegen backend translated that back into a native comparison — a `while` loop transpiled to Python, Rust, Java or JS/TS called a function named `op_<` that doesn't exist. Separately, Rust and JS/TS redeclare rather than mutate a variable reassigned inside a loop body (`let mut i = ...` or `let i = ...` again, shadowing the outer binding instead of updating it, since both are block-scoped languages), and Rust's arithmetic codegen moved rather than borrowed operands, so an expression that reuses a variable twice (`x + 2.0 / x`, as a convergence loop's body routinely does) failed to compile with "use of moved value". None of these had a test that actually ran the generated code — only text-pattern assertions — until a Newton's-method parity case was added and executed through all four targets.
- **A unit symbol inside an equation string was read as an unbound variable.** The symbolic layer has no notion of units, so it parses `"y = x * 2.0 m"` into plain algebra over the symbols `x` and `m`; calling the equation then reported `m` as a missing argument. Past that check the bare symbol evaluated to a *string* — units only ever sit next to a number in the source, never in a denominator — so `"Q = m * {cap} * (T2 - T1)"` with `cap = 4.18 J / (gram * K)` died on "Invalid operand types for binary operation". Unit symbols are now tolerated as unknowns only after both strict passes have failed, so a unit-named unknown (solving for `V`, `T`, `A`) is still solved for rather than read as one volt, and a bare unit symbol evaluates as one of its unit so the dimensions reassemble.
- **Absolute temperatures normalise to Kelvin before any arithmetic.** An affine unit has no arithmetic of its own: `120 degF - 20 degC` has to become an interval, and multiplying an absolute temperature cannot inherit a zero point. Both operands go to K first, so a difference is a true interval (28.89 K) instead of two subtracted zero points, and every multiplicative path in `Quantity` keeps the offset-free operands it already assumed.
- **The READMEs stated the wrong uncertainty default.** Both the root and `physure-python` READMEs annotated `propagation_mode` with `(default: uncorrelated)`. The default is *correlated* — `CONFIGURED` starts at zero and `PropagationMode::from_u8` maps zero to `Correlated` — so the one line a reader would trust to know whether `x - x` cancels said the opposite of what the code does. Both now name the real default and say why it is the default. Their architecture blocks also still listed `ext/` as "grammar DSL, IO, pandas, numba", naming a module that was removed and omitting the six that are actually there.
- **A dead term in the symbolic parser's operator match.** `match_op` tested `(is_op || text_matches) && text_matches`, which reduces to `text_matches`, so the token-kind check it appeared to perform never ran. Behaviour is unchanged — `=` and `==` are the only strings passed in and both only ever lex as `Op` — but `clippy::overly_complex_bool_expr` is deny-by-default, so this had been failing `cargo clippy` for the whole workspace.
- **The `phs` CLI reports the version it actually is.** The help header, the REPL banner and the TUI header each hardcoded `v0.2.4` while the workspace was at `0.2.3`, so the one number a user would quote in a bug report was wrong in all three places and right nowhere. They now read `env!("CARGO_PKG_VERSION")`, the same source the transpiler's generated-file header already used, which is why that header was the only one still correct. The REPL frame is padded to its inner width as well — it had been built from fixed-width string literals that were one character short, so the right edge never lined up, and a version string of a different length would have skewed it further.
- **Transpiled Rust kept the formula's shape.** The Rust codegen emitted binary operations unparenthesised, so any grouped subexpression was re-associated by Rust's own precedence on the way out: `12.0 m / (3.0 s * 2.0)` became `12 / 3 * 2` and answered 8 where PHS, Python and Java all answer 2. Division was the visible case, but the same flattening applied to every arithmetic operator, and the result still compiled and still carried a plausible-looking unit — the failure mode a transpiler is least able to afford, since the wrong number leaves as source code someone else then trusts. Operands are now wrapped the way the Python target already wrapped them.
- **The pandas accessor is `.phs`, not `.mk`.** `mk` was this project's provisional name and the Series accessor was the last public API still carrying it. `.mk` stays registered as a deprecated alias that warns and forwards, so existing code keeps working and is told what to change rather than failing with an `AttributeError` that says nothing about where the name went. The Python REPL prompt moved from `mk> ` to `phs> ` for the same reason — it disagreed with the native `phs` REPL, which had always used `phs> `.
- **A `(sigma-, sigma+)` pair on a scalar says what it is.** `Q_(12.3, "pb", uncertainty=(0.5, 0.4))` reached `float()` and came back as `TypeError: float() argument must be a string or a real number, not 'tuple'` — a message about the plumbing, where PHS answers the same input by naming what it cannot do yet. The two entry points now say the same thing. The guard is narrow on purpose: a scalar has no second element for a second uncertainty to belong to, so a pair on one can only be asymmetric, while an array magnitude keeps taking a tuple as the ordinary per-element uncertainty it has always been.
- **Java adds uncertainties in quadrature, and refuses a sum it cannot convert.** `Quantity.add` and `Quantity.subtract` fell back to `a.uncertainty + b.uncertainty`, so 0.3 and 0.3 gave 0.6 where Rust and Python give 0.42 — an error about 40% too large for every quantity that went through the Java path. Worse, the mismatched-unit fallback added the raw magnitudes with no conversion at all, so `1 km + 1 m` came back as 2 km; that path now raises a `PhysureException` naming what it cannot do instead of returning a number. There is no JUnit in the build, so the check compiles the classes with `javac` and runs a small program against them.
- **A quantity no longer behaves as if it were independent of itself.** A standard deviation alone cannot say whether two operands came from the same measurement, so `x - x` reported `σ·√2` instead of zero, `x / x` reported an uncertain 1, and `x + x` gave ±0.42 where the answer is ±0.6 — a result that looks plausible enough to ship in a paper. The core now records provenance alongside every scalar uncertainty (`uncertainty::lineage`): each value carries the measurements it came from and their sensitivities, merged through the chain rule `c_new(id) = Σ Jₖ·cₖ(id)`, with `σ = √(Σc²)`. Where two lineages share no source this reduces exactly to the quadrature sum it replaces, so results for independent quantities are unchanged. Tracking is always on, needs no opt-in, and covers all three models — Gaussian and unscented by jacobian, Monte Carlo through its shared sample array. Cancellation survives scaling and intermediate steps: `2x - 2x` is zero and `(x + y) - y` returns `x` with its own uncertainty. Two separate measurements that happen to agree still combine in quadrature, and an exact constant (a conversion factor, a plain number) never becomes a source. This reaches PHS, the Rust API and Python alike, where previously only Python could get it right and only inside a `PhysureContext()`.
- **Python's scalar path now tracks provenance by default, matching the Rust core.** `Uncertainty.from_standard` picked the lineage-tracking model only when a *vector* covariance store happened to be active — a store that path never uses — so a plain `Q_(3.0, "m", uncertainty=0.3)` fell back to a variance-only model and `x - x` came out at 0.4243 while the same expression in Rust and PHS gave 0. Scalars are lineage-tracked unconditionally now, so the three environments agree digit for digit. Array uncertainties keep their existing dispatch. `propagation_mode("uncorrelated")` becomes the opt-out and is now actually honoured — it had no effect on this path before, and only looked like it worked because the default was already behaving uncorrelated.
- **Python computes scalar provenance in the Rust core, not next to it.** The lineage type is exported as `physure._core.Lineage` and `LineageModel` is a thin wrapper over it, so a scalar uncertainty in Python follows the same code that PHS and the Rust API follow instead of a parallel implementation that can drift away from it one rounding decision at a time. A lineage pickles through `Lineage.from_terms`, which rebuilds it with its original source ids rather than minting new ones — an unpickled quantity still cancels against itself — and importing ids raises the core's counter past them, so a lineage restored in a fresh process cannot collide with one minted there later. `Lineage` compares by its terms, never by which variant holds them, so a value that made that round trip still equals the one it came from.
- **A live JAX or torch uncertainty now says so instead of answering differently.** Coefficients are `f64` in the core, so a value still attached to an autograd graph or a `jax.jit` trace cannot be handed to it without detaching it. Under `jax.jit`, `x - x` used to come back as 0.1414 while PHS, Rust and eager Python all said 0. Such a value now raises and names the two ways forward: `physure.python_lineage()` for the Python implementation, which keeps the graph and gives the correct 0, or `physure.propagation_mode("uncorrelated")` to drop provenance deliberately. It is per-user and per-scope, never a default, because a silently different answer across two languages is worse than an error. Concrete tensors and arrays with no graph are untouched and still go through the array machinery, where `x - x` remains the quadrature sum.
- **`QuantityVector::norm()` reported an uncertainty exactly √2 too small.** It squared the vector through `dot(self, self)`, and `mul` treats its two operands as statistically independent, so each component contributed σ(xᵢ²) = √2·xᵢσᵢ instead of the correct 2·xᵢσᵢ. Every component is now squared with `pow(2.0)`, whose analytic derivative knows it is the same variable, which gives the GUM result σ = √(Σ (xᵢ/|v|)²σᵢ²) and preserves the component's uncertainty backend instead of collapsing it to Gaussian. For `(1 ± 0.09, 2 ± 0.06, 2 ± 0.18) m` the norm now reads `3 ± 0.13 m`, not `3 ± 0.0919 m`.
- **Monte Carlo propagation no longer redraws an operand that already carries samples.** `ensure_samples` rebuilt the other operand's array from its mean and standard deviation even when that operand was itself a Monte Carlo value, so any shared history between the two was destroyed — the one thing sampling is supposed to give for free. `x - x` returned 0.0028 ± 0.4253 instead of 0 ± 0, `x / x` returned 1.0101 ± 0.1455 instead of 1 ± 0, and `x + x` reported ±0.4227 where the answer is ±0.6. The propagation path now reuses the operand's own sample array when the lengths match; two independently drawn quantities still combine in quadrature, and correlation survives a unit conversion because rescaling multiplies by a zero-sigma constant.
- **A unit symbol that the script also binds as a variable is now rejected instead of guessed.** `g = 9.81 m / s ^ 2` followed by `f = 10.0 kg * g` read `g` as the gram unit and produced a mass-squared quantity where the author meant 98.1 N; with `t = 3.0 s` bound, `5 m / t` meant metre per *tonne*. The check runs once over the parsed program, so the interpreter and all three transpile targets are covered, and the error names the token and both rewrites: `(10 kg) * g` for the variable, `10 kg * "g"` for the unit. Only a token following an explicit `*` or `/` is a candidate — `10 m` is a quantity literal by grammar, so binding `m` does not poison every later literal.
- **`floor` and `ceil` keep the uncertainty**, like `round` now does. Both rebuilt the quantity with a zero standard deviation, so `floor(9.81 +/- 0.05 m/s^2)` printed as an exact `9.0 m / s ^ 2`. The mean is moved by adding an exact offset, which slides the whole distribution and leaves a Monte Carlo or unscented backend intact.
- **`sin`, `cos` and `tan` are dimensionally checked and keep the uncertainty.** They returned a bare number built from the mean — unit and uncertainty both discarded — and applied themselves to anything, so `sin(9.81 m/s^2)` answered -0.379 as though metres per second squared were radians. The argument must now be an angle (converted to radians through its own scale, so `sin(90 deg)` is 1) or a dimensionless value read as radians; the result is dimensionless and the sigma comes from the derivative.
- **A degree is a plane angle again.** `physure.conf` declares `radian` and `steradian` against the same dimension symbol, and the Rust loader let the last one win, so `deg`, `arcmin` and `arcsec` were registered as scaled *steradians*: `90 deg => rad` failed as a unit mismatch while `1 deg + 1 sr` was accepted.
- **Inches are usable again**: `in` was a grammar keyword taken by `let ... in`, so `12 in`, `12 in => cm` and `1.5 in^2` were parse errors and only the `inch` alias worked.
- **Every prefixed unit was read one character short.** The `_is_*` predicates in the grammar were written without `&`, so instead of peeking at the next character they consumed it, and the symbol that followed lost its first letter: `1 kg` evaluated as 1 gram, `100 kPa` as 100 pascal, `1 mol` as `1 * ol`. The answers were off by three orders of magnitude and carried the wrong unit while looking entirely ordinary on the page. A sweep test now evaluates all ~240 unit symbols the shipped systems define, and the handful that still fail are listed by name in `KNOWN_GAPS` rather than left to be rediscovered.
- **A unit symbol was truncated at its first digit.** `_unit_char` had no `ASCII_DIGIT`, so the remainder became an implicit multiplication: `1 a0` evaluated to `0.0 a` — the Bohr radius annihilated to zero — and `1 m2` to `2.0 m`. The lookup now tries the whole symbol before the digit-stripped stem, so `a0` stays the Bohr radius while `m2` is still metre squared, and a digit-bearing name that is not a unit (`x2`) is still an ordinary identifier.
- **Non-ASCII unit symbols never reached the registry.** The lookup scanned with `is_ascii_alphabetic`, so any Unicode symbol the grammar accepted resolved to the empty string and was handed to the expression parser, which rejects it: `1 Å` and `1 °` were parse errors, and `1 Ω` worked only because `Ω` happens to be listed in the `identifier` rule. The arcmin and arcsec prime aliases were also written as `'] #'` in `physure.conf`, where the alias list closes at the first `]`.
- **An unknown unit is reported instead of invented.** A symbol the registry did not know had a dimension fabricated for it, so `5 foobar` evaluated happily and every operation after it carried a unit that meant nothing. It now raises `UnknownUnit` with the nearest symbol as a suggestion, retrying case variants first, since a typo in the case is the common cause.
- **`1 km == 1000 m` was false** while `1 km + 1000 m` converted correctly — comparison read the magnitudes and ignored the scale, so the one operation whose whole job is to answer a question about equality was the one that got it wrong. All seven comparison builtins now share the scale-folding helper the arithmetic path uses, and comparing mismatched dimensions raises rather than answering.
- **`10.0 +/- 0.5 m` printed as `10.0 m`.** The uncertainty was parsed, carried and propagated correctly, and then dropped by `Display` — the one place a reader would look to check it.
- **`Ω` was missing from the derived-symbol table**, so `2 V / 3 A` printed as `kg·m²/(A²·s³)` instead of `0.667 Ω`.
- **`PhyFunction.solve()` produced a malformed definition.** The Python binding stringified the whole `PhsValue::Equation`, so `symbolic.py` embedded `var = expr` into a new function body and wrote out `name(...) = var = expr`. It now matches on the equation and returns the right-hand side alone.
- **`cond ? a : b` was eaten by the format spec.** `format_spec` accepted a bare `ASCII_ALPHA+`, so the `: b` of a ternary looked like a format directive and the branch disappeared into it. The `format` builtin also ignored the spec it was given and printed the default rendering.
- **`deriv("0.5*m*v^2", "v")` differentiated whatever was in scope.** A quoted string parsed as `Expr::Identifier`, so the interpreter looked its whole text up in the environment before falling back to a string: with `v = 3.0 m/s` bound, the formula was silently rewritten by the value. Strings are `Expr::Str` now and stay literal; `{expr}` is the explicit way to fold a value in. Interpolating a quantity used to defeat the purpose anyway — the symbolic parser had no implicit multiplication, so `0.5 * 2.0 kg * v^2` stranded `kg` after the number and the derivative collapsed to 0.
- **Calling an equation checked only one side for satisfied free symbols**, so an equation whose unknown sat on the left refused the arguments that would have solved it.
- **More derived symbols print as symbols**: V, F, S, Wb, T, H, lx and kat. Bq, Gy, Sv and lm are deliberately left unmapped: Bq shares its dimension with hertz, Gy with Sv, and lm with candela, and picking one of a genuinely ambiguous pair on the user's behalf is how `gal` became a galileo.
- **An anonymous compound unit folds its scale factor into the printed magnitude** before the derived-symbol lookup, so an ohm times a milliamp displays `239.68 V` instead of a base-unit magnitude with the scale left off.
- **Unicode letters are accepted in unit annotations**, so a parameter can be annotated `R: Ω` — `unit_term` took `ASCII_ALPHA` only, and every annotation using a non-ASCII symbol was a parse error.
- **The LSP reported diagnostics on the wrong line** and wrapped every message in a generic wrapper that hid what was actually wrong; `validate_unit_shadowing` now carries the statement's own position.
- **Method-call syntax never parsed.** `method_call` was a rule with nothing referring to it, so the interpreter arm that handles it was unreachable; `primary` now goes through it.
- **`100 kPa * sin(x)` parsed `sin` as a unit.** The unit rule matched the function name before the call rule could, turning a product into a nonsense dimension.
- **`call_arg` accepted only `name = value`**, so the guide's `plot3d(P, x: r)` would not parse; `name: value` is accepted too, with the plain-expression branch left last so a format spec (`x:.2f`) still wins. Reading a ternary's branches off `expr` also panicked, because `ternary_op` is a rule of its own and nests them a level deeper.
- **`J`, `kJ` and `kg·m²/s²` shared one entry in Python's unit cache.** The key was `RationalUnit::id`, which is derived from the dimensions alone, so whichever spelling arrived first answered for all of them. Scale and display name are part of the key now.
- **`physure_core::linalg` and `physure_core::plotting` were not declared in `lib.rs`**; without the first the workspace did not compile at all.
- **A scaled dimensionless unit printed a `unity` dimension.** A unit of dimension "1" was resolved through `dim_to_base`, which maps "1" to the `unity` unit, so `2 m * 3 %` printed as `m * unity`. Dimension "1" is tested before that lookup now, and `RationalUnit::mul`/`div` carry the display name through when the other operand is a dimensionless scale-1 unit.
- **`25 m/s => km/h` read `89.99999999999999 km/h`.** `format_float` printed the shortest string that round-trips an f64, which is honest and shows every piece of conversion debris. An f64 carries 15 decimal digits exactly and the debris always lands past them, so the magnitude is rounded to 15 significant figures and that result kept only when it is genuinely shorter — a literal typed to full precision still round-trips.
- **`__repr__` reassembles a prefixed symbol** (kPa, mV) for known derived units instead of falling back to base dimensions.
- **A unit symbol meant one thing in a literal and another after `=>`.** `2 Ω => kΩ` reported `Unknown unit 'k'`: a conversion target is parsed as an ordinary expression, so it goes through `identifier`, which was a hand-kept list of Greek letters for the first character and ASCII for the rest, and `kΩ` was cut after the `k`. The literal `1 kΩ` parsed correctly the whole time, because that path reads `_unit_char`, which is `LETTER`. Both rules read `LETTER` now. The list they replace was already missing symbols the registry ships (Å, and µ written as U+00B5 rather than U+03BC), which is how the defect survives: adding a unit does not tell anyone that a grammar rule elsewhere has to learn about it. The sweep guarding the literal position has a counterpart for the target position now, over the same ~240 symbols; `°` and `%` remain out of reach there, since no identifier can spell a character that is not a letter.
- **A constant on the left of an operation could change the uncertainty model.** Propagation dispatches on the left operand, so with `propagation_mode = monte_carlo` in the conf, `3 m + x` fell through to the generic arm and came back Gaussian with the samples discarded, while `x + 3 m` kept them: the same expression gave a different model depending on which side the constant sat on. An exact value has no distribution to lose, so it is now re-expressed in the other operand's model — n copies of the mean, or a zero-width sigma point — before the operation runs.
- `physure._core.Quantity.__str__` renders the measurement (`0.25 kPa`) by delegating to the core's `Display`, instead of repeating `__repr__` (`Quantity(0.25, kPa)`); the REPL and `print()` now read like the `phs` CLI.
- Local bindings now transpile to real code in the Python, Rust and Java targets. They used to be emitted as a call to an undefined `let(...)` function, so the generated file did not compile.
- **Uncertainties survive formatting, rounding and `repr`.** A format spec (`g:.2f`) printed the mean alone, `round(q, n)` rebuilt the quantity with a zero standard deviation, and `physure._core.Quantity.__repr__` omitted the uncertainty — an uncertain measurement looked exact in all three.
- **A percent uncertainty is relative again**: `9.81 +/- 0.5% m/s^2` was parsed as ±0.5 instead of ±0.049, a spread twenty times too wide. A percentage applied to a magnitude that is only known at run time is now rejected rather than guessed.
- Transpiled files stamp the compiler's real version. All three targets hardcoded `v0.2.4` while the workspace was on `0.2.3`, so a generated file named a compiler that had never produced it; the banner now comes from `env!("CARGO_PKG_VERSION")`.
- The `physure` crate README's usage example imported `use physure::{...}`, which does not compile. The package is `physure` but its library target is `physure_core`, and Cargo derives the import path from the latter. The README is not wired in with `include_str!`, so no doctest ever caught it.
- `Debug for Quantity` (Rust) prints `std_dev`, so a failing assertion about an uncertain quantity no longer reports what looks like a different measurement.
- **A PHS format spec applies to the whole expression, not to its right operand.** `op_format` sat inside `comp_expr`, one precedence level below `+ - => ..`, so the spec bound to whatever stood immediately to its left inside that level. `0.1 + 0.2: .2f` was a parse error, and `25 m/s => km/h: .2f` printed `25.00 m/s` — the spec formatted the conversion *target* and the conversion was dropped without a word, the one failure a unit library may never have quietly. Parenthesising the expression was the workaround and still works; it is no longer needed.
- **`..` binds looser than every other operator, so each endpoint is a whole expression.** It used to sit at the same precedence as `+` and `=>` and associate to the left, which left `0 m .. 100 m => km` reading as `(0 m .. 100 m) => km` — and since nothing converted a range, the `=> km` was dropped in silence. The conversion now belongs to the endpoint it was written on (`0 m .. 0.1 km`, and `0 m => km .. 100 m` gives `0 km .. 100 m`), while a parenthesised range converts as a range (`(0 m .. 100 m) => km` is `0 km .. 0.1 km`). A range is its two endpoints and nothing else, so multiplication, division, conversion and the format spec now reach both instead of neither: `(0 .. 100) m` is `0 m .. 100 m` and `0.5 m .. 1.5 m: ifrac` is `1/2 m .. 1 1/2 m`. Exactly one `..` per expression — `a .. b .. c` names no interval, and letting it parse would only pick one of the readings and print it as though it had been meant.
- **Transpiling a range reports instead of crashing.** `BinaryOp::Range` was `unreachable!()` in all three code generators, so `phs transpile` on a script holding `r = 0 m .. 100 m` panicked rather than saying what it could not do. An interval is something a builtin samples, not a value a Rust, Python or Java variable holds, so the three targets now return a codegen error naming the two ways forward: pass the range to the call that consumes it, or transpile its endpoints separately.
- **`linspace`, `parallel_map` and pipeline execution could bypass the loop-iteration ceiling meant to stop a script from hanging or exhausting memory.** `linspace` and `parallel_map` materialized their full input before ever checking `max_loop_iterations`, and `PhsPipeline` had no step-count ceiling at all. Each now checks its limit before doing the expensive work, closing the same denial-of-service shape three separate builtins had opened.
- **`phs serve` had four exploitable issues found in a live adversarial pentest of the bridge's model server.** An empty `--token` silently became a full auth bypass (`"" == ""` matches any blank header) while the startup banner still reported auth as enabled; token comparisons used plain `==`, a timing side-channel, closed with a constant-time byte compare; a malformed kwargs request unwound past the handler's own 400-JSON path into tiny_http's bodyless 500 fallback; and `Access-Control-Allow-Origin: *` was sent unconditionally, including with auth disabled, letting any page a browser visits script requests into a local server. An unbounded `thread::spawn`-per-connection model was replaced with a fixed 32-thread pool, and request bodies are now capped at 10 MB, since a pile of slow or oversized requests could otherwise exhaust threads or memory on their own.
- **`phs pack`/`phs validate` executed a manifest's top-level code as part of validating it.** `Manifest::validate()` instantiated every exported module through the full interpreter, so a side-effecting builtin like `export3d()` sitting at top level ran during what is documented as a safety check — the opposite of what "check before you trust it" promises. Validation now only parses a module and extracts its signatures; a new `--allow-execution` flag on `phs pack` opts back into full evaluation for callers who already trust the package.
- **A `phs.toml` manifest could point an entry or export outside its own package directory.** `base.join(rel_path)` never checked where the joined path actually landed, so `../../secret.phs` resolved and packed like any other export. Every manifest path is now canonicalized and checked against the package's canonicalized base directory before use, and a path that escapes it is rejected as a path traversal rather than packed.
- **`PhsModuleWrapper.__getattr__` recursed into itself forever** when an instance existed without `__init__` having run (`copy.copy`'s default reconstruction path, among others). It read `self._fn_cache` directly, so a lookup for the missing cache re-entered the same lookup; it now checks `self.__dict__` first, which never re-enters `__getattr__`.
- **A `.phs` function called from Python with mixed positional and keyword arguments, or with a plain non-unit string, misbehaved instead of erroring clearly.** The keyword path required every parameter to arrive as a keyword or raised, so a call mixing both forms failed even when the arguments were otherwise complete; the fix accepts either form and rejects only a genuine duplicate, unexpected, or missing argument by name. Separately, `_coerce_scalar` assumed any string containing a space was a unit expression and any other string was a bare number, so a non-numeric, non-unit string (a label passed through a pipeline step) raised instead of passing through unchanged; both conversions are now attempted and left as plain text on failure.
- **`physure-python/pyproject.toml` carried its own hand-set `version`, independent of `physure/__init__.py`'s `__version__`.** `bump-release.yml` only ever bumped the latter, and `release.yml`'s `check-version` job only ever checked the tag against the latter too — but maturin builds a wheel's actual version from `pyproject.toml`, so the `v0.2.4` tag built and uploaded wheels still labeled `0.2.3`, which PyPI silently skipped as already published. `bump-release.yml` now bumps both files in the same commit, and `check-version` fails the release outright if they ever disagree again, the same class of single-source-of-truth drift this project has already been bitten by once in its unit conf catalog.

# Configuration freeze, Phase 4b: moving code-resident data into the catalog — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every number that a user would legitimately want to pin, audit or override, and that today lives only in code, becomes catalog data (`physure.conf` keys or sections) that a frozen file copies, seals and governs; what cannot move is listed, with its owner, in a coverage table that is part of the guarantee (spec §9). Nobody may be led to believe something is frozen when it is not.

**Source:** `docs/superpowers/audits/2026-11-14-code-resident-numbers.md` §3 (class A), §8 (the proposed migration set M1-M10), §6 (randomness, environment), §11 (the defects track). **Owner decisions (2026-11-14):** Monte Carlo has a **fixed default seed (0), configurable, with an explicit random opt-in**; **printed text counts as a result**: display rules move into the catalog and a witness fixes printed text; defects were fixed first (done, merged). **Deferred, with the owner's later sign-off, to Phase 5 (bindings): M9 (the Python default `p = 0.95`) and M10 (unit display tables derive from the catalog: `µ` → `u` is a text change)**; the audit says so and the coverage table lists them as not frozen.

## Design decisions

1. **Compiled default = today's behaviour**, except the seed (decision 2) and the two documented text/exactness changes (currency exactness, decision 5). A frozen file that omits a key behaves exactly like a library without the key.
2. **Monte Carlo seed policy (owner decision): fixed default seed 0.** `[Settings] monte_carlo_seed = 0` (integer, `u64`) or `random` (OS entropy, today's behaviour). Semantics to settle in Task 1 and challenge in the review: the Monte Carlo generator is a **stream** seeded from the setting at the first draw after a configuration activation (and re-seeded when the setting changes or `reset_cache()`/activation runs), advancing with every draw; `with_seed(n)` scopes (CLI `--seed`, `phs eval`'s default 0, MCP, the witnesses) take precedence. Consequences the implementation must handle explicitly: (a) **parallel loops**: today `Limits::sequential` forces seeded runs to be sequential because a rayon worker does not see the thread-local seed scope (`CallerScopes` of the previous track deliberately does not carry the seed: each task would replay the caller's draws); with a default seed every run is "seeded", so the plan must keep large loops parallel **and** deterministic: each task opens `with_seed(derive(base, iteration index))` (a documented mixing function, stable across thread scheduling); measure that `for i in 0..20000 { ... Monte Carlo ... }` gives identical bits on 1 and 8 threads (`RAYON_NUM_THREADS`) and that performance does not regress where Monte Carlo is not used; (b) **threads in a host** (Python, WASM, Java, LSP, `serve`): each thread has its own stream; two threads must not start from the same state and silently correlate: derive the per-thread seed from `(base, a stable thread key)` and document what is and is not reproducible across threads; (c) the **REPL/`serve`** are processes: one stream per process; per-request reseeding is **not** done (it would make independent requests identical); (d) the CLI flags `--seed` and `phs eval` keep their meaning; (e) Python/WASM/Java read the compiled default or the embedded catalog's value until Phase 5 makes them honour a frozen file (state it in the coverage table); (f) `monte_carlo_seed = random` makes a frozen file non-reproducible **by choice**: `verify` says so as a warning and the witnesses are unaffected (they pin their own seed).
3. **Every new setting is also pinned for the witnesses.** The battery cases that depend on a setting open the thread-local `scoped_*` guard with the compiled default, exactly as the propagation mode is pinned (the review of Phase 3 measured why: a process-global setting changes witness results silently). New guards: samples, seed (already per-case), `asymmetric_shape`, `default_dof`, display keys.
4. **Python-only data (currency, thermochemistry tables) moves to catalog text now, but is listed "not frozen" until Phase 5** (Python cannot honour a frozen file: `default_conf()` refuses while one is in force). The core reader exists after this phase, so chemistry plan 3 and Phase 5 only have to delegate.
5. **Currency (M4):** a shipped, opt-in `currency.conf` (not in the default catalog: rates are not physics and would put `EUR` into every frozen file), read by `enable_currency()` through the core's `extend` path. **Not bit-identical, on purpose:** the core's exact scale gives `100 MXN => USD` = `5.9` where the Python float gave `5.8999999999999995`; CHANGELOG entry. The rates stay the Python file's current literals (`EUR 1.08`, `MXN 0.059`) — they are placeholders, not market data: the file says so in a comment, with a date, and the guide tells users to override them in their own conf. **No network fetch exists (audit §6.2); none is added.**
6. **Thermochemistry (M5):** sections `[Thermochemistry:<edition>]` following the `[AtomicWeights:<edition>]` pattern, a selector `[Chemistry] thermochemistry = <edition>`, user overrides in `[Thermochemistry]`, a core reader on `UnitRegistry`, edition names reserved and validated like the atomic-weight ones. The first edition carries **exactly** the Python table's numbers (bit-identical) and is named for what it is (`legacy-python-1`: 8 species, textbook values rounded to 1 decimal, no uncertainty, phase implicit, 298.15 K, 1 bar). **Scientific rigor:** the review must compare each of the 8 species' ΔfH° and S° with a primary source (NIST Chemistry WebBook / CODATA Key Values for Thermodynamics / NIST-JANAF) and list the deviations in the audit; a better-sourced edition (with uncertainties and phases) is **future work**, recorded in the coverage table, not part of this phase.
7. **Display rules (M7), printed text is a result (owner decision):** keys `display_significant_digits = 15`, `display_scientific_below = 1e-4`, `display_scientific_from = 1e16`, `uncertainty_digits = gum` (the GUM 1-or-2-figure rule; an integer forces a count as `@precision` does). `format_float`/`gum_round` read them once per call from the settings (thread-local scoped override for tests and witnesses). A **golden table** of formatted outputs (a few hundred values: magnitudes across 1e-300..1e300, the boundaries 1e-4/1e16, values with and without uncertainty, the GUM boundary cases 0.95/1.0/1.9/2.0 leading digits, negative zero, NaN, infinities) pinned **before** the change, unchanged at default. Witnesses: new battery cases `display.*` record the printed text of fixed values as `WitnessValue::Text` under the compiled default settings, and `verify --run` compares them; document that two frozen files with different display keys print differently by design. The dead settings (`default_output`, `auto_simplify`, `default_system`, `readable_representation`, `verbose`, `mkml_recursion_limit`, `[System] base_units`) are **not** wired here: the coverage table lists them as "accepted and ignored (an auditor must not assume they do something)", and the unfrozen reader/`phs conf status` warns when a frozen/unfrozen conf sets one (decide the exact warning).
8. **Smaller keys:** `monte_carlo_samples = 1000` (M1; `Quantity::new_scalar` reads it; Python passes `None` so the core decides), `max_while_iterations = 10000` (M3, same pattern as `max_loop_iterations`; **fixed at the compiled default for witnesses**, like the other ceilings), `asymmetric_shape = dimidiated` (M6, consulted where `ShapeKind::DEFAULT` is today: `moments.rs` ~83/93/112/402/426/490), `default_dof = inf` (M8: the nu of an uncertainty with no declared degrees of freedom).
9. **The coverage table `docs/conf_coverage.md` is built and tested, not just written:** one row per number class (every class A item of the audit, every class B item with its protection: engine pin and the witness ids that exercise it, class C items with owner phase, the environment/randomness/floating-point records of audit §6), a column "frozen by the file / pinned+witnessed / not frozen (owner, phase)", and a Rust test that (a) every catalog key named in the table exists in the shipped `physure.conf`, (b) every witness id named exists in `battery()`, (c) every `Setting` key the core knows appears in the table (so a new key cannot be added without saying what it covers).

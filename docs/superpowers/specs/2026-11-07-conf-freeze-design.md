# `phs conf`: freezing the whole configuration — design

**Status:** design approved section by section by the user on 2026-11-07; this document is the written spec awaiting their review.
**Scope of this spec:** the mechanism and its first four phases of work (§11). Each phase gets its own implementation plan.

## 1. Why

Some users run physure in strictly audited settings (factories, laboratories). They validate their calculations against **one** state of the software and its data, and changing that state needs a long process (paperwork, months of testing) that does not follow the release rhythm of this project. Today a library upgrade can change a result without anyone choosing it: a constant is revised, a unit definition is corrected, an algorithm is improved. For these users that is not an improvement, it is an unannounced alteration of validated calculations.

The atomic weights already have the answer in miniature: named, frozen editions, a fingerprint test, an edition report (`docs/atomic_weights.md`, §6). This spec generalises it to **everything that determines a result**, and adds the tooling to freeze, inspect, compare and update it deliberately:

```
phs conf            phs conf show      phs conf freeze     phs conf verify
phs conf diff       phs conf update    phs conf seal       phs conf history
```

The user's requirements, in their words (translated): it must not be limited to chemistry, it must cover **everything**; freezing with nothing configured must build the frozen file that holds the overrides; and every change must be deliberate and leave a trace.

## 2. What determines a result (three layers)

| Layer | What it is | How it is frozen |
|---|---|---|
| **Data** | `physure.conf` (settings, dimensions, prefixes, units, constants, categories, compatibility, atomic weights), unit-system files, and any number that today lives only in code | **Copied** into the frozen file and sealed. |
| **Engine** | The algorithms of the core: uncertainty propagation, Student-t quantiles, balancing, parsing… A data file cannot hold an algorithm. | **Identified and pinned** (version, commit, build, target, binary hash) with an enforcement policy, and **witnessed** by recorded reference calculations (§8). |
| **Environment** | OS, CPU architecture, thread count, and from Python the versions of Python, numpy and torch | **Recorded**; `verify` reports differences as warnings. |

Terminology used throughout: *layer* means one of these three; *source* means one stacked piece of configuration text (§3).

### What is not covered today (stated plainly, and kept current in `docs/conf_coverage.md`, Phase 4)

Verified in the code at the time of writing: the exchange rates of `physure.ext.currency` are literals in Python (`EUR = 1.08`, `MXN = 0.059`); the default number of Monte Carlo samples is a literal in the core (`physure-core/src/quantity.rs`, `samples.unwrap_or(1000)`); the unit systems `imperial.conf` and `international.conf` are read by Python only; the Python chemistry tables (`STANDARD_ENTHALPY_FORMATION`, `STANDARD_ENTROPY`) are literals. Phase 4 starts with a complete audit of code-resident numbers and migrates each into the catalog; until a number is migrated it is listed as **not frozen**. Nobody may be led to believe that something is covered when it is not.

**Closed in Phase 4** (plan `docs/superpowers/plans/2026-11-15-conf-freeze-phase-4b-data-migration.md`): the audit (`docs/superpowers/audits/2026-11-14-code-resident-numbers.md`) found 10 data items (class A), 25 engine items (B) and 13 binding-only items (C). The Monte Carlo sample count and seed, the `while` ceiling, the asymmetric shape, the default degrees of freedom and the display rules are `[Settings]` keys (`CORE_SETTING_KEYS`); the thermochemistry tables are catalog editions (`[Thermochemistry:legacy-python-1]`); the exchange rates are a shipped Python text (`currency.conf`), not frozen until Phase 5; `imperial.conf` and `international.conf` hold no number that affects a result. Everything not frozen is a row of `docs/conf_coverage.md` with its owner, and `physure-core/tests/conf_coverage.rs` keeps the table in step with the catalog, the core's keys and the battery.

## 3. Sources: how the configuration is built today

The effective configuration is not one file; it is a stack of sources applied in order, a later one overriding an earlier one:

1. the catalog embedded in the library (`physure-core/src/units/physure.conf`);
2. a unit system file, if used (Python: `systems/imperial.conf`…);
3. the `physure.conf` of the working directory (the core reads exactly this one; the CLI's `config.rs` looks in five places, but only for the language).

Different surfaces resolve this differently (the core reads only the working directory; Python adds system files). The mechanism needs **one definition of "the configuration in force"**, implemented once in the core and reused by every surface (§6).

A frozen file keeps the **sources as they were read, separately and in order**, instead of a merged result. Reasons: nothing is transcribed (a registry-to-text serialiser would have to be lossless for every unit kind, scale, offset, level and compatibility row, and any slip would alter a calculation); an auditor sees where a value comes from; loading is a replay.

## 4. The frozen file, `physure.frozen.conf`

The name is deliberately different from `physure.conf`: an older tool or another binding that reads the working directory's `physure.conf` leniently must never take a frozen file for a plain overlay and silently ignore its seal and engine pin.

It is **not** a plain conf. The first line is `#physure-frozen 1`. A header in INI syntax is followed by framed blocks whose text is kept verbatim:

```
#physure-frozen 1
[Freeze]
format = 1
created = 2026-11-07T14:03:11Z
content_sha256 = …
seal_sha256 = …

[Engine]
version = 0.3.1
commit = 9f2c1ab3d4e5f60718293a4b5c6d7e8f9a0b1c2d
profile = release
target = x86_64-pc-windows-msvc
features = html-viewer
rustc = rustc 1.97.1 (8bab26f4f 2026-07-14)
flags = opt-level=3;debug-assertions=off;panic=unwind;rustflags=<sha256>;target-features=<sha256>
binary_sha256 = …
policy = build

[Environment]
os = windows
arch = x86_64
family = windows
endian = little
pointer_width = 64
cpus = 16

[Witness]
builtin.units.foot_to_metre = 3fd381d7dbf487fd:0000000000000000:m
user.validation.1 = sha256:<64 hex>

[History.1]
time = 2026-11-07T14:03:11Z
action = freeze
engine = 0.3.1+9f2c1ab3d4e5
engine_sha256 = …
policy = build
pinned = 0.3.1+9f2c1ab3d4e5
actor = irvin@host
reason = initial freeze
old_content_sha256 =
new_content_sha256 = …
diff = …
prev_entry_sha256 =
entry_sha256 = …

@@ source 1 origin=embedded sha256=…
…the embedded catalog text…
@@ end source 1
@@ source 2 origin=overrides sha256=…
# Your overrides: same grammar as physure.conf. After editing, run `phs conf seal`.
@@ end source 2
@@ witness validation.1 sha256=…
…script text…
@@ end witness
```

* `source 2` is **always** the overrides block and is the one meant to be edited by hand. When `freeze` finds an existing `physure.conf`, its text becomes the content of `source 2`; when there is none, the block is created empty with a comment stating the grammar. Further sources (system files) follow it and are added by the bindings that use them (Phase 5).
* **Structure rules** (refused by the constructor, reported by the verifier, refused by the parser where they are syntactic): source 1 has origin `embedded` and source 2 has origin `overrides`, both always present; origins are unique; witness script names are unique; `[Witness]` has a key `user.<name>` for every script `<name>` and no `user.*` key without a script; `created` equals the time of the first history entry; the first entry is a `freeze` with empty `old_content_sha256` and `prev_entry_sha256`, every later entry is an `update` or a `seal` whose `old_content_sha256` is the previous entry's `new_content_sha256`; every reason is 1 to 500 characters. A section opened twice, a key repeated in a section, a number that is not written canonically (digits only, no sign, no leading zero) and a line starting with `@@ ` inside a block that is not that block's end marker are parse errors that name the line.
* Line endings are normalised to LF on write; reading accepts CRLF. A bare carriage return (one not followed by a line feed) is refused, in the file and in a source or script given to the library. Empty lines at the end of a block are not part of its text.
* The header sections follow the strict grammar of the conf (no inline comments; a bad line is an error). `policy` is one of `binary`, `build`, `release`, `record` (§7); from Python `[Environment]` also has `python`, `numpy` and `torch`.
* **`[Engine]` is read strictly** (`frozen::engine::read_engine`): the keys `version`, `commit`, `profile`, `target`, `features`, `rustc`, `flags` and `policy` are required, `binary_sha256` is optional, and **any other key is an error** (an unknown key in the block that sets the policy would be a knob nobody can see). Every value is validated: `version` non-empty `[0-9A-Za-z.+-]`; `commit` exactly 40 or 64 lowercase hexadecimal characters or the literal `unknown`; `profile` `[a-z0-9_-]+`; `target` `[A-Za-z0-9_.-]+`; `features` empty or sorted, unique, comma-separated `[a-z0-9-]+` names; `rustc` and `flags` one non-empty line without padding and without any control character or Unicode line/paragraph separator (U+2028, U+2029); `binary_sha256` a lowercase SHA-256. `verify` reads the block and also requires that it could have been recorded (`build` and `binary` need a known commit, `binary` needs `binary_sha256`, §7): a sealed file whose block cannot be read, or could not have been recorded, is a discrepancy, and such a file can be neither made nor resealed.
* `[Environment]` records `os`, `arch`, `family`, `endian`, `pointer_width` and `cpus` (`frozen::engine::environment_pairs`). It is informational, outside the seal, and no behaviour may ever depend on it.

### 4.1 Canonical form and hashes

* The **canonical text** of a source: lines trimmed at both ends, blank lines and lines starting with `#` or `;` dropped, joined with `\n`. Reformatting and comments do not change it; one digit does. This form is sound only because it is **defined by the core's reader** (`physure-core/src/units/conf.rs`, which trims every line and skips `#`/`;` lines in every section): two texts with the same canonical text are read identically by it. Sources are therefore replayed through the core reader only. Python's `configparser` reads an indented line as the continuation of the previous value, so two texts the seal treats as equal could mean different things to it: Phase 5 must not use it to replay a frozen source.
* `source_sha256` = SHA-256 of the canonical text.
* `content_sha256` = SHA-256 of, for each source in order, `origin\n` + `source_sha256\n`.
* **Witness scripts are hashed byte-exact**, never with the canonical form above (in PHS `;` ends a statement, indentation is significant and a string may span lines): `exact_sha256(text)` = SHA-256 of the script text after CRLF becomes LF and trailing newlines are removed, with no other change.
* `engine_sha256` and `witnesses_sha256` = SHA-256 of the canonical text of the block: its `key=value` lines sorted and joined with `\n` (keys are unique names without `=`, values are one line). The same `engine_sha256` is recorded in every history entry, for the block as it was at that entry (§5.3).
* `scripts_sha256` = SHA-256 of, for each witness script in file order, `<name>\n` + `exact_sha256(script)\n` (the empty string when there is none).
* `seal_sha256` = SHA-256 of exactly this text, each line ending with `\n`:

  ```
  physure-frozen-seal-1
  format:<format>
  created:<created>
  content:<content_sha256 recomputed from the source texts>
  engine:<engine_sha256>
  witnesses:<witnesses_sha256>
  scripts:<scripts_sha256>
  history:<entry_sha256 of the last history entry>
  ```

  Every part is a labelled fixed-length hash or a one-line scalar, so no pair, script or boundary can move from one part to another. The history is covered through its last entry: each entry's hash covers the previous entry's hash (§5.3). What is outside the seal is listed in §9.
* SHA-256 is implemented in the core (about 80 lines) and checked against the NIST test vectors: the core keeps its policy of no new dependencies.

## 5. Behaviour

### 5.1 Resolution: "the configuration in force"

In this order, implemented once in the core (`units::frozen`):

1. an explicit file: `--conf PATH` (CLI) or the argument of the API call;
2. the environment variable `PHYSURE_CONF=PATH`;
3. discovery: the nearest `physure.frozen.conf` found walking up from the working directory to the root of the file system (as git finds `.git`);
4. none: today's behaviour (embedded catalog plus the working directory's `physure.conf`) — **unless** `PHYSURE_REQUIRE_FROZEN=1`, which makes the absence of a frozen file an error (exit code 2): the audited setting fails closed.

**The rules as implemented (Phase 1c, `frozen::active`).** The host names the explicit file with `set_explicit_conf` (the CLI's `--conf`, Phase 2). An explicit path or `PHYSURE_CONF` that is empty, does not exist or is not a file is an error and never falls back to discovery or to the unfrozen catalog; a relative one is relative to the current directory. A file that resolves but is not a frozen file is an error of loading (§5.2). `PHYSURE_REQUIRE_FROZEN` must be unset, `0` or `1`: any other value (the empty string, `true`, ` 1`) is an error, so a typo cannot switch the audit mode off; a variable whose value is not Unicode is an error, never read as unset. Discovery passes over a directory named `physure.frozen.conf`, and a candidate that exists but cannot be examined (permission denied) is an error rather than "nothing found". Without a readable current directory (deleted, on Unix) the result is unfrozen, which is what the unfrozen catalog does without one, unless something needs the directory (a relative path, or `PHYSURE_REQUIRE_FROZEN=1`): then it is an error. On `wasm32-unknown-unknown` there is no file system, environment or current directory, and the result is always unfrozen.

**Cache.** `active()` caches per process under the inputs of resolution (the explicit path, the two variables, the current directory): discovery runs once per set of inputs, and each call checks only the stamp (length and modification time, taken from the handle that read the file) of the file in force, so an edited file is loaded again. A resolution error is not cached (a file created afterwards is seen); a load error is, under the stamp of the file that was read. The consequence is staleness, never a bypass: a frozen file created in a directory after the process resolved that directory to unfrozen is not seen until the inputs change or `reset_cache()` is called (`set_explicit_conf` and `set_engine_file` call it). The SHA-256 of the engine file is cached per (path, length, modification time).

**Activation; one process, one configuration.** Loading changes no process-wide state. The call of `active()` that installs a loaded file **activates** it: the process-wide settings go back to the library's compiled defaults and the file's `[Settings]` and `[Compatibility]` are applied, in one step under the cache lock (a setting the file does not mention takes its compiled default, never a value an earlier reading left). From then on the resolution is sticky: if it later gives another file or none (the current directory or the environment changed), the result is `ActiveError::ResolutionChanged` until `reset_cache()`. Paths are compared as text, so the same file reached through two spellings (relative and absolute, another case, a symbolic link) is `ResolutionChanged`, which fails closed. `reset_cache()` forgets everything cached (the merged working-directory `physure.conf` of §6 included) and, if a frozen file had been activated, restores the compiled defaults and then the embedded catalog's `[Settings]` and `[Compatibility]`. A request for the catalog on the thread that is loading a frozen file returns `ActiveError::Reentrant` instead of deadlocking (a defect if it happens: loading reads no catalog). The lock of the cache is never held while a caller's code runs.

**Fail closed.** Programs call `frozen::ensure_valid()` at start-up: it resolves, loads and activates, and its error has `exit_code()`: **1** integrity (the file cannot be read, is larger than 64 MiB, is not a frozen file, does not verify or does not replay; also `Reentrant`), **2** resolution (`ResolutionChanged` included), **3** engine. `phs` names its own executable as the engine file and calls `ensure_valid()` before **every** command, `--version` and `--help` included, printing `phs: refusing to run: <message>` and exiting with that code. **Phase 2 must exempt `phs conf status`, `verify` and `diff`** from this check, since they exist to inspect a file that may be broken or pinned to another engine (they load it with `LoadOptions { check_engine: false }` where asked). The fallible hooks (`try_with_conf_registry`, `try_build_registry_from_conf`, `build_registry_with`) return the error; the two infallible ones (`with_conf_registry`, `build_registry_from_conf`) panic with `physure: refusing to run: <error> (see `phs conf status`)` only as a backstop. `Parser::parse_expression`, `Quantity::new` and the chemistry functions use the fallible ones, so they return an ordinary error; `chemistry::atomic_weight` and `atomic_weight_edition` now return `PhysureResult`.

### 5.2 Loading a frozen file (sealed)

1. Parse the header and the blocks. Any malformed framing is an error.
2. Recompute every `source_sha256`, `content_sha256`, the history chain and `seal_sha256`. **Any mismatch is an error, never a warning**, and the message names the file, what was expected and what was found.
3. Check the engine against `[Engine]` according to `policy` (§7).
4. Build the registry **only** from the sources, replayed in order into an empty registry and read strictly (a bad line is an error). The `embedded` source is read with the trusted reader (the one entitled to define the shipped atomic-weight editions); every other source is read as untrusted user text. The catalog of the installed library and the working directory's `physure.conf` are **not read**; `status` warns if the latter exists. The replay is stricter than `extend_registry`: a `[Settings]` line that does not read (an unknown key other than those the core leaves to other bindings, a bad value, no `=`), a `[Compatibility]` row that does not read, a section name that is not one of a conf, a line before the first section (a byte-order mark included), a line without `=`, a `[Constants]` value that is not a finite number followed by a unit the registry reads, a name defined twice in one text, unit fields that would not be read, and a selected atomic-weight edition that no source defines are all problems. `[Settings]` and `[Compatibility]` of the sources are collected (later ones winning) and applied only at activation (§5.1), never by loading.

The order of the checks is: read (at most 64 MiB, the stamp from the same handle) → parse → `verify` (integrity) → read the engine block → check the engine under the file's policy → replay. The engine is checked before the replay, so a different engine is reported as such. `LoadOptions { check_engine: false }` exists for inspection (`status`, `verify` and `diff`, Phase 2, which inspect a file pinned to another engine without a flag and say so with exit 3); evaluation always checks the engine.

An upgrade of the library therefore cannot change a value: the sources do not come from the library.

### 5.3 The history

Every `freeze`, `update` and `seal` appends one entry; entries are chained:

```
n | utc time | action (freeze|update|seal) | engine version+commit | engine_sha256 | policy | pinned | actor
  | reason | old content_sha256 | new content_sha256 | diff summary (counts per section) | previous entry sha256
```

and the entry's own SHA-256 is recorded with it: `entry_sha256` = SHA-256 of `n=<n>\ntime=<time>\naction=<action>\nengine=<engine>\nengine_sha256=<engine_sha256>\npolicy=<policy>\npinned=<pinned>\nactor=<actor>\nreason=<reason>\nold_content_sha256=<…>\nnew_content_sha256=<…>\ndiff=<diff>\nprev_entry_sha256=<…>` (every value one line, no final newline). Deleting, reordering or editing an entry breaks the chain.

`engine` is the short form (`version+` twelve characters of the commit) of the engine that performed the action: text supplied by the caller and recorded as given, not checked (Phase 1c fills it mechanically from `EngineIdentity::current().short()`). The three fields that say what the file pins are derived by the library from the `[Engine]` block at the moment of the entry, never given by the caller: `engine_sha256`, the SHA-256 of the canonical block (§4.1); `policy`, the block's policy; and `pinned`, the short form of the identity the block records. A change of the engine block, weakening the policy included, therefore shows in the log mechanically as a different `policy`, `pinned` or `engine_sha256` between consecutive entries, whatever the `reason` and the `diff` say. A `policy` that is not one of the four, or an empty `pinned`, is a parse error that names the line. `verify` requires the last entry's `engine_sha256`, `policy` and `pinned` to agree with the current block: a block changed without a reseal is reported, and so is a file from which the entry that changed the block was removed, or whose last entry's `engine_sha256`, `policy` or `pinned` was rewritten, even when every other hash and the seal were recomputed. `actor` is `$USER`/`$USERNAME` and the host name; it is **informational, not authenticated**.

### 5.4 Commands

All accept `--conf PATH` and `--json`. Exit codes: **0** ok (or identical, for `diff`); **1** discrepancy (broken seal, modified file, differences, witness mismatch); **2** misuse, or a required frozen file is missing; **3** engine differs from the validated one. Every error names the file, what was expected and what was found; nothing falls back silently to "not frozen".

| Command | Behaviour |
|---|---|
| `phs conf` / `status` | Which configuration is in force and why (flag, variable, discovery, none); frozen or not; seal and verification; creation date and engine; number of history entries; atomic-weight edition (`atomic_weight_edition()`); warnings: an ignored `physure.conf`, a missing required frozen file, environment differences. |
| `show [KEY]` | The effective configuration as `section.key = value`, whole, one section, or one key (`constants.molar_gas_constant`). `--origin` adds the source each value comes from. |
| `freeze --reason "…" [--out PATH] [--witness FILE.phs]…` | Writes `physure.frozen.conf` from what is in force now; refuses to overwrite an existing frozen file (that is `update`). With **no** `physure.conf` it still writes the file, with `source 1` = the embedded catalog and an empty `source 2`. Records the engine (policy `build`), the environment and the witnesses (§8), and prints the seal, reminding the user to record it outside. **As built (Phase 3):** the witnesses (the built-in battery and each `--witness` script, named after its file stem, repeatable) are evaluated under the file about to be written (a *probe*: the new file without witnesses, sealed, written to the temporary directory and loaded as the explicit configuration), never under the unfrozen catalog; `AlreadyFrozen`, `WouldOverwrite`, the policy and the overrides are refused before anything is evaluated; a script that cannot be read, named or evaluated cleanly, and a built-in case that panics or hits a limit, refuse with exit 2 and nothing is written. One history entry, whose `diff` ends with `; witnesses: N built-in, M user`. |
| `verify [FILE] [--expect SHA] [--run]` | Recomputes seal, hashes and chain; compares with `--expect` (a seal kept in the user's quality system, §9); reports environment differences; with `--run` re-executes the witnesses under the frozen configuration. **As built (Phase 3):** `--run [--timeout-ms N]` evaluates under FILE (made the explicit configuration of the process), nothing when the file does not verify (exit 1), pins another engine (exit 3) or records no `builtin.*` witness (exit 1: "nothing is witnessed", with the hint `phs conf update --reason "..."`); exit 0 when every recorded witness matches (new cases are informational), 1 when one differs, is missing or errs. JSON: `witnesses` (`checked`, `match`, `differs`, `missing`, `new`, `errors`), `witnesses_ok`. |
| `diff [A] [B]` | Default: A = the frozen file in force, B = what the installed build would use unfrozen. Data differences by section (added, removed, changed with old → new), then engine and environment differences, with counts. `--json` has a stable schema. Exit 0 identical, 1 different (in data or engine: environment differences are listed and informational, amended after the review of Phase 2). |
| `update --reason "…" [--engine-policy P] [--accept-witness-changes all\|KEY[,KEY...]] [--yes]` | Adopt what the installed build brings (new catalog, new engine). Shows the `diff`, does nothing if it is empty, asks for confirmation (`--yes` in scripts), writes atomically (temporary file and rename) keeping the overrides, appends a history entry. **As built (Phase 3):** "empty" means the canonical catalog and the engine block are this build's **and** the file records at least one `builtin.*` witness: a file without the battery (every Phase 2 file) has something to do, its summary ends `witnesses: battery not recorded`, and the battery is recorded without the flag (every case is new). Nothing to do evaluates nothing (decision S9). Otherwise the preview ends with the witnesses as recorded against evaluated under a probe of the planned file; a recorded witness that differs or is missing refuses (**exit 1**, nothing written, JSON `"refused": "witnesses"`) unless `--accept-witness-changes` names it (or `all`; a key that did not change is exit 2), a witness that cannot be evaluated refuses whatever the flag, new cases are recorded without it; the history `diff` then ends with `witnesses: N changed, M new, K missing; changed: ...; missing: ...; old [Witness] sha256 <12 hex>`. Before writing, the stamp and the SHA-256 of the bytes read are compared with the file on disk. |
| `seal --reason "…" [--yes]` | Accept the user's hand edit of the `overrides` block (an edit of any other part is refused, with what `verify` found): shows (a) the full canonical text of the new `overrides` and (b) what they contribute to the catalog, the entry difference between the catalog the sources build without them and with them (amended in Phase 2: the file keeps only the marker of the previously sealed overrides, not their text, so a diff against the last sealed state cannot be made from the file alone; a copy of the previously sealed file can be given to `diff`), asks for confirmation, re-seals, appends an entry. Until then `verify` says "modified since the last seal" and what changed. This is the **only** way to change overrides: no `set`/`unset`. **As built (Phase 3):** `seal --reason "…" [--accept-witness-changes all\|KEY[,KEY...]] [--yes]`. The draft exists only after the proof that only source 2 changed; then the engine of the file as read is checked (exit 3 for another engine, before anything is evaluated, since the probe carries the same `[Engine]` block); then the witnesses are evaluated under the probe and the drift rule of `update` applies (an override a witness depends on, such as `molar_gas_constant`, refuses with exit 1 until accepted). |
| `history` | Prints the log. |

There is no `unfreeze`: deleting the file does it, and with `PHYSURE_REQUIRE_FROZEN=1` that fails closed. `phs upgrade` never touches a frozen file; when one is in force it ends by suggesting `phs conf diff`.

`show` and `diff` need a deterministic **entry listing** of a registry (`section`, `key`, canonical value text) for every kind of definition; the origin of an entry is found by listing after each source and attributing the change to it.

## 6. Where it lives

* Core (`physure-core/src/frozen/`: `sha256`, `canonical`, `model`, `seal`, `time` in Phase 1a; `engine`, the engine identity and its policies, in 1b; `active` (resolution, the cache, activation), `load` (sealed loading) and `ops` (the `freeze`, `update` and `seal` operations and the atomic writer) in 1c): file model, canonical form, hashes, verification, resolution, sealed loading, the entry listing (1d), the engine identity.
* **What a frozen configuration governs (Phase 1c).** `build_registry_from_conf`, `with_conf_registry` and their fallible `try_` forms, `build_registry_with("")` (a non-empty `extra` is refused while a frozen file is in force: extra definitions belong in the overrides block), and everything that goes through them: unit parsing (`Parser::parse_expression`, `Quantity::new`), the chemistry functions, PHS (it reads the catalog in force on every use; the process-wide copy it kept was removed), the CLI, the language server, and the `physure.units` registry and `unit_facts` of Python. **What it does not govern, by design** (the host owns these registries): a scope opened with `with_catalog` (a host that scopes an unfrozen registry, as Java's PHS evaluation does, is not governed inside it), `UnitRegistry::build_default_si` and `build_default_imperial`, and the public `extend_registry`, `parse_physure_conf`, `load_embedded_catalog` and `DEFAULT_PHYSURE_CONF`.
* **Bindings that read the embedded catalog themselves refuse until Phase 5** (`frozen::refuse_unwired`: an ordinary error that names the file in force and says what to do, never a panic): Python's `default_conf()`, from which `UnitSystem` is built with `configparser` (a `RuntimeError`; its test, `physure-python/tests/test_frozen_refused.py`, was written but not run, since building the extension would touch a shared virtual environment), and Java's `default_catalog`, checked on every call. WebAssembly is not affected: on `wasm32-unknown-unknown` the resolution is always unfrozen. A frozen file that resolves but cannot be used is a refusal too.
* The language server calls `ensure_valid()` in `initialize` and sends its error with `window/showMessage` from `initialized` (tower-lsp drops a message sent from `initialize`), and as a diagnostic on every document; it keeps running.
* **The unfrozen catalog with a working-directory `physure.conf`** is the embedded catalog merged with that file, built once per version of the file and cached with the configuration in force (Phase 1c; before, it was rebuilt on every call, which made a PHS script of 2000 literals about seven times slower with a one-line `physure.conf`). The key is the absolute path, the length and the modification time from the handle that read it; a call costs one `stat`. While the modification time is less than two seconds older than the reading, the text is read again and compared on each call, so an edit of the same length within the file system's time granularity is seen; a file edited with its length and an old modification time restored by hand is not seen until either changes, the current directory changes or `reset_cache()`. The file's `[Settings]` and `[Compatibility]` are applied when the merge is built or rebuilt, no longer on every call: a setting changed by the program afterwards is no longer overwritten by the next read of the catalog.
* Build metadata: `physure-core/build.rs` **always** emits the commit, profile, target, compiler (`rustc -V`) and build flags under internal names (`PHYSURE_ENGINE_*`) that the library reads with `env!`; the library never reads a variable a user can set, so a value the build script rejected cannot reach the binary. `features` is computed in the code: the sorted named features of `physure-core` that are enabled, without `default`. `flags` is `opt-level=<n>;debug-assertions=<on|off>;panic=<unwind|abort>;rustflags=<sha256 of CARGO_ENCODED_RUSTFLAGS>;target-features=<sha256 of CARGO_CFG_TARGET_FEATURE>`. A fact that cannot be determined (`PROFILE`, `TARGET`, `OPT_LEVEL`, `CARGO_CFG_PANIC`, the output of `rustc -V`) stops the build with a message instead of becoming `unknown`, since two such values would compare equal under `build`.
* **The commit is the builder's claim, and git is not consulted** (decision of 2026-11-08, after the reviews of Phases 1b and 1c kept finding ways for a build to claim a commit it did not compile: a pure function in `build_support/commit.rs`, unit-tested). The variable `PHYSURE_BUILD_COMMIT` is the only input: a full lowercase hash (exactly 40 or 64 hexadecimal characters) is recorded as the commit; unset gives `unknown` (silently, as in every development build); anything else gives `unknown` with a cargo warning, so a shortened or mistyped hash cannot pass for a commit. `unknown` never equals anything. Why not git: a build cannot prove that the files it compiles are those of a commit (a tracked file can change between any check and rustc reading it, measured), and a probing build script has to defeat `git replace`, attribute filters, `assume-unchanged`, hooks and worktrees, all of which the earlier reviews found. What pins behaviour is the `binary` policy (the hash of the artefact) and the witnesses of Phase 3; the commit tells an auditor which source the pipeline says it built. The release workflows set `PHYSURE_BUILD_COMMIT` to `github.sha`. `cargo:rerun-if-changed` watches only `build.rs` and `build_support`, and the three variables.
* **Scope of `commit`:** it names the revision the builder says it built; the code that evaluates includes `physure-core`, `physure-script` (the PHS interpreter), `physure-cli` and the bindings. `build` therefore pins the builder's claim and the build facts (profile, target, features, rustc, flags), not the whole evaluating engine; only `binary` pins the artefact.
* A build whose commit is `unknown` cannot record the policy `build` (§7): it compares the commit and `unknown` equals nothing. `binary`, `release` and `record` need no commit (decision of 2026-11-13; the earlier rule for `binary` only served traceability, which the builder's claim does not prove anyway). Without `--engine-policy`, `freeze` uses `build` when the build names its commit and `binary` otherwise (`EnginePolicy::recommended_for`).
* CLI (`physure-cli/src/conf.rs`): the eight commands over the core API.
* Python, WebAssembly and Java call the same resolution in Phase 5 (until then they refuse, see above). Python reads its configuration with `configparser`, adds system files and its own working-directory file, so wiring it is its own task.

## 7. Engine pinning

`[Engine] policy` — set by `freeze --engine-policy`, default `build` when the build names its commit and `binary` otherwise, changed only through `update`/`seal` (so it is in the history: each entry records the block's `policy`, the `pinned` identity and the block's `engine_sha256`, §5.3):

| Policy | The running engine must have |
|---|---|
| `binary` | the same file that contains the engine (SHA-256) |
| `build` (default) | the same version, commit, profile, target, features, compiler (`rustc`) and build flags (`flags`) |
| `release` | the same version |
| `record` | nothing (the identity is recorded, never enforced) |

A mismatch is an error (exit 3) **when evaluating**. `status`, `verify` and `diff` inspect the file under a different build all the same (they exit 3 to say the engine differs; no flag is needed, and the `--allow-engine-mismatch` of Phase 2, which changed nothing, was removed in Phase 3). There is no override for evaluating, and `verify --run` evaluates nothing under an engine the file does not pin: to run on another engine, `update` (which records the change, with its reason, in the history).

The comparison (`frozen::engine::check`) reports every field that differs, and every doubt is a difference:

* **`unknown` never equals anything**, not even another `unknown`: under `build`, a recorded or running commit that is `unknown` is a mismatch.
* `build` cannot be **recorded** for an identity whose commit is `unknown` (`binary` can: it compares the hash of the executable, decision of 2026-11-13; `freezable`, enforced when the block is built by `engine_pairs` and again by `verify`, so a block written by hand that could not have been recorded is a discrepancy and can be neither made nor resealed; the same holds for `binary` without `binary_sha256`). This is a design choice: a binary hash alone does not tell an auditor which source it came from. `release` and `record` can always be recorded.
* `binary` needs a recorded `binary_sha256`; without one it is a mismatch, and the running file is hashed only under `binary` and only when a hash is recorded. `binary` attests **the file at its path at check time**, not the image in memory (on Windows a running executable can be renamed and replaced). The caller must hash the file that contains this engine: for the CLI the executable, for a Python extension module the module (not the interpreter), for the Java library the library. The core deliberately has no "hash my own executable" convenience, which in a binding would pin the interpreter. **Which file is hashed is told by the host** with `frozen::set_engine_file` (`phs` names its own executable); if the host named none, a `binary` file does not load and the message says that the host did not say which file contains the engine. The core has no default.
* Under `build`, a recorded `binary_sha256` is informational and ignored.

**Trust boundary.** Whoever controls the build environment (the variable `PHYSURE_BUILD_COMMIT`, `PATH`, `RUSTFLAGS`, the toolchain) controls every field of the identity. `build` protects against accidents, not against a malicious builder; `binary` is the only policy whose evidence is the artefact itself.

**Scope of `commit`.** The commit is the builder's claim (§6): the variable `PHYSURE_BUILD_COMMIT` at build time, recorded as given when it is a full lowercase hash and `unknown` otherwise; git is not consulted and no tree is checked for edits. It names the revision the builder says it built, and proves nothing about the files that were compiled. The code that evaluates includes `physure-core`, `physure-script` (the PHS interpreter), `physure-cli` and the bindings, while the build facts (profile, target, features, rustc, flags) are those of `physure-core`'s build. `build` therefore pins the claim and those facts, **not the whole evaluating engine**; only `binary` pins the artefact.

**What the policies do not prove.** Not visible to a build script and therefore not pinned by `build`: `overflow-checks`, `lto`, `codegen-units`; the versions of the dependencies when `physure` is built inside someone else's workspace (their `Cargo.lock` decides); dynamically linked libraries (libm, the C runtime, the interpreter, numpy, torch). Not seen by the build script either: extra arguments given to the compiler after `--` in `cargo rustc`; `RUSTC_WRAPPER`; dependency overrides (`paths` and `[patch]` through `--config` or `~/.cargo`, source replacement, vendoring); custom profiles, which report `PROFILE` as `debug` or `release`. Nothing detects an edited tree: the commit is the builder's claim (git is not consulted, so neither a dirty tree nor a build from a copy of the crate inside another repository is noticed; a build without `PHYSURE_BUILD_COMMIT` records `unknown`). `release` accepts development builds that share a release's version number (between releases the version is not bumped). The witnesses (§8) are how a difference in what is not pinned is detected.

## 8. Witnesses

A witness is a reference calculation whose result is stored bit for bit and recomputed by `verify --run` under the frozen configuration. It catches what an engine pin cannot: the same binary on a different CPU or C library giving different last digits, and a change that the version string does not reflect.

* **Built-in battery** (about 40 cases; the list is part of the plan of Phase 3): unit conversions including affine and logarithmic units, uncertainty propagation in each mode with a fixed seed, the Welch–Satterthwaite example of the GUM (H.1), Student-t quantiles at several ν, molar masses, reaction balancing, Arrhenius, the gas constant read from the catalog. Each stores the mean and the standard uncertainty as IEEE-754 bit patterns and the unit text.
* **User witnesses:** `freeze --witness validation.phs`. The script is embedded in the frozen file (it is self-contained), evaluated with the same machinery as `phs eval` (JSON), and the canonical result is hashed. `verify --run` re-evaluates the embedded text.

**What was built in Phase 3** (plan `docs/superpowers/plans/2026-11-13-conf-freeze-phase-3-witnesses.md`, with the corrections of its adversarial review), against the design above:

* **Ids are versioned.** `builtin.<id>` with `<area>.<what>` in `[a-z0-9_.-]`; a release may add cases and never changes what an id computes. A recorded case the running build lacks is *missing* (a discrepancy), a running case the file lacks is *new* (informational, recorded by the next `update` or `seal` without a flag). The battery has **47** cases: 12 `units.*` (linear, affine `degC`/`degF`, logarithmic `dB` and `pH`), 6 `const.*`, 11 `unc.*` (each propagation mode pinned with a thread-local scope; Monte Carlo seed 1; GUM H.1 as `unc.gum_h1_uc`, `unc.gum_h1_nu_eff` and `unc.expanded_k_p95`, from the six-contribution linear budget, since the engine cannot express the product terms of the Guide's model; G.4.1 as `unc.welch_satterthwaite_g41`), 8 `stat.*` (Student-t), 10 `chem.*`. Each is checked in `physure-core/tests/battery_reference.rs` against a reference that does not come from the engine (NIST SP 811, the SI Brochure, CODATA 2022, the NIST/SEMATECH Student-t table, JCGM 100:2008 H.1 and G.4.1, CIAAW 2024).
* **Value formats** (each prefix is a prefix of the whole value): `<mean bits>:<u bits>:<unit>` (16 lowercase hex digits each, the unit text as printed, split at the first two colons), `text=<one line>` (a balancing, canonical: integer coefficients, input order), `failed=<one line>` (a case that legitimately errs under the configuration, recorded and compared like any value; only a panic or a limit is an error that refuses `freeze`), `sha256:<64 hex>` (user witnesses only). `verify` reports a key or value outside these forms as `Problem::WitnessEntry`.
* **User witnesses** are named after the file stem (the alphabet of names), normalised (CRLF to LF, trailing newlines trimmed) and the normalised text is what is evaluated; seed 0, the sandbox of `Limits::sandboxed`; the recorded value is the SHA-256 of `physure_script::report::canonical_witness` (format `phs-witness-1`: `ok`, per result item the line, name, kind, bit patterns of value and uncertainty, unit and dimension, and the error codes only), not of the JSON report as first designed: the codes and bits are what a result is, a message's wording is not.
* **Evaluation context: a probe and a draft.** `ops` was split into `prepare_freeze` / `prepare_update` / `prepare_seal` (one read of the file: a `Draft` with the file as read, its stamp, the SHA-256 of its bytes and the summary), `Draft::probe` (the new file sealed with the recorded witnesses, validated, written by the CLI to the temporary directory and loaded as the explicit configuration while evaluating, then removed on every path) and `finish` (sets `[Witness]` and seals **once**, so the history gains exactly one entry whose `diff` already holds the witness part). `freeze`, `plan_update` and `plan_seal` are the same steps finished with the recorded witnesses (Phase 2 behaviour). The core decides no policy: the CLI compares, applies `--accept-witness-changes` and passes the re-recorded witnesses (`rerecord`) to `finish`.
* **One order everywhere:** the battery in id order, then the user scripts in file order.

## 9. Security model and limits (to be stated in the user documentation)

* A hash detects that a file changed; it does **not** show who wrote it: whoever edits the file can recompute the seal. For authenticity, record the seal outside the file (`freeze` prints it; `verify --expect` compares). Cryptographic signing with a key is a possible later improvement and is out of scope.
* **What is outside the seal**, exactly: the `[Environment]` block, and formatting that carries no data: comment and blank lines and the whitespace around keys and values in the header, the order of the keys in a header section and of the sections, empty lines between and at the end of blocks, line endings, and in a source whatever its canonical form drops (comment lines, blank lines, indentation and trailing whitespace, §4.1). Nothing else: the format, `created`, the content of every source and its origin and position, `[Engine]`, `[Witness]`, every witness script byte for byte with its name and position, and every history entry are sealed.
* `actor` in the history is informational.
* Environment differences are warnings, not errors: bit-for-bit reproducibility across machines is not promised, and the witnesses are how a difference is detected.
* What is frozen is data; algorithms are identified, pinned and witnessed, not preserved. To reproduce a result years later, keep the binary named by `[Engine]`.
* The engine pin has the limits of §7, to be stated in the audit documentation: the identity is only as trustworthy as the build environment that produced it (`build` protects against accidents, not a malicious builder; `binary` is the only policy whose evidence is the artefact); **`commit` is the builder's claim** (`PHYSURE_BUILD_COMMIT`; git is not consulted), so `build` pins that claim and the core's build facts, not the files compiled and not `physure-script`, the CLI or the bindings that also evaluate; `overflow-checks`, `lto`, `codegen-units`, a consumer's lockfile, dynamically linked libraries, compiler arguments after `--` in `cargo rustc`, `RUSTC_WRAPPER`, dependency overrides and custom profiles are not pinned; an edited tree is not detected; `release` accepts development builds sharing a version number; `binary` attests the file at its path when checked.
* The coverage table (`docs/conf_coverage.md`) is part of the guarantee: it says what is and is not frozen.
* **`verify --run` executes the scripts embedded in a file**, which may come from someone else (Phase 3, correction C3). They are bounded by the sandbox of the interpreter (no file is read, no module from disk, no native plugin, one thread, a bounded call depth, native stack and output), by loop-iteration and pipeline-step ceilings **fixed** at the compiled defaults (1 000 000 and 1 000) and opened on the evaluating thread, so the file's `[Settings]` cannot raise them, and by a wall-clock deadline (60 s per script by default, `--timeout-ms`) with a watchdog after it. A panic or a limit is that witness's error, never a difference; after a script that does not stop, the remaining ones are not run and the process ends after reporting. **There is no memory cap** (§13, Phase 3 residual 1). The battery is the library's own code and runs unbounded by the deadline.
* Witnesses sample behaviour: passing them is not a proof that the rest of the library is correct or unchanged, and a user witness's hash shows only that its result changed.

## 10. Testing

* SHA-256 against the NIST vectors; canonical form: comments and whitespace do not change it, one digit does.
* Tampering: editing a value, deleting a source, editing, deleting and reordering history entries, changing the recorded engine — each must break the seal and name what.
* Resolution and precedence: walking up, `PHYSURE_CONF`, `--conf`, `PHYSURE_REQUIRE_FROZEN`, a bad explicit path.
* A working-directory `physure.conf` is ignored while a frozen file is in force, and `status` says so.
* Engine policy matrix (four policies × matching/mismatching) and exit codes.
* Witnesses: altering a stored result is detected by `verify --run`.
* The sealed registry equals the registry built from the same sources unfrozen (differential test on the whole entry listing).
* CLI integration tests run the real `phs` and assert output and exit codes; documentation examples are executable (as for `docs/atomic_weights.md`).

## 11. Phases

Each is its own plan and is useful alone.

1. **Core:** SHA-256, canonical form, file model, history chain, resolution, sealed loading, engine identity and policies, entry listing.
2. **CLI:** the eight commands, JSON output, exit codes, `phs upgrade` hint.
3. **Witnesses:** the built-in battery, user witnesses, `verify --run`.
4. **Data migration:** audit of code-resident numbers (currency, Monte Carlo defaults, Python chemistry tables, others the audit finds); each moves into the catalog; `docs/conf_coverage.md`.
5. **Bindings:** Python, WebAssembly and Java honour the frozen file and report their environment (Python, numpy, torch versions); system files become sources.

## 12. Out of scope

Cryptographic signing; `diff --impact "H2O,CO2"` (numeric effect of a change on named molar masses; it can be added without changing anything above); anything about the user's own scripts beyond witnesses; freezing the versions of Python packages (recorded, not enforced).

## 13. Risks and open points

* The registry replay must reproduce the unfrozen registry exactly (the differential test of §10 guards it).
* Verification cost: a frozen file embeds the whole catalog (~900 lines); the SHA-256 of that is microseconds-to-milliseconds, cached per process.
* `[Settings]` are process-wide in the core: a frozen file applies them when it is activated (§5.1), over the compiled defaults. **Rule for future settings:** a setting a later library adds and a frozen file does not mention takes its compiled default, so a new setting's compiled default must reproduce the previous behaviour. Thread-local overrides (`settings::scoped`, the angle-mode guard, `with_seed`) and a host's own propagation mode are choices of the host, outside the freeze. Settings and the embedded catalog may already have been applied before a frozen file is activated; the activation overwrites every setting, and `ensure_valid()` at start-up activates early.
* A binary hash for a Python wheel means the extension module file; its definition is settled in Phase 5.
* The size of Phase 4 is unknown until its audit finds how many code-resident numbers exist; it must not block Phases 1–3. **Closed in Phase 4:** the audit (2026-11-14) counted 10 A, 25 B, 13 C and 9 D items; A1-A4, A6, A7, A9 and A10 moved (M1-M8, commits `429cf6a`..`44de88a`), A5 and A8 (M9, M10) were deferred to Phase 5 by the owner, the B items stay in the engine (pinned, witnessed where a witness exists), the C items are Phase 5's.

  6. Python and Java refuse while a frozen file is in force instead of honouring it, until **Phase 5**; the Python test of the refusal was written but not run in Phase 1c.
  7. The working-directory `physure.conf` merge (§6) trusts its stamp once the file's modification time is two seconds older than the reading; a hand edit that restores both length and an old modification time is not seen until `reset_cache()` or a change of directory.
  8. **Fixed after the review of Phase 1c** (each measured before and after): a dangling link, or a directory, named `physure.frozen.conf` was passed over by discovery and the process ran unfrozen (now `ResolveError::Unreadable`); activation passed through the compiled defaults before storing the file's values, so a thread reading during a reload saw a default (33 440 of 516 million reads in the probe; now `ProcessSettings::activate` stores each value once); a sealed file with thousands of sources made loading take minutes, since each source is replayed over a copy of the registry (at most `MAX_SOURCES` = 256).
  9. **Withdrawn on 2026-11-08** together with the git check it was about (a build could claim a clean `HEAD` while compiling a file edited after the check): the commit is now declared to be the builder's claim.
  10. The file in force can change within one process: the path is fixed after the first resolution (`ResolutionChanged`), but a valid sealed file that replaces the content at that path is re-verified and re-activated when its stamp changes. A long computation or the language server can therefore see two catalogs in sequence. Each state is a verified one, never a mixture of files. **Phase 2 documentation**; a process that must not change catalogs restarts. **Closed in Phase 2 by documentation** (the user guide `docs/conf_freeze.md`, §6).
  11. The language server discovers `physure.frozen.conf` from its own working directory, not from the workspace the editor opens, and one server cannot serve two projects with different frozen files. **Phase 5** (workspace folders).
  12. The Java binding refuses through `refuse_unwired` when a handle is created; a registry created before a frozen file came into force keeps being used. The JVM cannot change its own working directory or environment, so it is not reachable in practice. **Phase 5.**
  13. A `binary` pin hashes the file `current_exe` names (cached by path, length and modification time), not the code that is running: on Windows a running executable replaced by rename names the new file. **Phase 5**, with the per-binding file of Phase 1b residual 2.
  14. `plan_update` / `plan_seal` followed by `write_atomic(replace)` has no compare-and-swap: a hand edit made between the plan and the write is overwritten (the result still verifies). **Phase 2**: write only if the file's stamp is the one the plan read. **Built in Phase 2:** `UpdatePlan` and `SealPlan` carry the stamp of the read they were made from; just before `write_atomic` the CLI takes the file's length and modification time again and refuses with exit 1 ("changed since it was read; nothing written") if either moved. Its limits are Phase 2 residual 1 below.
  15. A transient error while opening the file (a sharing violation) stays cached under the unchanged stamp, so a long-running process refuses until the file changes or `reset_cache()`. It fails closed. **Phase 2** (`phs conf verify` retries). **Closed in Phase 2 by reasoning:** `phs` is a single-shot process that resolves and reads the file afresh on every run, so running `phs conf verify` again is the retry; the long-running case is the language server's, which is Phase 5's (residual 11).
* **Residual risks left by Phase 2** (the `phs conf` commands; each one has an owner):
  1. The compare-and-swap of `update` and `seal` (1c-14) compares the stamp (length and modification time), not the content, and a short window remains between that check and the rename: an edit made in that window, or one that restores both the length and the modification time, is overwritten (the result still verifies; the other edit is lost). Accepted, of the same kind as 1c-7; re-reading and hashing the content before the write would narrow the window but not close it without a lock.
  2. **Fixed after the review of Phase 2:** with `--json` and without `--yes`, `update` and `seal` asked on the terminal before the preview was visible. With `--json` they now never ask: without `--yes` they refuse with exit 2 and the preview inside the document.
  3. The values `show` and `diff` print are the entry values of Phase 1d, which render some kinds in Rust's debug form (`RationalUnit { ... }`, `None None`), and a unit's value includes an internal `id` that is not stable across builds. Output saved from one build is therefore not comparable with output from another (the guide says to compare the files with `phs conf diff` instead), and the value text is not a stable format even though the `--json` field names are. **Phase 5**, when the bindings reuse the report types: a stable, build-independent value text.
  4. `--allow-engine-mismatch` is accepted by `status`, `verify` and `diff` but changes nothing: inspection never loads with the engine check, and the exit code stays 3 (decision S3). Harmless and documented, but a flag that does nothing invites a reader to think it does something. **Phase 3** gives it a meaning for `verify --run` (witnesses under another engine) or removes it. **Closed in Phase 3:** removed; `status`, `verify` and `diff` refuse it as an unknown flag (exit 2), and `verify --run` evaluates nothing under another engine (exit 3: a result under an engine the file does not pin proves nothing).
  5. `phs upgrade` is refused by the pre-command check while the file in force is broken or pinned to another engine (only `phs conf` is exempt), so a site that replaced `phs` by hand cannot use `phs upgrade` until it runs `phs conf update`. It fails closed. Left as is.
  6. **Coarse modification times.** The compare-and-swap of residual 1 trusts length and modification time. On file systems whose modification time is coarse (FAT and exFAT: two seconds; some SMB shares), an edit of the same length made within that granularity after the plan read the file is not seen and is overwritten. Accepted; **the cheap fix is noted for a follow-up**: keep the SHA-256 of the bytes the plan read and compare it with a hash of the bytes re-read just before the write (it narrows the window to the rename, as residual 1 says, without a lock). Owner: the next change to `update`/`seal`. **Built in Phase 3** (correction C11): the plan keeps the SHA-256 of the bytes it parsed, and just before the write the CLI compares it with the SHA-256 of the bytes on disk as well as the stamp, so an edit of the same length that keeps the modification time is refused (exit 1, nothing written). The window between that check and the rename (residual 1) remains.
  7. **A symlinked frozen file is replaced by a regular file.** `update` and `seal` write through a temporary file renamed over the path, so a `physure.frozen.conf` that is a symbolic link becomes a regular file holding the new content, and the link's target keeps the old one. Accepted and documented (the guide, §4.8); owner: the next change to `write_atomic` (resolve the link and write beside its target, or refuse a link).
  8. **`show --origin` marks a restated value only for some kinds.** A restatement (`embedded (restated by overrides)`: the overrides set a value to what it already was) is recognised by a `key = value` line of the overrides under the matching section, so it is marked only on the entry whose `section.key` that line names; the derived entries the same line restates (`constant_meta`, the alias names of a unit) keep the earlier origin without the mark. Accepted (informational); owner: Phase 5, with the stable value text of residual 3.
  9. **`overrides_contribution` is exact only for files of two sources.** What `seal` shows as the contribution of the overrides is the catalog after source 2 against after source 1; a further source (none is made today) is not attributed, and its redefinition of an entry the overrides set is not reflected. Accepted while `freeze` makes two sources; owner: whichever phase adds a source (Phase 5, system files as sources).
  10. **Fixed after the review of Phase 2** (each reproduced against the real binary, each with a test): `seal` re-sealed overrides under an engine the file does not pin (now exit 3, naming `update`); `diff` exited 1 when only `[Environment]` differed (now informational, `environment_identical` in JSON); the engine state of a file that does not verify could read "matches" (now not checked); unfrozen `status` called an ignored `physure.conf` an overlay (now it reports the runtime's reading and warnings); a reason could hold control characters and text output echoed file strings raw (now refused, and text output escapes them); `--help --json` printed text and `show | head` panicked on the broken pipe; a FILE beside `--conf` silently ignored `--conf` (now exit 2).
* **Residual risks left by Phase 3** (witnesses; each one has an owner):
  1. **No memory cap in `verify --run`.** The sandbox bounds time, loop iterations, pipeline steps, call depth, native stack and output, not memory: an embedded script can allocate until the machine refuses. The guide says to run `--run` on a file from an untrusted source in a constrained environment. **Phase 5** (with the bindings' evaluation: an allocation budget in the interpreter, or a child process with an OS limit).
  2. **Monte Carlo bits move with dependency bumps.** `unc.montecarlo_seed_1` depends on `rand`'s `StdRng` and `rand_distr`'s normal sampling, neither reproducible across versions: a bump of either is a reported witness change (exit 1), to be reviewed and accepted. Accepted and documented (the guide, section 9.6); owner: whoever bumps `rand` or `rand_distr`, who must say so in the changelog.
  3. **Cross-OS libm differences.** The C math library of the target (msvc, glibc) can differ in the last bit of `exp`, `ln`, `pow`, so the same release can make `verify --run` exit 1 on another operating system. Accepted: one frozen file per operating system (the guide, section 9.6). Owner: **Phase 5** if a binding needs one file across systems (a pure-Rust libm would remove it, at a cost to measure).
  4. **A user-witness hash shows only that something changed**, not what: the file keeps the hash, not the old result, and `verify --run` prints only the running canonical text. Accepted and documented (keep the canonical text or the file outside); owner: a later phase if users ask for the recorded canonical text in the file.
  5. **The window before the rename.** The compare-and-swap of `update` and `seal` now compares the SHA-256 of the bytes as well as the stamp (Phase 2 residual 6, built), but an edit made between that check and the rename is still overwritten; there is no lock. Accepted, as Phase 2 residual 1.
  6. **The engine check of `seal` is made on the file as read.** `seal` checks the `[Engine]` block of the draft's `old` (proved to be the sealed one by `only_the_overrides_changed`), then evaluates the probe; an edit of the engine block on disk after that read is caught only by the byte-hash check before the write (residual 5's window remains). Accepted; owner: the next change to `seal`.
  7. **`update` with nothing to do never evaluates.** Under `release` or `record`, a build of the same version (another commit, another C library) runs a file whose `update` says nothing to do, so the drift rule is never reached; `verify --run` is the check, and the guide says so (decision S9). Accepted.
  8. **A battery case that legitimately errs is a value.** `failed=<first line>` is compared like any result, so a reworded first line of an error message is a reported difference. Accepted (it is visible, never silent); owner: whoever rewords a core error a case can return.
  9. **Stack and memory isolation of `verify --run`.** The adversarial review of Phase 3 found that a flat operator chain (`x = 1+1+...+1`, 200,000 terms, 400 KB) ended `verify --run` and `freeze --witness` in a stack overflow (no JSON, a probe file left behind): the parser built a left-nested tree as deep as the chain, and the checker, the evaluator, `Clone` and `Drop` recurse over it. **Fixed at the root in `physure-script`:** the parser refuses an expression tree deeper than `MAX_EXPRESSION_DEPTH` (128 levels; measured in a debug build on a 1 MiB stack, the static checker, the most expensive pass with no stack check of its own, holds 349 levels, a factor of 2.7; the sandboxed evaluator stops itself with its stack budget), and `MAX_NESTING_DEPTH` (64) now also counts what makes the parser recurse without brackets (`if` chained after `else`/`then`/`if`, function bodies nested by indentation); `phs conf` deletes probe files more than a day old before it makes one. What remains: the scripts still run on a thread of the `phs` process, so a native stack overflow the bounds do not foresee (in a builtin, the symbolic engine) or an allocation the machine refuses still ends the process (residual 1). **Phase 5**: run user witnesses in a child process (stack and memory isolation, an OS memory limit), with the bindings' evaluation.
  10. **Evaluation under the unsandboxed interpreter.** `phs run` and the bindings evaluate on the caller's thread with no stack budget. Measured on a 1 MiB stack (a Windows main thread, a JVM thread, WebAssembly), the evaluator holds 35 (`not`) to 64 (`+`) levels of a chain in a debug build and 91 to 334 in release, against `MAX_EXPRESSION_DEPTH` = 128: a chain within the bound can still overflow such a thread there (it always did, with no bound at all). Not a witness path (witnesses are always sandboxed, on a 64 MiB thread with a 48 MiB stack budget). A bound low enough for that thread (about 16 levels in debug with a factor of 2) would refuse a sum of 17 terms. Accepted; owner: **Phase 5**, with the bindings (a stack budget for every interpreter, or a larger evaluation thread).

  Corrections made after the adversarial review (each with its tests): `verify --run --expect SEAL` evaluates nothing when the seal does not match; a user witness whose result has an error finding, or no result at all, is an error row (`verify --run` exit 1 even when the hash matches; `update` and `seal` never re-record it, whatever the flag), and `freeze` refuses a script that produces no result (exit 2); `--accept-witness-changes` with nothing to accept warns (stderr and JSON `warnings`, exit 0); under `binary` or `build` with the engine matching, a `NEW` built-in row is an error (keys were removed from an honest file), while under `release` and `record` it stays informational; `verify --run` hashes the bytes `inspect` verified and re-hashes the file just before evaluating (a change: nothing evaluated, exit 1) and just after (a change: results discarded, exit 1).
* **Residual risks left by Phase 4** (the data migration; each one has an owner, and each is a row of `docs/conf_coverage.md`):
  1. **Per-thread streams.** Draws outside a unit of evaluation (Python `Q_`, a host's own threads) come from a stream per thread, `mix(seed, k)` with `k` the order in which threads first drew: reproducible on one thread doing the same operations in the same order, not across threads. By design; owner: **Phase 5** (a unit of evaluation for each binding call that should reproduce).
  2. **`monte_carlo_seed = random` is not reproducible by choice.** `status` and `verify` warn (`reproducibility_warnings`); `phs eval`, MCP and user witnesses then draw seed 0. By design (owner decision).
  3. **`phs serve` requests are not independent replicates.** Every request starts at the position of the stream after the modules loaded, so the same request gives the same samples; the seed is read at start. Accepted and documented (the guide, section 10.2).
  4. **The language server's values depend on the edit history.** A document keeps its stream across incremental edits; a fresh open (and `phs file.phs`) reproduces. Accepted; owner: **Phase 5**, with the workspace resolution of Phase 1c residual 11.
  5. **Python, Java and WebAssembly are not frozen until Phase 5.** They read the compiled defaults or an unfrozen working-directory `physure.conf` for the new keys (the seed included), Python keeps its own currency, thermochemistry and atomic-weight tables (equal to the catalog edition for thermochemistry, a test), and Python's `str` does not follow the display keys (C11). Owner: **Phase 5** and chemistry plan 3.
  6. **M9 and M10 deferred by the owner.** Python's default coverage probability `p = 0.95` (M9) and the unit names written by code tables, `µ` against the catalog's `u` (M10). When M10 moves, unit text changes and with it the hash of a user witness (`unit=` is part of `phs-witness-1`). Owner: **Phase 5**.
  7. **Printed text the display keys do not govern**: the 15-digit cut before `frac`/`ifrac` and `MAX_DENOM`, a number quoted in an error message, the 17-decimal cap and the `-0.00` of a negative-zero mean, `format()` with a spec, plot axes, the symbolic printer; NaN prints `NaN.0` (audit T20, a defect, open; no display witness records NaN).   9. **Accepted-and-ignored settings.** The six keys of `CORE_UNUSED_SETTINGS` stay readable so that older confs load, and do nothing; `status` and `verify` warn where a user sets one. By design.
  10. **`use` modules and native plugins** are code outside the file (audit Q10: refuse them under a frozen file, or record their hashes). Owner: the owner's decision on Q10.
  11. **The catalog constants carry no uncertainty** (audit T14). Owner: a later catalog task (a grammar for a `[Constants]` uncertainty).
